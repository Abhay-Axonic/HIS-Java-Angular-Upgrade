# Angular Rebuild Playbook (Phase 3)

*Consolidated, repeatable process for rebuilding a legacy AngularJS 1.5 screen in modern Angular, refined from what both Phase 2 pilot batches (10 screens total) actually found — not a theoretical process, a corrected one. Written after both pilot batches were built, golden-trace audited, and manually domain-reviewed by the owner; every step below exists because something in that record either worked and is worth repeating, or failed silently and needs a specific counter-measure now baked in.*

*This is Phase 3: process/tooling/template hardening only. No new screens are rebuilt as part of this document. Phase 4 (scaling to the remaining ~1,557 screens) is a separate, not-yet-approved phase — see `docs/ANGULAR_PHASE4_SEQUENCING_RECOMMENDATION.md`.*

---

## Why this document exists

Phase 2 proved the rebuild *process* works — both pilot batches were audited, rebuilt, golden-trace verified, and are sitting on pushed feature branches. But the same two batches also surfaced two structural facts that must shape how the next ~1,557 screens get done:

1. **Golden-trace capture (initial page load) cannot catch interaction bugs.** All 4 of the bugs found-and-fixed in Phase 2 (status-toggle CSS/mutation, zero backend access control, MISReports dropdowns, broken patient search — `docs/ANGULAR_PENDING_FINDINGS.md` entries 12–15) were invisible to golden-trace and were only found when the owner manually clicked through the rebuilt screens side-by-side with legacy. A process that stops at golden-trace re-audit will silently ship these same bug classes into every future screen.
2. **A screen "looking real" is not the same as a screen being real.** Three separate screens across both pilots turned out, on close reading, to not be what they appeared: `addItemPOCreation` was a dead route shadowing a real one under a different name (entry 2), `SurgicalSiteInfection` was a copy-pasted non-functional mockup (entry 6), and `OTBillingCompletion`'s wired view was a stale clone of an unrelated screen's template (entry 7). All three were caught *before* rebuild effort was wasted on them, but only because of deliberate, close reading — not because any tooling flagged them automatically. Two of the five original batch-2 picks had to be swapped mid-project for this reason.

Everything below is built to make both of those failure modes structural, not something each new screen's session has to rediscover from scratch.

## The process, end to end

### Step 0 — Confirm the screen is real before committing a slot to it

Before spending any audit time on a candidate screen, confirm it is actually what it appears to be:

- Read the **view template in full** and check that its `ng-model`/`ng-click`/`vm.*` bindings resolve against functions that actually exist in the controller wired to that exact route (not a same-named function in a sibling file — `grep` across the directory, don't assume file proximity means correctness).
- Confirm the controller **wired to the route** is the one that actually implements the screen's apparent behavior, not a generic/shared controller that happens to also be reachable under a different, unlisted state (the `addItemPOCreation`/`addItemPO` pattern, entry 2). If a state routes through a shared controller (e.g. `MasterController`, 353 known screens) with a view referencing `vm.*` bindings, that view **cannot** be getting real data from that controller — it's very likely either dead or, per entry 2, silently duplicated under a different, self-registered state elsewhere in the codebase. Grep the whole tree for a `.config($stateProvider)` self-registration before concluding a screen is simply broken.
- If the view has **zero** live data bindings (no `ng-repeat`, no `ng-model` tied to anything the controller populates) and every interactive control calls a function absent from its own controller, treat it as a non-functional mockup (entry 6) and swap the pilot slot rather than rebuild a mockup for "parity."
- **Confirm the module ID and superuser requirement by reading the live `.state(...)` resolve block in `app.js` directly** (or the file's own `.config($stateProvider)` block, for a self-registered state) — never guess or infer it from the screen's apparent sensitivity. This is the exact value that goes into the new screen's route `data.moduleId` / `data.requireSuperUser` (see Step 3).
- **Confirm the screen's backend actually exists (added 2026-07-21, see entry 67).** A screen can pass every check above — real view, real controller, real-looking `GenericService`/`BillingGenericService` calls to real-looking endpoint constants — and still have **no working backend at all**. `modalityTypeMaster` (Phase 4 batch 7) is a confirmed instance: all 6 of its endpoint constants resolve correctly and are called correctly, but no Java controller/service/DAO implementing any of them exists anywhere in the codebase, and the real legacy app itself gets an identical 404 hitting them — this screen has, as far as the repo's history shows, never had a working backend, in any environment. The checks above are all frontend-only and cannot detect this. Before starting Step 2/3 on a new screen, run `python3 tools/angular-audit/check_backend_endpoints.py --only <stateName> --auth-token <fresh JWT>` (capture a real, currently-valid token from `cookieObject.authToken` in an active logged-in browser session — a plain unauthenticated check is unreliable: some endpoint prefixes reject anything without a valid token at a security-filter layer that runs *before* Spring MVC's routing, returning the same generic 401 whether the route exists or not, which silently masked this exact bug the first time this check was written). A screen where every endpoint 404s even with a valid token needs an owner decision before any rebuild time is spent on it, the same as an `addItemPOCreation`-style dead-frontend case — just the mirror image (dead backend, not dead frontend).

If any of the above turns up ambiguous or contradictory (the *addItemPOCreation*/*OTBillingCompletion* shape — a real, complete controller sitting disconnected from its wired view, or vice versa), stop and log it as a decision point rather than guessing which side is "real." Do not rebuild until it's resolved.

### Step 1 — Audit

Read the actual controller and view in full — not a skim, not an assumption based on filename or folder. Specifically check for:

- **The recurring missing-`$state`-DI crash bug.** Found independently in three separate controllers across both pilots (`organizationController.js`, `assetCategoryMasterController.js`, `implantMasterController.js` — entries 8 and 10): a login-redirect guard calls `$state.go('login')` on a missing session cookie, but `$state` was never added to that controller's own dependency-injection list, so it throws `ReferenceError` instead of redirecting — a blank/broken page on session expiry with no visible explanation. Grep any new controller's DI list against every `$state.*` call it makes before assuming the guard works. This is a legacy bug, not a rebuild bug — it doesn't block the rebuild, but the rebuild should use the safe pattern (defensive session check, never a literal port of the crash) the same way `organizationMaster`'s fix and `assigningPickerDispenser`'s rebuild both already did.
- **Whether `controllerAs:'vm'` in the state config is actually load-bearing.** Entry 11 found three controllers that declare `controllerAs:'vm'` in their self-registered state but assign almost exclusively to `$scope.*` (1 `self.`/`this.` assignment vs. 166 `$scope.` in one case) — their views have **zero** `vm.*` bindings anywhere. Declaring `controllerAs:'vm'` does not reliably mean the view uses it. Grep the view for `vm\.` usage before assuming which wiring pattern (classic `$scope` vs. `controllerAs:'vm'`) actually applies — this changes how the rebuilt component reads legacy's data flow, and guessing wrong wastes the whole audit.
- **Validation/business-logic duplication** (the `insuranceMaster` pattern, entry 1) — the same field can be validated by more than one independent mechanism (HTML5 attributes vs. a manual JS block) with different strictness. Preserve *all* layers found for true parity; don't assume the more visible one is the only one.
- **Race conditions and load-order assumptions**, not just final state. `insuranceMaster`'s ledger-name backfill (entry 4) only diverges from a byte-for-byte port in one specific, narrow case: which of two concurrent requests resolves first. A naive "does the final rendered state match" check misses this kind of thing entirely — read how legacy actually sequences its requests, not just what it eventually shows.
- What real, live data the backend actually needs to exercise this screen meaningfully (dev-DB seed gaps blocked real interaction testing on `insuranceMaster`, `MISReports`, and `inputOutputCharts` in Phase 2 until additive, owner-approved DB fixes unblocked them — plan for this rather than discovering it mid-audit).

**If this screen has a "sibling" — another screen that looks structurally similar (shared naming convention, same module, overlapping API calls, or a documented cluster from the screen-clustering analysis) — check for these 5 recurring divergence patterns specifically, confirmed across unrelated modules (procurement, pharmacy, lab, nursing, OPD) when 37 sampled "sibling" screens were checked against a designated core and only 1 came back a genuine faithful copy:**

- **Status-vocabulary drift.** Two screens that look like they track the same underlying concept (approval status, sample status, dispensing status) can use entirely different numeric or string vocabularies for it (`scheduleWorklist`/`PMSchedule`'s processStatus codes; confirmed again independently across 4 different inventory screens in the procurement cluster, each using its own status representation). Never assume a status code or string means the same thing in a sibling screen just because the field name matches — read what each screen's own save/approve logic actually writes and compares against.
- **Live-vs-commented-out guards.** The exact same check (a store-selection popup, a null-check on parsed session data, a checkbox column, a cancel button's wiring) can be fully live and correct in one screen and dead — commented out, or missing entirely — in a sibling that otherwise looks identical (`scheduleWorklist` has a live `storePopup()` check `PMSchedule` lacks entirely; the `assigningPickerDispenser`/`narcoticsIssueWorklist` null-check-ordering crash, entry 9, recurred independently in a third sibling screen during the clustering analysis). Diff the guard/check code between siblings line-for-line, don't assume "looks the same" means "behaves the same."
- **Wrong workflow category.** A screen that structurally clusters with an "approval workflow" family (search → select → approve/reject → save) can turn out to be a pure read-only report with no select/approve/save machinery at all, or a full transactional screen mixed in with read-only viewers. Confirm what KIND of screen this actually is (read-only display vs. transactional save vs. bulk-action worklist) before assuming it needs the same interaction model as its cluster-mates.
- **Non-functional mockups.** Some "sibling" screens have no real `ng-repeat`/data binding at all — a static single table row, a search button with no `ng-click` — the same pattern already known for 83% of the 353 `MasterController`-sharing screens, but confirmed to recur among screens with their *own dedicated* controller files too, not just shared ones. Check that the view's data-bound elements actually have live bindings before assuming a screen that looks complete is complete.
- **Bugs baked into the "reference" screen itself.** Don't assume the most full-featured or most-often-cited sibling in a family is a clean baseline — two separate designated "core" screens in the clustering analysis themselves called undefined functions (a broken pagination handler in one, a broken cancel-flow call in another), discovered only because a sibling's *absence* of the same bug made the comparison obvious. Audit the presumed-reference screen with the same rigor as any sibling, not as a trusted baseline.

A screen matching one of these patterns is not disqualified from rebuild — it's just evidence that "this looks like its sibling" is a hypothesis to verify with the same full audit, not a reason to shortcut one. See `docs/ANGULAR_PENDING_FINDINGS.md` entries 9, 28, 42 and the screen-clustering divergence analysis (session notes, 2026-07-20) for the full evidence behind these 5 patterns.

**Also check for shared, prototypal-scope directives with hardcoded calls to a function they assume the consuming controller defines (added 2026-07-21, see entry 55).** Legacy has several reusable UI directives (`<modal>`, `<dietCssdPopUp>`, `<shortcut>` — all in `resources/assets/js/common/`/`directive/`) built with `scope: true` (prototypal, not isolate) whose hardcoded template includes an `ng-click`/event binding calling a function (`cancel()`, `keyPressed()`) the directive itself never defines — it silently relies on the *consuming* controller happening to define it. If the screen's own controller doesn't, that interaction crashes in legacy today, invisibly, until someone actually clicks it. Before assuming a screen's confirm-modal/keyboard-shortcut/similar shared-widget interaction works, grep the screen's own controller for the specific function name the directive's template hardcodes — don't assume every screen using a shared directive is equally safe. (A 2026-07-21 sweep of all 49 already-built screens for `<modal>` usage specifically found 12 affected, cataloged in entry 55; `<dietCssdPopUp>` and `<shortcut>` were checked the same way and found unused by any already-built screen, so no retroactive gap exists for those two, but a *future* screen using either needs this same check applied fresh.)

### Step 2 — Golden-trace capture

Capture the real network calls (`tools/golden-trace/capture.js`) legacy makes on initial load for this screen, with real seeded session/cookie state. This remains valuable and worth keeping: it independently reproduced a real crash bug (`assigningPickerDispenser`, entry 9) purely from an anomalous call-count signature (2 calls instead of the expected 5), without anyone reading a line of that controller first. But treat it for what it structurally is — **a load-time signature only.** It will not catch anything that requires a click, a toggle, or a save to trigger. Do not treat a clean golden-trace re-audit as evidence the screen works; it's evidence the *initial load* works.

### Step 3 — Rebuild using the standard scaffold

Start from `new/src/app/features/_screen-template/` (built this phase — see "The template scaffold" below), not a blank component. It bakes in, by default:

- **`moduleAccessGuard`** (`new/src/app/core/module-access.guard.ts`) wired via the route's `canActivate` — parameterize `data: { moduleId, requireSuperUser }` from Step 0's confirmed values. A route with no module gate in legacy (e.g. `billingGroupMaster`, `periodicityService`) correctly omits `moduleId` entirely — don't invent a stricter check than legacy actually has.
- **The global `authInterceptor`** (`new/src/app/core/auth.interceptor.ts`, wired once in `app.config.ts`) — already attaches the `Authorization`/`userId`/`unitId` headers every backend call needs. Nothing per-screen to do here; this is infrastructure, not boilerplate to re-copy.
- **`<app-status-toggle>`** (`new/src/app/shared/status-toggle/`) for any status/active-inactive toggle UI. Wraps the corrected CSS (`input:checked + .slider` state, matching legacy's exact colors) and emits a `toggle` event the host component handles with a proper `signal.update()` call — never a direct in-place mutation of a row object nested in a signal's array (the fragile pattern entry 12 found: it doesn't corrupt data, but only visibly updates when *some other* signal write happens to trigger a re-render, which is not something to rely on).
- **`buildOptionalParams()`** (`new/src/app/shared/search/optional-params.ts`) for any multi-field search where legacy AND-combines whichever fields are non-empty. Send only the fields the user actually filled in — mirroring legacy's own conditional request-building — rather than sending every field with the same value (the `inputOutputCharts` bug, entry 15: sending UHID and name as the same string returns zero results for virtually any real search, since a real patient's UHID and name never overlap).
- **The shared `Shell` component** (`new/src/app/shell/shell.ts`, wrapping `<router-outlet>`) — as of Phase 4 batch 4, every new screen's route is nested under the `Shell` parent route in `app.routes.ts` with a real `data.title` (sourced from the screen's actual legacy state title, not invented), applied at this step, not retrofitted afterward. Add the screen's nav entry to `new/src/app/shell/shell-nav.data.ts` (grouped under the same module the audit tooling already assigns it) only if it's a "primary" destination — not a `detailsX`/`XDetails` screen reached only via another screen's row action, and not a parameterized/public/callback-only route. Grow the sidebar incrementally, batch by batch — do not attempt to replicate legacy's full sidebar in one pass (see `docs/ANGULAR_HYBRID_DEPLOYMENT_PROPOSAL.md` Part 2).

**Standing policy — shared component/directive behavior improvements (added 2026-07-21, see `docs/ANGULAR_PENDING_FINDINGS.md` entry 55):** when a shared Angular component or convention used by this rebuild (e.g. the `Shell`'s modal pattern, `<app-status-toggle>`, etc.) has correct, working default behavior that differs from a bug baked into legacy's own shared directive/partial (e.g. a hardcoded button calling a function that's never defined), this is an **acceptable, disclosed standing improvement** — not a parity violation requiring a fix or a retrofit. Log the specific instance once in `docs/ANGULAR_PENDING_FINDINGS.md` when first found (as entry 55 already does for the shared `<modal>` directive's `cancel()` crash), and do not re-litigate the same shared-component divergence screen by screen every time it recurs on a new screen. This is distinct from a screen-specific bug baked into that ONE screen's own controller — those still get faithfully reproduced per the rest of this playbook; this policy applies narrowly to bugs living in a shared, widely-reused legacy directive/partial that the rebuild's equivalent shared convention doesn't happen to replicate.

**Standing policy — validation-message visibility (added 2026-07-22, see `docs/ANGULAR_PENDING_FINDINGS.md` entries 111 and the batch 11 cross-cutting `.help-block` finding, owner decision 2026-07-22):** legacy's global CSS (`param.common.master.css:8445`, `.help-block{ display: none !important; }`) permanently hides every Angular "field is required"-style validation message on every screen using this widely-shared markup pattern, across the entire legacy app — confirmed a real, long-standing, unintentional legacy defect, not a deliberate UX choice (nothing in the `has-error`/`show-errors-check-validity` machinery is designed around messages being invisible; the CSS rule simply wins the cascade). The rebuild's validation messages render **visibly** by default across every screen built so far, and this is now a **formal, owner-approved standing policy** — an acceptable, disclosed improvement over legacy's broken CSS, in the same spirit as entry 55's shared-`<modal>` policy. Do not silently normalize this screen by screen, and do not "faithfully" suppress a rebuild's validation messages to match legacy's broken CSS — visible validation messages are the correct, sanctioned behavior going forward, no further owner sign-off needed per screen. This does not retroactively require re-auditing already-shipped screens; it confirms the behavior most of them already happened to have.

See the scaffold's own `README.md` for the full field-by-field checklist and placeholder tokens.

### Step 4 — Re-audit against the golden trace

Compare the rebuilt screen's actual network calls/responses against the captured trace. This catches load-time behavioral gaps a plain read-through misses — it's how `insuranceMaster`'s missing ledger-name backfill (entry 4) was found in Phase 2. Still only covers initial load; proceed to Step 5 regardless of a clean result here.

### Step 5 — Browser-automation interaction testing

Drive the rebuilt screen with real interactions — clicks, toggles, saves, searches with real seeded data — not just page load. This is not optional and not redundant with Step 4: **all four of Phase 2's fixed bugs were invisible to load-only verification and were only found this way.** Specifically exercise:

- Every status-toggle control, watching for both the server round-trip *and* the visible on-screen state change (the toggle bug was a case where the data changed correctly but nothing on screen showed it).
- Every search/filter control with realistic combined input (not just each field tested in isolation — the patient-search bug only appeared when both fields were populated at once, exactly what the UI's default behavior does).
- Access control: attempt to reach the screen as a session that legacy itself would deny, and confirm the rebuild denies it identically (compare against legacy's real "Access Denied" response for the same role, not an assumption of what should happen).
- Any parameter control that legacy renders as an interactive `<select>` — confirm the rebuild's equivalent is genuinely interactive, not silently hard-disabled (the MISReports bug, entry 14).

### Step 6 — Domain-expert manual review

A reviewer who knows the actual business/clinical/billing meaning of the screen reviews it side-by-side against legacy, live, with real data. This is what actually caught the toggle-CSS bug and the access-control gap in Phase 2 — not because the automated steps above were badly built, but because they structurally only look at load-time state and pre-specified interactions, and a domain reviewer notices "this looks wrong" in ways a script can't be written to check in advance. Keep this step even after Steps 2–5 are solid; it isn't redundant with them, it's a different failure mode entirely.

### Step 7 — Merge to a pilot/feature branch, hold for owner review

Every unit of work stays on its own branch. Merging into the batch/pilot branch (not `main`) is routine once verified; merging into `main` requires the owner's explicit go-ahead every time, no exceptions, regardless of how minor the change looks. Pushing a feature/pilot branch to GitHub for backup/review is lower-stakes and can be done routinely; pushing and merging are two separate decisions, and merging into `main` is the bigger one of the two.

**Standing decision — batch size (confirmed 2026-07-22, after a deliberate size experiment):** batches 9 and 10 (10 screens each) shipped with zero severity-1 findings between them. Batch 11 was deliberately sized at 15 screens to test whether a larger batch materially changed review difficulty or findings density — it produced 4 severity-1-tier findings (a rate increase, not just a raw-count increase from more screens) plus one malformed inter-agent report that needed independent re-derivation from source, and 2 of the 15 findings turned out to be misreads of legacy source that had to be caught and corrected during live testing rather than at review time. **Batch size is confirmed at 10 screens going forward** — the added coordination surface at 15 (more parallel agent groups, more simultaneous findings to cross-check) measurably increased the chance of an error slipping past review, without a clear compensating speed benefit, since the audit/rebuild work is agent-parallelized regardless of batch size.

## Clinical/Billing-Tier Addendum (added 2026-07-23, first applied at batch 15)

The administrative-tier low-risk pool is confirmed exhausted (`docs/ANGULAR_PENDING_FINDINGS.md` entries 142, 146 — a 53%-sample research pass on the remaining `MasterController` cluster found 0% alive, worse than the ~83%-dead partial estimate that preceded it). Starting with batch 15, new batches draw from the clinical/billing risk tier. This is a deliberate policy shift, not a routine batch, and changes the process as follows — these changes apply **only** to clinical/billing-tier batches; admin-tier batches (should any remain or resurface) keep the process as documented above, unchanged.

**Step 6 is mandatory and blocking for this tier, not a best-practice recommendation.** In practice, across every admin-tier batch so far, Step 6 collapsed into "the rebuild agent's own Step 5 interaction testing, summarized in a report the owner approves" — not an independent domain review. That is no longer sufficient for this tier. No screen in this tier merges to `main` without a recorded sign-off distinct from the rebuild agent's own Step 5 testing: who reviewed it, what real data they used, what they specifically confirmed, and any discrepancy they caught that automated testing missed. The sign-off is a real artifact appended to the batch's findings entry — "approved" in chat is not sufficient by itself for this tier, the same way every other finding in this project is expected to leave a record, not just a verbal go-ahead.

**Step 6 splits into two parts for this tier:**
- **6a** — the existing domain-expert side-by-side review (a reviewer who knows the screen's real business/clinical/billing meaning clicks through the rebuilt screen against legacy, live, with real data), now mandatory and auditable per above, for every screen in the tier.
- **6b (new)** — for the narrower subset of screens touching an actual billing **calculation** (amount, discount, tax, cap, threshold, rounding) or a clinical **safety-relevant** workflow (dosing/administration, patient identification, critical-value alerting, consent): a named subject-matter expert — a billing/finance lead for the former, a clinician for the latter, not this project's usual code-reading discipline — must explicitly attest that the **observed behavior itself** is correct, not merely that it matches legacy. Steps 0-5 can only establish "matches legacy"; they cannot establish "legacy is right here," and this project's own mission (`CLAUDE.md`) ranks billing accuracy above faithful reproduction of a potentially-wrong legacy calculation. If an SME determines legacy's own behavior is substantively wrong (not cosmetically different), that escalates to a DECISION_NEEDED doc — the same mechanism already used for the JWT-signing-key and resetPassword findings — rather than the standard "log it and faithfully reproduce it" treatment every other bug gets.

**No named SME currently exists on this project for 6b (open dependency, flagged 2026-07-23).** If a screen in this tier requires 6b and no SME is available, **that screen is held — not silently skipped, and not downgraded to a 6a-only review.** A screen requiring 6b is not considered complete through Step 7 until a real sign-off exists. This is a standing gate, not a one-time exception to work around.

**Batch size defaults to 5 for this tier** (not the standard 10), until a track record across 2-3 batches justifies scaling back up — mirroring how the 10-screen standard itself was set empirically after the batch-11 experiment (see the batch-size decision above), not assumed by analogy.

**Composition is deliberately diversified** across clinical-only / billing-only / both risk tags, per the original Phase 2 pilot's own practice — it picked across risk tiers deliberately and explicitly disclosed when the resulting mix skewed (e.g. "the final 5-screen batch has two billing-only picks and no both pick — flagging that trade-off rather than deciding it's fine") rather than silently accepting whatever was easiest to find. Any forced skew in a future batch's actual candidate pool must be disclosed the same way, in that batch's own candidate-research writeup.

**Phase 0's risk tags remain confirmed unreliable in both directions** (module folder names can hide real clinical/billing content, and keyword sweeps can false-positive on aggregate/administrative screens) — this does not relax for this tier. If anything, a false negative here (missing that something is more sensitive than tagged) is more costly than in the admin tier. Every candidate still gets full individual verification before selection, same discipline as every prior batch's candidate research.

## Phase bookkeeping: the substantive transition from Phase 4 to Phase 5 (2026-07-24)

**This document's own title and intro (above) still say "Phase 3" and describe "Phase 4" as scaling the low-risk tier — that framing is now stale and this section corrects it, without changing anything about how batches are actually run.** `docs/ANGULAR_REMAINING_POOL_RECONCILIATION.md` (written 2026-07-24) put a real, sampled number behind what this project had already concluded going into batch 15: the low-risk/administrative tier is confirmed exhausted, not just low-yield. A 53%-sample of its remaining `MasterController`-routed screens came back 0% alive (entry 146); the low-risk tier's real remaining buildable count is now estimated at roughly 5-20 screens project-wide, not the hundreds implied by the original tier-size tag.

**In substance, batches 15 through 17 (and everything after) are Phase 5 work — rebuilding the medium/higher-risk clinical and billing tier — even though batch numbering continues sequentially from Phase 4's batches rather than resetting to "batch 1" under a new phase label.** This is a documentation/bookkeeping acknowledgment, not a process change:

- The Clinical/Billing-Tier Addendum above (added at batch 15) already **is** Phase 5's actual process — nothing in it needs to change because of this section.
- Branch naming (`rebuild/phase4-batchN`) is **not** being renamed retroactively or going forward — renumbering branch conventions mid-project would cost more in confusion than it buys in accuracy, and batch numbers are already a continuous, unambiguous sequence on their own.
- The one real, practical implication: **do not go looking for more low-risk-tier batches.** If a future candidate-research pass finds itself reaching for the low-risk tier "because it's easier," that's a signal to stop and re-check against `docs/ANGULAR_REMAINING_POOL_RECONCILIATION.md` first — the ~5-20 remaining real screens there are not confirmed individually yet, and treating that tier as a fallback source of "easy" batches without re-verifying would repeat exactly the mistake entry 146 caught (assuming a shared-controller cluster is a viable pool without sampling it first).
- The clinical/billing tier's own true remaining size is **not yet reconciled with the same rigor** — `docs/ANGULAR_REMAINING_POOL_RECONCILIATION.md` section 6 flags this as a very-low-confidence estimate (~1,190-1,215, largely untested) pending a comparable sampling pass against that tier's own 283 uncharacterized `MasterController`-routed screens. That research task is proposed, not yet scheduled, as of this writing.

No other part of this playbook changes. Step 0-7, the confirm-modal/validation-visibility/shared-directive standing policies, batch sizing (5 for this tier), and the diversification rule all carry forward unchanged.

## Known caveats carried forward — do not silently forget these

These are open, undecided items from Phase 2 that Phase 3 does not resolve (no application/business-logic code changed this phase) and that should not get lost as the project moves toward Phase 4:

1. **`billingGroupMaster` and `periodicityService` have no module-level access gate, in legacy or the rebuild — by design, matching legacy exactly, not a rebuild bug.** This is a known, pre-existing gap in legacy's own security model (module permission is enforced *only* in legacy's frontend router — confirmed zero backend-level `@PreAuthorize`/`@Secured`/`hasRole` usage anywhere, and `JwtTokenFilter` only validates the JWT itself). Worth a dedicated, separately-scoped security-hardening decision at some point — explicitly **not** something to fix piecemeal during parity rebuilds, since parity means matching legacy's actual behavior, gaps included, until the owner decides otherwise.
2. **`implantMaster` and `organizationMaster`'s status-toggle fix (CSS + signal-update pattern) was applied but never independently click-verified** — no real hospital/implant master data exists in this dev environment, and fake data was deliberately not fabricated to force a test. `billingGroupMaster`, `insuranceMaster`, and `assetCategoryMaster` were live-click-verified and confirmed working. Re-verify the other two once real seed data exists in any environment.
3. **`MISReports`' unit/user/org dropdowns render correctly and are genuinely interactive, but show 0 options in this dev environment** — a missing-seed-data gap (`metaDataDetailsDtosList` empty), not a code defect. ## What this phase deliberately did not do

- No new screens were rebuilt.
- No application/business-logic code was changed (the scaffold branch adds new, previously-nonexistent reusable components — it does not modify any of the 10 already-built pilot screens or their behavior).
- Phase 4 was not started — only a sequencing *recommendation* was written, for the owner's review.**STANDING SIBLING-ENDPOINT CHECK (added 2026-08-03 after BR-160):** after fixing (or verifying) a screen's PRIMARY CRUD paths, **explicitly enumerate EVERY OTHER endpoint the screen calls** — status toggles, secondary actions, related child-record operations, view/detail fetch paths — and check EACH for the same org/unit-trust pattern before declaring the screen's backend secured. BR-160 proved a screen's "done" fix can still leave an unchecked sibling endpoint: BR-159 secured `multicounterPackage`'s 4 creation endpoints + child propagation, but the screen's status-toggle path (`inActivePackage`, keyed only by `parent_package_id`) remained a live cross-tenant write-by-ID until caught during the rebuild's Step 1 re-audit. Do not infer "the other endpoints are fine" from the primary path being fixed — enumerate the screen's full endpoint surface (controller JS → all URIs → backend controllers → DAO methods) and verify org/unit scoping per endpoint. This applies to every billing-tier screen, not just this batch.
