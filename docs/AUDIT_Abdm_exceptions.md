# Audit: Silent Exception-Swallow Patterns — legacy/Abdm module

*Read-only audit, 2026-07-06. Same method as `docs/AUDIT_Billing_exceptions.md`, `docs/AUDIT_Global_exceptions.md`, `docs/AUDIT_ADT_exceptions.md`, `docs/AUDIT_BloodBank_exceptions.md`, `docs/AUDIT_CSSDMaster_exceptions.md`, `docs/AUDIT_Pharmacy_exceptions.md`, `docs/AUDIT_DietAndKitchen_exceptions.md`, and `docs/AUDIT_OTIMS_exceptions.md`; scope here is the Abdm module (Ayushman Bharat Digital Mission integration) — ABDM/FHIR health-data-exchange: credential/session management with the ABDM gateway, FHIR bundle construction for consultations/prescriptions/diagnostics/discharge summaries, and a vendored `in.projecteka.fidelius` encryption/key-management library (ECDH key exchange, AES-GCM encrypt/decrypt, key-pair generation) nested under an unusual `com/param/src/main/java/in/projecteka/fidelius/...` path.*

**Scope:** every `.java` file under `legacy/Abdm` (47 files, all under `src/main/java` — no `src/test/java` directory exists in this module; file enumeration was done with a recursive `find` that reaches both the normal `com/param/{*, fhir/model}` packages and the nested vendored `com/param/src/main/java/in/projecteka/fidelius/{, keys, dercyprion, encryotion}` packages — confirmed all 47 files are reached, including the 10 fidelius files). 497 `catch` blocks structurally parsed.

**Method:** read-only. Automated structural parse (comment/string-aware brace matching, implemented as a small Python script since this module's total line count, ~40,700, and one single file's line count, 25,382, made pure manual reading impractical for full coverage) of every `catch` block, classified by body content, cross-checked by manual sampling — spot-checked empty-catch findings, hardcoded-generic-error findings, `e.getMessage()`-referenced findings, printStackTrace-only findings (including one inside a `static { }` initializer block and one where the parser correctly scoped to the catch body only, excluding a `return null;` sitting *after* the try/catch rather than inside the catch itself), all 8 properly-rethrow exclusions in the vendored `DecryptionController.java`/`AbdmCredentialController.java` files, the multi-catch check (none found), the 4-file raw/structural gap, and the billing-critical file set (all 4 forward-import hits opened and read directly) — all matched their classification. The parser itself was first validated against a raw `catch\s*(` grep count (501 raw occurrences vs. 497 structurally valid — the 4-occurrence gap was manually confirmed to be entirely commented-out/dead code: three `/* ... */`-fenced dead catch blocks inside abandoned scratch code in `AbdmCredentialDaoImpl.java` (an unused "transfer" HTTP-call block around line 3533, and two unused discharge-summary-JSON-building blocks around lines 12815 and 18505 — all leftover experimental code fenced entirely in block comments), plus one dead catch inside a `/* ... */`-fenced example snippet in `DiagnosticReportImagingDcmSample.java` (line 151) — the same dead-scaffolding pattern noted in every prior audit in this series, just larger in raw byte count here because the dead blocks themselves are large. No file under `legacy/` was modified.

**Definition used (per task, identical to every prior audit in this series):** a finding is any catch block that is (a) empty, (b) returns `null`/a generic hardcoded error with no logging of the real cause, or (c) neither logs (via a real logger call) nor rethrows. Catch blocks that call a real logger (`logger.error(...)`/`log.error(...)`, backed by an `org.apache.log4j.Logger` or `org.slf4j.Logger` import) or that `throw`/rethrow anywhere in the body are excluded as non-findings.

**189 billing-critical findings (61.0% of all findings), concentrated in exactly 2 of the module's 47 files** — `AbdmCredentialDaoImpl.java` (185 findings) and `AbdmCredentialController.java` (4 findings). Per the file-level propagation convention used throughout this series, every one of the file's 185 findings — including many that are ABDM-credential/session/consent methods with no billing content of their own — inherits billing-critical status.

## Methodology caveats (read before acting on this list)

- **Billing-critical determination required the forward-import criterion, not the filename criterion.** Checked from every angle used in prior audits: (a) **package check** — no file lives under `com/param/billing/` or `com/param/global/billing/`; all 47 files are under `com/param/{*, fhir/model}` or the vendored `com/param/src/main/java/in/projecteka/fidelius/*`. **Zero hits.** (b) **path/filename keyword check** (`payment|invoice|tariff|discount|deposit|fund|insurance|razorpay|pesapal|charge|voucher|refund|bill|consumption|collection|sanction|mpesa|ccavenue`, with the `(?<!dis)charge` exclusion) — exactly one filename match, `DischargeSummarySample.java`, which is the expected `discharge`-collision false positive (a clinical discharge-summary FHIR sample, unrelated to billing) — **excluded, zero genuine filename hits**. (c) **reverse-import check** — whether `legacy/Billing` or `legacy/Global` imports anything from any Abdm package (`com.param.Abdm*`, `com.param.fhir.*`, `in.projecteka.fidelius.*`) — **zero hits**. (d) **forward-import check** — whether any Abdm file imports `com.param.billing.*` or `com.param.global.billing.*` directly — **4 hits**: `AbdmUrlMaster.java` (imports `com.param.billing.global.transaction.model.InsuranceMaster`, but the import is unused/dead — no reference anywhere else in the file — and the file has zero catch blocks, so it contributes zero findings but is still billing-critical by the letter of the criterion), `AbdmCredentialdDto.java` (imports and actually uses `com.param.global.billing.dto.ItemDetailsResponse` as a DTO field type — `List<ItemDetailsResponse> items` — but this is a pure DTO with zero catch blocks, so again zero findings), `AbdmCredentialController.java` (imports and catches `com.param.global.billing.controller.BillingException` in ~90 method pairs — see below), and `AbdmCredentialDaoImpl.java` (imports and *constructs* `com.param.global.billing.dto.ItemDetailsResponse`/`BillListResponse` objects with real tax/rate/amount fields inside `v3DataFlowHealthInformationHipOnRequest` — see Summary). **Per this series' established convention (see OTIMS audit's `OTReservationDaoImpl.java`/`ProcedureTemplateServiceImpl.java` treatment), billing-critical status is applied at the file level once criterion (d) is met — every finding in a billing-critical file is marked billing-critical, not just the specific catch block that touches billing logic.** This is why all 185 `AbdmCredentialDaoImpl.java` findings are billing-critical even though only a handful of its ~200 methods touch `ItemDetailsResponse`/`BillListResponse` directly, and why all 4 `AbdmCredentialController.java` findings are billing-critical even though those 4 specific catches are plain `printStackTrace()`-only clauses with no billing content of their own.
- **`AbdmCredentialController.java`'s `BillingException` catches are almost all non-findings, and this is worth flagging as a genuine positive pattern.** Nearly every one of its ~90 public endpoint methods follows `catch (BillingException be) { throw be; } catch (Exception e) { throw e; }` — both catches contain a real `throw` and are correctly excluded. A number of these methods also have a **dead, commented-out** `//throw new BillingException(e.getMessage());` line sitting *after* the live `throw e;` — harmless leftover scaffolding, not counted, since the live throw already satisfies the rethrow exclusion. Only 4 methods in the whole file deviate from this pattern (their `catch (Exception e)` block is `e.printStackTrace();` with no throw) — those 4 are the file's only findings.
- **A "fabricated success" sub-pattern was found and is flagged specifically, matching the kind of check the OTIMS audit's commit history describes doing for `ProcedureTemplateServiceImpl.java`/`OTReservationDaoImpl.java` (where none was found).** Here, 5 catch blocks across 2 files return a **hardcoded `SUCCESS` status with a `null` payload** instead of an error status: `AbdmCommonUtil.java:150`, and `AbdmCredentialDaoImpl.java:360, 907, 1084, 1548` (methods `getCredentialDetails`, `onFetchModes`, `getCredentialDetailsByHealthId`, `checkPatientAlreadyExist` — all ABDM credential/session/patient-lookup DAO methods). This is strictly worse than the module's dominant hardcoded-generic-error pattern: a caller receiving `Response(SUCCESS, SUCCESS_CODE, null, null, null)` after a real exception has no way to distinguish "the operation succeeded with no data" from "the operation silently failed." 4 of these 5 are in the billing-critical `AbdmCredentialDaoImpl.java` file (inheriting that status via file-level propagation, not because these particular methods touch billing data themselves) and are flagged individually in the findings table below with an explicit NOTE. This is a distinct, more severe variant of `silent-swallow` (not reclassified as `status-masks-failure`, since that severity is reserved strictly for a catch body that is `return null;` and nothing else, per this audit's definition — these bodies return a `Response` object, not `null`, and one of the four also has a `printStackTrace()` call preceding the return).
- **`AbdmCredentialDaoImpl.java` is a single 25,382-line file — the largest file in this entire audit series by a wide margin** (for comparison, OTIMS's largest file, `OTReservationDaoImpl.java`, was a few hundred lines). Because full manual line-by-line reading of a file this size is impractical, this audit relied on an automated structural parser (comment/string-aware brace matching) for full coverage, with targeted manual spot-checks (opening the actual source at ~20 reported line numbers spanning empty catches, hardcoded-error catches, `getMessage()` catches, printStackTrace-only catches, the fabricated-success catches, and the `IOException`/`UnsupportedEncodingException` catches) to confirm the parser's brace-scoping was correct — in particular, confirming that `return null;`/`return new Response(...)` statements sitting *after* a catch block's closing brace (i.e., the method's own fallback, not the catch's own body) were correctly excluded from that catch's classification, exactly as CSSDMaster/Pharmacy/DietAndKitchen's audits describe doing for their own "catch-body-only" scoping rule.
- **The `printStackTrace()`-only vs. `printStackTrace()`-plus-substantive-return distinction was applied exactly as tightened in the Pharmacy audit.** A catch body whose only statement(s) are `e.printStackTrace()` and/or `System.out/err.println(...)` is classified `other` (164 such findings — by far the largest `other` count in this series, reflecting how pervasive `printStackTrace()` is in this module's copy-pasted method template). A catch body that does `e.printStackTrace()` **and then** returns a hardcoded error, `e.getMessage()`, or (per the fabricated-success note above) a hardcoded `SUCCESS`, is classified `silent-swallow` — the printStackTrace() call is noted in the row but doesn't change the severity, since it's console-only and the substantive return is what actually reaches the caller.
- **`status-masks-failure`** (the strict `return null;`-and-nothing-else pattern) — **zero instances** in this module, same as OTIMS. Every catch body in this module that returns something returns a `Response`-shaped object (even the 5 fabricated-success ones), a `String` message, or is genuinely empty/print-only; no catch body anywhere is exactly `return null;`.
- **Multi-catch clauses** (`catch (TypeA | TypeB e)`) — **zero** occurred in this module, same as every prior audit in this series.
- **2 of the module's 47 files are pure interfaces** (`IAbdmCredentialControllerService.java`, `IAbdmCredentialDao.java` — both verified with `interface` keyword, second-character-uppercase convention, no naive `I*.java` overcounting issue here since no implementation class in this module happens to start with a capital `I`) with zero catch blocks by construction.
- **Every one of the 10 files with at least one catch block has at least one finding — there are no "clean" implementation files in this module** (unlike OTIMS, which had 3 clean service classes where every catch properly rethrew). The closest counter-example is `AbdmCredentialController.java` (see above): 173 of its 177 catches properly rethrow, but the remaining 4 are still findings, so the file as a whole isn't "clean." The other 37 files with zero catch blocks are DTOs, FHIR model/POJO classes, serializers/deserializers, and small vendored key-material classes that simply never use try/catch.
- **The 4-occurrence raw-vs-structural gap is entirely dead/commented-out code**, detailed in the Method paragraph above: 3 in `AbdmCredentialDaoImpl.java` (all `/* ... */`-fenced abandoned experimental blocks — a leftover HTTP "transfer" call and two leftover discharge-summary JSON builders, none reachable at runtime) and 1 in `DiagnosticReportImagingDcmSample.java` (a `/* ... */`-fenced example snippet). Consistent with the same dead-scaffolding pattern found in every prior module in this series.
- **The parser is structural, not control-flow-aware**, identical caveat to every prior audit in this series: a catch block containing `throw` anywhere in its body is treated as "properly rethrows" and excluded, even if a nested conditional path could still silently fall through without throwing.
- **The vendored `in.projecteka.fidelius` library (10 files, ~530 lines combined) contributes only 4 findings, all in files with a single catch block each**, and none are billing-critical (this vendored encryption/key-management code is entirely about ECDH key exchange and AES-GCM encrypt/decrypt for ABDM data-sharing consent flows, unrelated to billing by any of the four criteria). Its logging is entirely `printStackTrace()`/`System.out.println` as well — no separate logging framework was found here despite the task's suggestion to check for one; the only non-JDK/non-Spring imports in this sub-package are Bouncy Castle cryptography classes. Two files in this sub-package (`DecryptionController.java`, `EncryptionController.java`) properly `throw`/rethrow in their substantive `decrypt`/business-logic catches (`InvalidCipherTextException`/`Exception` in `DecryptionController.java`'s `decrypt` helper), with the module's only finding in each coming from a separate, less consequential catch (a `static { }` initializer block in `DecryptionController.java`, and the encryption routine's outer catch in `EncryptionController.java`).
- This audit does **not** re-scan `legacy/Billing`, `legacy/Global`, `legacy/ADT`, `legacy/BloodBank`, `legacy/CSSDMaster`, `legacy/Pharmacy`, `legacy/DietAndKitchen`, `legacy/OTIMS`, `legacy/Entity`, or any other module — it is Abdm-only, matching this task's scope. In particular, it does not audit the `com.param.global.billing.dto.ItemDetailsResponse`/`BillListResponse`/`com.param.billing.global.transaction.model.InsuranceMaster`/`com.param.global.billing.controller.BillingException` classes themselves (they live in `legacy/Billing`/`legacy/Global`, already covered by their own prior audits in this series) — only Abdm's *imports and use* of them.
