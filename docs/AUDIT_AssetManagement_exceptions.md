# Audit: Silent Exception-Swallow Patterns — legacy/AssetManagement module

*Read-only audit, 2026-07-06. Same method as `docs/AUDIT_Billing_exceptions.md`, `docs/AUDIT_Global_exceptions.md`, `docs/AUDIT_ADT_exceptions.md`, `docs/AUDIT_BloodBank_exceptions.md`, `docs/AUDIT_CSSDMaster_exceptions.md`, `docs/AUDIT_Pharmacy_exceptions.md`, `docs/AUDIT_DietAndKitchen_exceptions.md`, and `docs/AUDIT_OTIMS_exceptions.md`; scope here is the AssetManagement module (fixed-asset lifecycle management — auction/disposal requisition and vendor approval, fixed-asset opening balance, asset indent/issue/return/acceptance/rejection workflow, preventive/corrective maintenance scheduling and spares consumption, and non-returnable gate-pass tracking) under `com/param/assetManagement/{auctionRequisition,auctionVendorApproval,fixedAssetOpeningBalance,indent,itemForAuction,maintenance,nonReturnableGatepass,pmsfrequency}`, plus one stray `com/param/pharmacy/master/unit/dao/pmsfrequency` file.*

**Scope:** every `.java` file under `legacy/AssetManagement` (153 files — 151 under `src/main/java/com/param/assetManagement/**`, 1 stray file under `src/main/java/com/param/pharmacy/master/unit/dao/pmsfrequency/PMSFrequencyDao.java` (a Hibernate DAO implementing `com.param.assetManagement.pmsfrequency.dao.IPMSFrequencyDao`, misplaced under a `pharmacy` package prefix but functionally and physically part of this module), and **1 file under `src/test/java`** — `com/param/AssetManagement/AppTest.java`, a trivial unused Maven-archetype JUnit scaffold (`assertTrue(true)`, zero catch blocks, zero findings) included in the file count and scanned like every other file, per this task's instruction not to skip test code. 227 `catch` blocks structurally parsed.

**Method:** read-only. Automated structural parse (comment/string-aware brace matching, a small Python script) of every `catch` block in all 153 files, classified by body content, cross-checked by manual sampling (spot-checked empty-catch findings and the two dominant sub-patterns across controller/dao/service layers — including the DAO `HibernateException`-then-`Exception` double-catch, the controller-layer `new ErrorResponse(code, message, ex)` pattern, and both exclusion categories, rethrow and logged — plus the billing-critical judgment calls below — all matched their classification on manual re-reading of the actual source). The parser itself was first validated against a raw `catch\s*(` grep count (231 raw occurrences vs. 227 structurally valid — the 4-occurrence gap was manually confirmed to be entirely commented-out/dead scaffolding code, one instance each in four files: `CorrectiveMaintenanceScheduleController.java` (a dead `/* @RequestMapping(value = "/order"...) */`-fenced method, lines 42–59), `PreventiveMaintenanceController.java` (a dead `/* @RequestMapping(value = "/saveAssetSchedule"...) */`-fenced method containing a `return null;`/generic-error catch, lines 88–105), `CorrectiveMaintenanceScheduleDaoImpl.java` (a dead `/* @Override searchFixedItemListByCodeOrName(...) */`-fenced method, lines 193–219), and `PreventiveMaintenanceServiceImpl.java` (a dead line-`//`-commented `saveOrUpdateSpareConsumption` method, lines ~231–238) — the same "abandoned scaffolding left in place" pattern noted in every prior module in this series, just with different method names here rather than a repeated `addSample` template). No file under `legacy/` was modified.

**Definition used (per task, identical to every prior audit in this series):** a finding is any catch block that is (a) empty, (b) returns `null`/a generic hardcoded error with no logging of the real cause, or (c) neither logs (via a real logger call) nor rethrows. Catch blocks that call a logger (`logger.error(...)`, etc.) or that `throw`/rethrow are excluded as non-findings.

## Methodology caveats (read before acting on this list)

- **Billing-critical heuristic returned zero hits on strict application of all four criteria, but one file required real investigation before being excluded — this is the key methodological finding of this audit.** (a) **Package check:** no file lives under `com/param/billing/` or `com/param/global/billing/` — all 153 files are under `com/param/assetManagement/**` or the stray `com/param/pharmacy/master/unit/dao/pmsfrequency` package. **Zero hits.** (b) **Filename/path keyword check** (`payment|invoice|tariff|discount|deposit|fund|insurance|razorpay|pesapal|charge|voucher|refund|bill|consumption|collection|sanction|mpesa|ccavenue`): exactly **one filename match**, `fixedAssetOpeningBalance/dto/InsuranceDetails.java` — opened and confirmed to be a pure getter/setter DTO describing a *fixed asset's* insurance policy (insurer name, policy number, policy dates, insured amount for e.g. fire/theft cover on hospital equipment), not patient health insurance or a billing/claims concept; it also has zero catch blocks, so the match is moot regardless of interpretation. No other filename hits anywhere in the module (no `bill`, `charge`, `payment`, `invoice`, `tariff`, `discount`, `deposit`, `fund`, `voucher`, `refund`, `sanction`, or gateway-name hits at the path level). (c) **Reverse-import check** — whether `legacy/Billing` or `legacy/Global` imports anything from this module's actual packages: `legacy/Billing` has **zero** references to `com.param.assetManagement` anywhere. `legacy/Global` imports `com.param.assetManagement.maintenance.dto.*` (`VendorDto`, `InsuranceDto`, `CorrectiveMaintenanceDto`, etc.) from three `Doctor*` classes — **but this is the same kind of package-name collision the OTIMS audit documented for `com.param.otims.model`**: the `com.param.assetManagement.maintenance.dto` package is not physically part of `legacy/AssetManagement` at all — it lives entirely inside `legacy/Global/src/main/java/com/param/assetManagement/maintenance/dto/`, a different Maven module that merely reuses this module's package prefix for its own DTOs. None of the 153 files scanned in this audit are in that `dto` package (this module's `maintenance` subpackage only has `controller`, `dao`, and `service`, no `dto` of its own), so this is **not** a genuine reverse-import hit against the audited module, and (per the OTIMS precedent) does not change any classification — it is flagged here only so it isn't mistaken for one. (d) **Forward-import check** — whether any AssetManagement file imports `com.param.billing.*` or `com.param.global.billing.*` directly: **zero literal hits**, confirmed by grep across all 153 files. **However, one close, deliberately-investigated call was found and excluded on the specifics**: `CorrectiveMaintenanceScheduleServiceImpl.java` autowires `com.param.global.pharmacy.dao.IWalkInSalesDao` (not `com.param.billing.*`/`com.param.global.billing.*` — a *pharmacy* DAO package) and calls its `saveStockTransaction(stockTransaction)` method to persist a `StockTransaction` (which carries a monetary `rate` field, from `batch.getRate()`) when a corrective-maintenance item is disposed. The concrete class behind that interface, `WalkInSalesDao.java` (which physically lives in `legacy/Global`, not this module), does import genuine billing types (`com.param.global.billing.controller.BillingException`, `com.param.global.billing.dto.PaymentDepositDetailsDto`, `com.param.global.billing.dto.AdmissionListIpdChargesResDto`) — but only for its *other* methods (walk-in pharmacy sales, unrelated to asset disposal); the specific method AssetManagement actually calls, `saveStockTransaction`, is a bare `getSession().save(stockTransaction)` Hibernate persist with no billing computation, invoice, or charge logic in it. Judged **not** billing-critical under a strict reading of criterion (d) — the import is not literally a billing package and the called method does no billing work — but flagged here explicitly, at the same level of detail as the OTIMS `Deposite` and DietAndKitchen `paymentEntitlementId` judgment calls, because it is a real architectural coupling (asset-disposal stock movements share a DAO class with patient-billing-adjacent pharmacy sales) that the owner should be aware of even though it did not change this audit's classification. The one catch block enclosing this call (`CorrectiveMaintenanceScheduleServiceImpl.java:147`, empty `catch (Exception e)`) is counted as a peripheral finding, not billing-critical.
- **A second, smaller content-level judgment call: the `payment` keyword.** Content-level (not filename-level) matches for `paymentTerms` appear as a plain `String` field on `itemForAuction/dto/VendorDetails.java`, `itemForAuction/dto/VendorDetailsResponse.java`, and are read/passed through `itemForAuction/service/ItemForAuctionService.java` and `auctionVendorApproval/service/AuctionVendorApprovalService.java` — but this describes a vendor's stated payment terms (e.g. "Net 30 days") for purchasing a *scrapped/auctioned* hospital asset from the hospital, a free-text descriptive field, not a calculated monetary amount, invoice, or patient charge. None of these four files match any criterion independently (no billing import, no filename keyword hit, no monetary calculation performed on the field itself), so this judgment call did not change any classification. The controllers that do have findings in this same subsystem (`ItemForAuctionController.java`, `AuctionVendorApprovalController.java`, `AuctionRequisitionController.java`, `AuctionRequisiApprovalController.java` — 9 findings between the sampled two, all counted above) remain peripheral for the same reason.
- **The `charge`/`consumption` keywords produced no genuine billing hits.** No non-`discharge` `charge` substring exists anywhere in the module (checked with the same `(?<!dis)charge` exclusion regex used in ADT/Pharmacy/OTIMS — there is no `discharge` collision here either, since AssetManagement has no patient-facing discharge concept at all). `consumption`/`Comsumption` [sic, misspelled in several class/file names throughout the maintenance subsystem] refers exclusively to **spare-parts consumption during equipment maintenance** (`CorrectiveMaintenanceSparesComsumptionDaoImpl`, `SpareConsumptionDto`, `CorrectiveMaintenanceSparesComsumptionDto`) — an inventory/stock concept, not the patient-service-consumption-tied-to-billing concept seen in the Pharmacy audit's `consumption` package.
- **The new `new ErrorResponse(code, message, ex)` sub-pattern (82 findings, 15 controller files) is classified `silent-swallow`, not excluded, and not `other`.** `ErrorResponse` (`legacy/Entity/src/main/java/com/param/common/dto/ErrorResponse.java`) is a shared DTO whose constructor internally runs `ex.printStackTrace(new PrintWriter(writer))` against an **in-memory `StringWriter`**, then copies the resulting stack-trace string and `ex.getMessage()` into fields serialized back to the HTTP caller. This is meaningfully different from a `printStackTrace()`-to-console call (Billing/DietAndKitchen's `other` cases) — it is captured into a string, not printed to stdout — but it is still **not a real logger call** (nothing is written to log4j/slf4j, nothing is persisted to a file or centralized log store) and the catch body itself never calls `throw`. Per this series' definition (c) — "neither logs via a real logger call nor rethrows" — it remains a `silent-swallow` finding: whatever a human operator would need to diagnose the failure server-side exists only transiently in the HTTP response the client happened to receive, not anywhere durable. This pattern is used consistently by 15 of this module's ~20 controller classes and is clearly a shared team convention, not 82 independently-written bugs.
- **The DAO/service-layer generic-error pattern (72 findings) and plain empty catches (68 findings) follow the same `HibernateException`-then-`Exception` double-catch template** seen in every prior module: `PreventiveMaintenanceDaoImpl`, `CorrectiveMaintenanceDaoImpl`, `CorrectiveMaintenanceScheduleDaoImpl`, `CorrectiveMaintenanceAssetReplacementDaoImpl`, `CorrectiveMaintenanceWorklistDaoImpl` (partially — see below), and most of the `*ServiceImpl` classes all show the same shape — first clause empty or generic, second (`Exception`) clause usually empty. This concentration is what drives the `maintenance` subpackage's outsized share of findings (47.7% of the module total from ~15% of its files).
- **Multi-catch clauses** (`catch (TypeA | TypeB e)`) — **zero** occurred in this module, same as every prior audit in this series.
- **`status-masks-failure`** (the bare `return null;`-only catch pattern from BR-003/BR-005) — **zero instances** in this module. The only `return null;` statements found (3, via grep) all sit either inside the same dead/commented-out scaffolding blocks counted in the raw-vs-structural gap above, or as a *method-level* fallback **after** an already-classified empty catch block (`CorrectiveMaintenanceScheduleServiceImpl.java:150`) — not as the sole content of a live catch body — so none qualify under this series' strict `status-masks-failure` definition.
- **A small, genuinely positive counter-example exists in this module, worth the owner's awareness:** `CorrectiveMaintenanceWorklistDaoImpl.java` has 4 catch blocks (lines 203, 221, 240, 257) that all properly `throw e;` after an empty catch body — these, plus 1 in `CorrectiveMaintenanceScheduleServiceImpl.java` (line 145, a `catch (CustomException e) { throw new CustomException(...); }` around a stock-allocation validation), account for all 5 non-finding rethrows in the module. Both files otherwise also contain findings elsewhere (`CorrectiveMaintenanceWorklistDaoImpl.java` has other empty/generic catches not shown here that are findings; `CorrectiveMaintenanceScheduleServiceImpl.java` ranks #4 in the top 15) — so "properly rethrows" is applied per-catch-block, not per-file, consistent with every prior audit's parser design.
- **Interface file count required the same non-naive convention as OTIMS.** A strict convention (filename starts with `I`, and the *second* character is uppercase) finds **40** pure-interface files (`IAuctionRequisitionDao.java`, `IPreventiveMaintenanceService.java`, etc.), all with zero catch blocks by construction. A naive `I*.java` glob overcounts to **57** — the extra 17 are ordinary implementation/DTO classes that merely start with the letter `I` followed by a lowercase letter: `ItemForAuctionController.java`, `ItemForAuctionDao.java`, `ItemForAuctionService.java`, `ItemAuctionAccessories.java`, `ItemAuctionDetails.java`, `ItemAuctionResponse.java`, `ItemForAuctionDetailRequest.java`, `ItemForAuctionRequest.java`, `ItemAuctionRequisitionAccessoriesRequest.java`, `ItemAuctionRequisitionApproveRequest.java`, `ItemAuctionRequisitionResponse.java`, `InsuranceDetails.java`, `ItemRequest.java` (×2, different packages), `ItemResponse.java` (×2, different packages), and `IssueBatch.java`.
- **Beyond the 40 interfaces and the 29 files that contain at least one catch block, the remaining 84 files (153 − 40 − 29) are "clean" in the trivial sense of containing zero catch blocks at all** — almost entirely DTO/request/response POJOs (`VendorDetails.java`, `ItemAuctionDetails.java`, etc.), plus the `AppTest.java` scaffold. This is a plain fact about the module's file mix, not a claim that these files handle errors well; they simply have no exception-handling code to evaluate.
- **The parser is structural, not control-flow-aware**, identical caveat to every prior audit in this series: a catch block containing `throw` anywhere in its body is treated as "properly rethrows" and excluded, even if a nested conditional path could still silently fall through without throwing.
- **Scope includes exactly one `src/test/java` file** (`AppTest.java`, noted above and in Scope) — unlike CSSDMaster, Pharmacy, DietAndKitchen, and OTIMS, which all had no `src/test/java` directory at all.
- This audit does **not** re-scan `legacy/Billing`, `legacy/Global`, `legacy/ADT`, `legacy/BloodBank`, `legacy/CSSDMaster`, `legacy/Pharmacy`, `legacy/DietAndKitchen`, `legacy/OTIMS`, `legacy/Entity`, or any other module — it is AssetManagement-only, matching this task's scope. In particular, it does **not** audit `legacy/Global/src/main/java/com/param/assetManagement/maintenance/dto/*` (a different module's DTOs, despite the shared package prefix — see the reverse-import caveat above) or `legacy/Global/src/main/java/com/param/global/pharmacy/dao/WalkInSalesDao.java` (which consumes genuine billing types for its own, out-of-scope methods).
