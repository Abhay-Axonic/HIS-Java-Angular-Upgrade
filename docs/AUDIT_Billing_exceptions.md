# Audit: Silent Exception-Swallow Patterns — legacy/Billing module

**Scope:** every `.java` file under `legacy/Billing` (558 files, 2,411 parsed catch blocks).
**Method:** read-only. Automated structural parse (comment/string-aware brace matching) of every `catch` block, classified by body content, cross-checked by manual sampling. No file under `legacy/` was modified.
**Definition used (per task):** a finding is any catch block that is (a) empty, (b) returns `null`/a generic hardcoded error with no logging of the real cause, or (c) neither logs (via a real logger call) nor rethrows. Catch blocks that call a logger (`log.error(...)`, etc.) or that `throw`/rethrow are excluded as non-findings.

## Summary

- **Total catch blocks parsed:** 2,411
- **Total findings (silent-swallow pattern matches):** 767
- **Non-findings:** 1,613 properly rethrow (`throw`); 31 properly log via a real logger call
- **By severity:** silent-swallow = 752, status-masks-failure = 3, other = 12
- **By path:** billing-critical = 456, peripheral = 311

| Severity | Billing-critical | Peripheral |
|---|---|---|
| status-masks-failure | 3 | 0 |
| silent-swallow | 443 | 309 |
| other | 10 | 2 |

**Only 28 of 558 files (5%) import any real logging library** (`org.apache.log4j.Logger` in 26, `org.slf4j` in 2). The other 530 files have no logger at all, so any non-rethrowing catch in them is structurally silent by construction. This confirms CLAUDE.md's framing of excessive silently-swallowing `try/catch` blocks as the #1 problem, particularly around billing.

## Methodology caveats (read before acting on this list)

- **billing-critical vs peripheral is a path/filename heuristic**, not a data-flow analysis: any file under a `cashDesk/`, `transaction/`, or `ipd/` directory, or whose filename contains a payment/invoice/voucher/discount/charge/consumption/etc. keyword, is marked billing-critical; everything else (master/reference data, DTOs, common utils, patientType/smartcard/unit config) is marked peripheral. Borderline cases should be re-checked by whoever picks up a fix.
- **The parser is structural, not control-flow-aware.** A catch block containing a `throw` anywhere in its body (including inside a nested try/catch that only throws on a different, unrelated failure) is treated as "properly rethrows" and excluded. A small number of the 1,613 excluded blocks may still silently swallow the *original* exception on the path where the nested code does not throw. This was spot-checked on a random sample (6/6 were direct, unconditional rethrows) but not exhaustively verified across all 1,613.
- **`status-masks-failure`** is reserved for catches that `return null;` — the exact BR-003/BR-005 pattern already fixed once in `GlobalExceptionHandler.java` (Spring turns a null return into an empty HTTP 200, i.e. failure looks like success).
- **`silent-swallow`** includes both fully empty catch blocks and the very common pattern `catch (Exception e) { return new Response(ERROR, ERR_500, ERR_500_MESSAGE, null, null); }` — this returns a correctly-flagged error status to the caller, but the real exception (`e`) is never logged or referenced anywhere, so the actual cause is unrecoverable in production. The per-row Notes column says explicitly whether `e` is referenced in the body or discarded outright.
- **`other`** is almost entirely `e.printStackTrace()`-only catches: visible on a console/stdout if anyone is watching it live, but not written to any persistent/centralized log, so effectively silent in a deployed environment.
