# Audit: Silent Exception-Swallow Patterns — legacy/BloodBank module

*Read-only audit, 2026-07-06. Same method as `docs/AUDIT_Billing_exceptions.md`, `docs/AUDIT_Global_exceptions.md`, and `docs/AUDIT_ADT_exceptions.md`; scope here is the BloodBank module (donor registration/screening, blood collection, component separation, cross-match, issue/loan/stock, transfusion tracking).*

**Scope:** every `.java` file under `legacy/BloodBank` (161 files, 818 parsed catch blocks).

**Method:** read-only. Automated structural parse (comment/string-aware brace matching) of every `catch` block, classified by body content, cross-checked by manual sampling (spot-checked findings across every severity category, both exclusion categories — rethrow and printStackTrace/`other` — and the empty-catch/return-null/generic-error sub-cases directly against source; all matched their classification). No file under `legacy/` was modified.

**Definition used (per task, identical to the Billing/Global/ADT audits):** a finding is any catch block that is (a) empty, (b) returns `null`/a generic hardcoded error with no logging of the real cause, or (c) neither logs (via a real logger call) nor rethrows. Catch blocks that call a logger (`logger.error(...)`, etc.) or that `throw`/rethrow are excluded as non-findings.

## Methodology caveats (read before acting on this list)

- **billing-critical vs peripheral is a path/filename/import heuristic**, not a data-flow analysis, identical approach to the Global/ADT audits. A file is marked billing-critical if: (a) it lives under a `com/param/billing/` or `com/param/global/billing/` package (none do — BloodBank has no such package); (b) its path/filename contains a payment/invoice/tariff/discount/deposit/fund/insurance/razorpay/pesapal/charge/voucher/refund/bill/consumption/collection/sanction/mpesa/ccavenue keyword; or (c) it is one of the classes directly imported by `legacy/Billing`. Criterion (c) contributes **zero** files: `legacy/Billing` does not import any `com.param.bloodBank.*` class anywhere (checked via `grep` of every `import com.param.bloodBank` line across all of Billing — no hits). Criterion (a) and (b) also contribute zero after the domain-term correction below — no billing-critical findings exist in this module.
- **The `collection` keyword required a special case, the BloodBank analogue of ADT's `charge`/`discharge` collision.** BloodBank is a blood-donation module, so "collection" appears constantly as the domain term for drawing blood from a donor (`BloodBagCollectionServiceImpl`, `IBloodBagCollectionService`, `BloodBagCollectionDaoImpl`, `IBloodBagCollectionDao`, `BloodBagCollectionController` — 5 files) and has nothing to do with billing/payment collections. A plain substring match on `collection` would have wrongly tagged all 5 as billing-critical. The heuristic here excludes `collection` when it's part of `bloodbagcollection` (case-insensitive) — no other `collection` occurrence exists in this module's paths, so the net effect of the `collection` keyword in BloodBank, after the correction, is zero matches. The `bill` keyword was also checked directly (no BloodBank path contains `bill` as a substring — `bloodbank` itself does not, since the letters split `...ood-bank...`, not `...ood-bill...`). Anyone extending this heuristic to further modules should keep re-checking for this class of collision.
- **One implementation detail is *not* used as a billing-critical signal, to stay consistent with the path/filename/import-only heuristic**: six BloodBank service classes (`BloodBagCollectionServiceImpl`, `BloodBagIssueAcceptanceServiceImpl`, `BloodBagLoanOutServiceImpl`, `BloodComponentOrderMasterServiceImpl`, `DonorRegistrationServiceImpl`, `IssueBloodBagServiceImpl`) implement `com.param.global.common.IBillingCommonConstants`. Inspection shows this interface is a shared cross-module *entity-numbering-sequence* registry (screen IDs and sequence constants like `BLOOD_BAG_NUMBER`, `DONORNUMBER`, `BLOOD_BAG_ISSUE_NUMBER`, alongside unrelated ones like `BILL_NUMBER`, `ENCOUNTER`, `ADMISSION`) — not a billing-calculation dependency, despite its name. Implementing it does not make a class billing-critical under criterion (c), which is scoped to classes *imported by Billing*, not interfaces a BloodBank class happens to implement. Flagged here for transparency since it's the closest thing to a billing link found in this module, but it is not counted.
- **The parser is structural, not control-flow-aware**, identical caveat to the Billing/Global/ADT audits: a catch block containing `throw` anywhere in its body is treated as "properly rethrows" and excluded, even if a nested conditional path could still silently fall through without throwing. Spot-checked directly against source (see Method) — confirmed correct on the samples checked, not exhaustively verified across all 6 excluded blocks in this module.
- **`silent-swallow`** includes fully empty catch blocks, the common pattern of returning a generic/hardcoded error response, and non-persistent console-only signals that aren't `printStackTrace` (e.g. `System.out.println("ERROR : "+he)` in `BloodBagIssueAcceptanceDaoImpl.java:119` and `:168` — a `System.out.println` reference to the exception variable is not treated as logging or as the `printStackTrace`-specific `other` category, so it's classified the same as no-op). The per-row Notes column distinguishes: empty body; a return statement that never references the caught exception variable (the real cause is fully discarded); and a return statement (or no-op) where the exception variable is referenced somewhere in the body but the result is never logged or surfaced.
- **`other`** is exclusively `e.printStackTrace()`-only catches (3 instances, all in `BloodBagIssueAcceptanceDaoImpl.java`): visible on a console/stdout if anyone is watching it live, but not written to any persistent/centralized log, so effectively silent in a deployed environment.
- **`status-masks-failure`** (the `return null;`-only pattern from BR-003/BR-005) has **zero** instances in this module — every generic-error catch in BloodBank returns a `Response<>(ERROR, ...)` object rather than a bare `null`, so the specific null-return failure-masking pattern fixed once in `GlobalExceptionHandler.java` does not recur here. (The underlying problem — the real exception is still discarded either way — is still present, just categorized as `silent-swallow` rather than `status-masks-failure`.)
- **Multi-catch clauses** (`catch (TypeA | TypeB e)`) are recorded once, under the last-listed type in the clause, as a parsing simplification. None occurred in this module (no `|`-joined catch clause was found in BloodBank).
- **Scope includes `src/test/java`** (1 file, `AppTest.java`), unlike the ADT/Billing audits which had no test directories to consider — it is a boilerplate Maven-generated stub with no catch blocks, so it contributes 0 to every count but is included in the `total_files` denominator for an accurate "every `.java` file" scope statement.
- This audit does **not** re-scan `legacy/Billing`, `legacy/Global`, or `legacy/ADT` (already catalogued in their own audit docs) or any other module — it is BloodBank-only, matching this task's scope.
