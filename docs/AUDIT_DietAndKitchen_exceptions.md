# Audit: Silent Exception-Swallow Patterns — legacy/DietAndKitchen module

*Read-only audit, 2026-07-06. Same method as `docs/AUDIT_Billing_exceptions.md`, `docs/AUDIT_Global_exceptions.md`, `docs/AUDIT_ADT_exceptions.md`, `docs/AUDIT_BloodBank_exceptions.md`, `docs/AUDIT_CSSDMaster_exceptions.md`, and `docs/AUDIT_Pharmacy_exceptions.md`; scope here is the DietAndKitchen module (diet/dish/meal/nutrition master data under `com/param/global/master`, and kitchen-side diet ordering/issue/acceptance/planning/rejection workflow under `com/param/kitchen`).*

**Scope:** every `.java` file under `legacy/DietAndKitchen` (124 files, all under `src/main/java` — no `src/test/java` directory exists in this module). 291 `catch` blocks structurally parsed.

**Method:** read-only. Automated structural parse (comment/string-aware brace matching) of every `catch` block, classified by body content, cross-checked by manual sampling (spot-checked empty-catch findings, the "references-variable" vs "does-not-reference-variable" split, the single `other`/printStackTrace finding, all "properly rethrows" exclusions, and the billing-critical heuristic in both directions — all matched their classification). The parser itself was first validated against a raw `catch\s*(` grep count (321 raw occurrences vs. 291 structurally valid — the 30-occurrence gap was manually confirmed to be entirely commented-out/dead code: whole methods fenced in `/* ... */` blocks, most concentrated in `DietPlanningDaoImpl.java` (4 commented-out methods, 8 dead catches) and `DietPlanningController.java`/`DietTemplateMapperController.java`/`DietTemplateMapperServiceImpl.java` (similar dead-method fencing) — same pattern as the `BillSalesReturnController.java`/`ItemService.java` dead-code gap noted in the Pharmacy audit). No file under `legacy/` was modified.

**Definition used (per task, identical to every prior audit in this series):** a finding is any catch block that is (a) empty, (b) returns `null`/a generic hardcoded error with no logging of the real cause, or (c) neither logs (via a real logger call) nor rethrows. Catch blocks that call a logger (`logger.error(...)`, etc.) or that `throw`/rethrow are excluded as non-findings.

## Methodology caveats (read before acting on this list)

- **Billing-critical heuristic returned zero hits, checked from every angle used in prior audits.** (a) package check: no file lives under `com/param/billing/` or `com/param/global/billing/` — all 124 files are under `com/param/global/master` or `com/param/kitchen`. (b) path/filename keyword check (`payment|invoice|tariff|discount|deposit|fund|insurance|razorpay|pesapal|charge|voucher|refund|bill|consumption|collection|sanction|mpesa|ccavenue`): **zero filename matches** — this is itself notable, since every other clinical module (ADT, BloodBank, CSSDMaster) still had at least a few filename hits even where they were later excluded as false positives (discharge/collection collisions); DietAndKitchen has none at all. (c) reverse-import check, whether `legacy/Billing` or `legacy/Global` imports anything from `com.param.kitchen.*` or the diet-specific classes under `com.param.global.master.*` — zero hits. (d) forward-import check (the extension added for Pharmacy), whether any DietAndKitchen file imports `com.param.billing.*` or `com.param.global.billing.*` directly — zero hits. All four criteria came back empty; this module's own package (`com.param.global.master`) is confusingly similar in name to other modules' `master` packages but is not itself billing.
- **The task's own hint — "diet 'charges'/'orders' could plausibly overlap with billing vocabulary" — was checked explicitly and did not pan out.** No file or identifier in this module contains the substring `charge` (checked case-insensitively across all 124 files, including inside method/field bodies, not just filenames — zero matches, so there was no need for the `discharge`-style exclusion regex ADT/Pharmacy required). `order`/`Order` is common (`DietOrder`, `DietOrderController`, `DietOrderDaoImpl`, `DietOrderServiceImpl`, etc.) but every instance refers to a *meal order* (which dish/quantity/meal-timing a patient receives from the kitchen) — a clinical/operational workflow object, not a purchase order, work order, or billable line item. Content-level grep for other billing-adjacent words (`invoice`, `payment`, `tariff`, `discount`, `refund`, `cost`) surfaced only one hit worth flagging: `PatientDetailsDto.java` carries a `paymentEntitlementId`/`paymentEntitlementDesc` pair of fields — but these describe the patient's insurance/entitlement *category* (used to decide which diet template or ward applies), not a calculated amount, and the DTO has no catch-block findings in this module (it's a pure data holder with no methods beyond getters/setters). This is a judgment call flagged for the owner's awareness, consistent with the conservative, heuristic-not-data-flow-analysis approach used throughout this series, but it did not change the classification — no findings in this file, so nothing to reclassify regardless.
- **This is a small, self-contained module** (124 files vs. Pharmacy's 758, Global's 2669) with no dependents found in either direction — no other module imports from it, and it imports nothing from Billing/Global's billing packages. This is consistent with Diet & Kitchen being an operationally-adjacent-but-financially-isolated subsystem (what a patient eats, not what a patient is charged).
- **The 30-occurrence gap between raw `catch(` grep (321) and structurally valid catches (291) is entirely dead/commented-out code**, concentrated in a handful of files where whole methods were fenced out with `/* ... */` block comments during some earlier refactor and left in place: `DietPlanningDaoImpl.java` (4 fully-commented methods — `getAllDietPlanning`, `getDietPlanningByPatientId`, `updateDietPlanning`, `deleteDietPlanning` — 8 dead catches total, spanning roughly lines 182–382), plus smaller instances in `DietPlanningController.java`, `DietTemplateMapperController.java`, `DietTemplateMapperDaoImpl.java`, `DietTemplateMapperServiceImpl.java`, and `DietTypeMasterController.java`. Each was manually opened and confirmed to be genuinely comment-fenced (not a parser miscount) before being excluded.
- **The parser is structural, not control-flow-aware**, identical caveat to every prior audit in this series: a catch block containing `throw` anywhere in its body is treated as "properly rethrows" and excluded, even if a nested conditional path could still silently fall through without throwing.
- **`printStackTrace`-only classification required the same care as the Pharmacy audit.** This module has exactly one `printStackTrace()` call in any catch block (`DishMasterDaoImpl.java:363`), and its catch body is *only* `e.printStackTrace();` — no substantive return inside the catch itself (the method's fallback `return new Response(ERROR, ...)` sits after the try/catch, per the same "catch body only" scoping rule used in every prior audit). Classified `other`, not `silent-swallow`, since nothing beyond the console print happens inside the catch clause.
- **The DAO layer's `HibernateException`-then-`Exception` double-catch pattern is nearly universal** in this module: almost every DAO method (`DietTypeMasterDaoImpl`, `DietUnitMasterDaoImpl`, `MealMasterDaoImpl`, `NutritionalMasterDaoImpl`, `KeyIngredientsMasterDaoImpl`, `DishMasterDaoImpl`, `DietAcceptanceDaoImpl`, `DietIssueDaoImpl`, `DietOrderDaoImpl`, `DietPlanningDaoImpl`, `RejectedDietListDaoImpl`, `WeekDayMasterDaoImpl`, `DietTemplateMapperDaoImpl`, `DietTimingMasterDaoImpl`) follows the shape `catch (HibernateException he) { return new Response(ERROR, ...); } catch (Exception e) { }` — the first clause returns a generic error referencing neither `he` nor a status code beyond a hardcoded `ERROR` constant, and the second clause is empty. Both halves are findings; this two-clause pair repeats so consistently that it likely reflects a single copy-pasted DAO template used across the whole module, rather than 12+ independently-written bugs.
- **Multi-catch clauses** (`catch (TypeA | TypeB e)`) — **zero** occurred in this module, same as every prior audit in this series.
- **`status-masks-failure`** (the `return null;`-only pattern from BR-003/BR-005) — **zero instances** in this module. Every non-empty finding returns a `Response`/`ResponseEntity`-style object with a hardcoded `ERROR` status, not a bare `null`.
- **Scope has no `src/test/java` directory** — same as CSSDMaster and Pharmacy; all 124 files are `src/main/java`.
- This audit does **not** re-scan `legacy/Billing`, `legacy/Global`, `legacy/ADT`, `legacy/BloodBank`, `legacy/CSSDMaster`, or `legacy/Pharmacy` (already catalogued in their own audit docs) or any other module — it is DietAndKitchen-only, matching this task's scope.
