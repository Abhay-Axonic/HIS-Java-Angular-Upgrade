# Audit: Silent Exception-Swallow Patterns — legacy/Entity module

*Read-only audit, 2026-07-06. Same method as `docs/AUDIT_Billing_exceptions.md`, `docs/AUDIT_Global_exceptions.md`, `docs/AUDIT_ADT_exceptions.md`, `docs/AUDIT_BloodBank_exceptions.md`, `docs/AUDIT_CSSDMaster_exceptions.md`, `docs/AUDIT_Pharmacy_exceptions.md`, `docs/AUDIT_DietAndKitchen_exceptions.md`, and `docs/AUDIT_OTIMS_exceptions.md`; scope here is the Entity module, which is **not a workflow module** like the other eight — it is the shared JPA/Hibernate entity, DTO, and mapper host that `com/param/otims/model`, `com/param/bloodBank/model`, `com/param/opd/model`, `com/param/adt/**/model`, and dozens of other packages physically live in, referenced by name in nearly every one of the eight prior audits' "this audit does not scan legacy/Entity" scope notes. It is also, by a wide margin, **the largest module in this series by file count** (1,422 files, vs. Pharmacy's 758 and Global's 2,669-file internal breadth previously noted as the next-largest single scans).*

**Scope:** every `.java` file under `legacy/Entity` (1,422 files, all under `src/main/java` — no `src/test/java` directory exists in this module). 57 `catch` blocks structurally parsed (from a raw grep count of 64 — see Method).

**Method:** read-only. A raw `grep -rc 'catch\s*('` sanity pass across all 1,422 files found only 64 total `catch` occurrences, concentrated in just 12 files — confirming, before any deeper parsing, the task brief's expectation that this entity-heavy module would have a dramatically lower catch-to-file ratio than any workflow module in this series. Because the catch-bearing file set was small enough to review exhaustively (not merely sample), every one of the 12 files was read in full and independently hand-classified, then cross-checked against a purpose-built Python structural parser (comment/string-aware brace matching, written for this audit) that re-derived the same 12 files' catch inventory from scratch. The two methods agreed on every catch block, including the trickier edge cases: a `printStackTrace()`-then-`throw` combination in `ServiceIdentityDaoImpl.java` (excluded as a proper rethrow despite the console print), several comment-only catch bodies in `GlobalCommonDateUtils.java` (e.g. `// TODO Auto-generated catch block`, a commented-out debug `System.out.println`) correctly treated as empty, and a `catch (Pdfcrowd.Error why)` in `GenaratePDFFromHtml.java` that returns `why.getMessage()` in an HTTP response body without ever logging it. The parser was itself validated against the raw grep count: 64 raw vs. 57 structurally valid, a 7-occurrence gap that was manually confirmed to be entirely dead/commented-out code — six `/* ... */`-fenced abandoned/duplicate methods inside `GlobalCommonDateUtils.java` (an old `setKey` override attempt, a full `getMD5EncryptedValue` method, an unused 3-argument `getDate` overload, an unused `getFirstDateOfMonth(int, SessionObject)` overload, a commented-out `getTodaysDate(SessionObject)`, and a duplicate `getDateByzone(String, String)` overload), together holding 7 dead catches — the same scaffolding/dead-code pattern every prior audit in this series has found, just concentrated in one file here instead of scattered across several controllers. No file under `legacy/` was modified.

**Definition used (per task, identical to every prior audit in this series):** a finding is any catch block that is (a) empty, (b) returns `null`/a generic hardcoded error with no logging of the real cause, or (c) neither logs (via a real logger call) nor rethrows. Catch blocks that call a logger (`logger.error(...)`, etc.) or that `throw`/rethrow are excluded as non-findings.

## Methodology caveats (read before acting on this list)

- **The billing-named package/subtree check the task asked for first was performed, and it is the headline non-finding of this audit.** `legacy/Entity/src/main/java/com/param/billing/**` genuinely exists — 191 files across three sub-packages (`billing/global/model` = 78 files, `billing/global/transaction/model` = 103 files, `billing/packages/model` = 10 files), covering everything from `BillingMaster`, `TariffMaster`, `PaymentReceiptDetails`, `CreditNoteMaster`, `FundSanctionRequestDetails`, `DoctorReferralShareMaster` to `CorporateContractMaster`. This satisfies billing-critical criterion **(a)** — package check — for all 191 files. But every one was spot-checked (e.g. `BillingMaster.java`, 879 lines, 97 `public` members, all JPA annotations/getters/setters/named-queries, zero `catch`) and confirmed to be a pure `@Entity` row-mapping class with no business-logic methods; `grep -rc 'catch\s*('` over the entire 191-file subtree returns **0**. Criterion (a) is real and correctly satisfied, but contributes **zero findings**, because these files have no exception-handling surface at all — exactly the entity-module composition the task brief predicted.
- **Filename/path keyword check (b)** (`payment|invoice|tariff|discount|deposit|fund|insurance|razorpay|pesapal|charge|voucher|refund|bill|consumption|collection|sanction|mpesa|ccavenue`, with the `(?<!dis)charge` exclusion applied): outside the `com/param/billing/**` subtree already covered by (a), **67 additional files** module-wide match one of these keywords by filename or path. 14 of those are `discharge`-path collisions (the entire `com/param/adt/discharge/model/**` directory, plus `DischargeTypeMaster.java`) — excluded as false positives, same exclusion every prior clinical-module audit needed. A `collection` check on the remainder found `BloodBagCollection.java`, `BloodBagCollectionExaminationDetails.java`, and `PhlebotomistHomeCollection.java` — specimen/blood *collection*, not payment collection; also excluded as unrelated-meaning false positives, per the task's own instruction to check this. Of the remaining ~53 genuine billing-adjacent-by-name files (`OtherCharge.java`, `PaymentEntitlement.java`, `DiscountType.java`, `Mpesa.java`, `MpesaMaster.java`, `CCAvenueLog.java`, `TInsurance.java`, `BillableConsumption.java`, etc.), **every single one except `MpesaUtility.java` is a pure entity/DTO class with zero catch blocks.** `MpesaUtility.java` is the one exception — it is a real utility class (an M-Pesa SOAP client for mobile-money payment retrieval) with one catch block, and it is billing-critical purely via this filename criterion. Note, though: a repo-wide `grep` for any caller of `MpesaUtility` (its class name or its one public method, `callSoapWebService`) found **zero** — this file is dead/unused code, not wired into any live payment flow, which the owner should be aware of even though it is still counted as a finding per the mechanical definition used throughout this series (same treatment prior audits gave to leftover scratch controllers).
- **Reverse-import check (c) required more care in this module than in any prior audit, and is the most consequential judgment call here.** In every prior module, criterion (c) asked whether `legacy/Billing`/`legacy/Global` import *from the audited module* — a meaningful yes/no, since those audited modules are themselves consumers of other things, not shared dependency hosts. Entity inverts that relationship: it *is* the shared dependency host nearly every other module (including Billing and Global) imports from, so a literal "does anything in Billing or Global import anything from Entity" check would trivially return yes for almost the entire 1,422-file module and be uninformative. To make the criterion meaningful, this audit checked exact reverse-import counts **per catch-bearing file**, split by consuming module:
  - `com.param.utility.TimeZoneComponent` — imported directly by **90 files in `legacy/Billing`** and **232 files in `legacy/Global`**, including core billing computation classes doing real amount/date work at billing time: `ContractGradeMasterDaoImpl`, `FundInFlowMasterDaoImpl`, `MPeriodicityServiceConfigDaoImpl`/`ServiceImpl`, `EHCpackageDaoImpl`/`ServiceImpl`/`Controller`, `FundSanctionRequestController`, `OTCompletionCssdKitDaoImpl`, `OtCompletionMedicalGasDaoImpl`. **Marked billing-critical.**
  - `com.param.global.common.GlobalCommonDateUtils` — imported directly by **78 files in `legacy/Billing`** and **331 files in `legacy/Global`**, the same billing-DAO set as above; it also independently carries its own monetary-rounding helpers (`getAmount(Double)` / `getAmountCap(Double)`, both `Math.abs`/`DecimalFormat`-based) used for amount formatting app-wide, though neither of those two specific methods has a `try`/`catch` of its own. **Marked billing-critical.**
  - `com.param.global.common.DateConverter` — exactly **1** reverse-import hit, and it is from `legacy/Global/src/main/java/com/param/opd/coversheet/service/CoversheetTemaplateServiceImpl.java` (OPD coversheet template rendering — an unrelated clinical-documentation domain, not billing). **Not marked billing-critical** — a single incidental import from one unrelated-domain Global file does not, in this audit's judgment, establish a genuine billing dependency, unlike the two files above where the *majority* of consumers are billing DAOs/services themselves. This is a deliberate judgment call, flagged here exactly as the OTIMS audit flagged its `Deposite`-keyword call, for the owner to override if they disagree.
  - `com.param.global.common.GenaratePDFFromHtml` — same situation: exactly **1** reverse-import hit, from `legacy/Global/src/main/java/com/param/global/unit/service/SmsUtilityConfigServiceImpl.java` (SMS utility configuration — also unrelated to billing). **Not marked billing-critical**, same reasoning as `DateConverter.java`.
  - `com.param.global.common.RequestJsonCheck` — a loose text search found the class name inside `legacy/Global/src/main/java/com/param/global/controller/OrderMasterController.java`, but on inspection all four occurrences are inside `//`-commented-out dead code (`//RequestJsonCheck.mapJsonToObject(...)`) — a false positive from the loose search, correctly excluded; the precise `import` statement grep returns 0.
  - The remaining 6 catch-bearing files (`TimeZoneServiceImpl`, `TimeZoneDaoImpl`, `ServiceIdentityDaoImpl`, both `LocalTimeConverter` classes, `LocalTimeStampConvertor`) have **zero** reverse-import hits from either `legacy/Billing` or `legacy/Global`.
- **Forward-import check (d)** — none of the 12 catch-bearing files import `com.param.billing.*` or `com.param.global.billing.*` directly. This is the expected/structurally-inverted result for this module: Entity is consumed *by* Billing, not a consumer *of* Billing, so criterion (d) — which found OTIMS's 2 billing-critical files in that audit — naturally contributes nothing here.
- **Net billing-critical file set: 3 files** — `GlobalCommonDateUtils.java` and `TimeZoneComponent.java` (via criterion (c), reverse-import from real billing DAOs) and `MpesaUtility.java` (via criterion (b), filename). Per this series' established file-level propagation convention, every finding in each of these 3 files is marked billing-critical, not just the specific lines that touch billing logic directly (none of the 40 `GlobalCommonDateUtils`/`TimeZoneComponent` findings are in a billing-specific method — they are generic date/timezone parsing helpers used by billing DAOs alongside every other module).
- **The `status-masks-failure` pattern (bare `return null;` and nothing else) appears 5 times in this module** — the first time in this series it has been anything other than zero (OTIMS, DietAndKitchen, and every module before them reported zero): `TimeZoneServiceImpl.java` (lines 21, 31), `TimeZoneDaoImpl.java` (lines 23, 36), and `GlobalCommonDateUtils.java` (line 168, inside `generatePassword(String, String, Date)`). All five are the exact `catch (Exception e) { return null; }` shape, no hardcoded message, no other statement.
- **The `other` category (2 findings) is the standard `printStackTrace()`-only pattern**, both in `TimeZoneComponent.java` (lines 219, 231) — console-only, no logger, no rethrow, no return-value handling beyond the method's normal `return null;` fallback outside the catch.
- **A related but distinct sub-pattern, not seen with this exact shape in any prior audit, appears once: `MpesaUtility.java` line 45 prints a fully hardcoded, generic message to `System.err` (`"\nError occurred while sending SOAP Request to Server!..."`) without ever referencing the caught exception variable at all** — not even `e.toString()` or a stack trace. This is classified `silent-swallow`, not `other`, because unlike the `printStackTrace()`/`System.out.println(e)` cases (which at least surface something derived from the real exception object), this catch discards the exception variable entirely and prints text that would be identical regardless of what actually failed — matching this series' `silent-swallow` definition (b) more closely than the `other` bucket, which is reserved for patterns that reference the exception object itself.
- **`GenaratePDFFromHtml.java` line 35 is this module's one instance of the "exception message surfaced to the caller via the response payload, but never logged server-side" sub-pattern** first documented in the OTIMS audit: `catch (Pdfcrowd.Error why) { ...String msg = String.format("Pdfcrowd Error: %d - %s", why.getCode(), why.getMessage()); return new ResponseEntity<>(msg.getBytes(), headers, HttpStatus.BAD_REQUEST); }`. Classified `silent-swallow`, consistent with how OTIMS classified the same shape.
- **Multi-catch clauses** (`catch (TypeA | TypeB e)`) — **zero** occurred in this module, same as every prior audit in this series.
- **The 7-occurrence raw-vs-structural gap is entirely dead/commented-out code, all inside one file** (`GlobalCommonDateUtils.java`) — see Method above for the full list of six `/* ... */`-fenced dead methods. Each was manually opened and confirmed to be genuinely comment-fenced, not a parser miscount, before being excluded.
- **The parser is structural, not control-flow-aware**, identical caveat to every prior audit in this series: a catch block containing `throw` anywhere in its body is treated as "properly rethrows" and excluded, even if a nested conditional path could still silently fall through without throwing. (This module's one rethrow, `ServiceIdentityDaoImpl.java:77`, is unconditional, so the caveat doesn't change its classification here — noted for completeness.)
- **Interface-file counting required more care here than the "second character uppercase" convention OTIMS established, because this module has naming collisions the convention doesn't anticipate.** A naive `I*.java` glob matches 76 files. Restricting to the OTIMS convention (second character uppercase) narrows that to 13 candidates — but of those 13, **six are not interfaces at all**: `ICPCCodesConfigurationMapper.java`, `ICPCGenderMapper.java`, `ICPCCodeConfiguration.java`, `ICPCTemplateMapping.java`, and `ICPCMapper.java` are `public class` entity/mapper classes for ICPC (International Classification of Primary Care, a real clinical coding standard — the "I" is part of the domain acronym, not an interface prefix), and `ICUTypeMaster.java` is likewise a `public class` (ICU = Intensive Care Unit). Conversely, the naming convention **under-counts** by missing `DepositTypes.java` (`public interface DepositTypes { ... REGULAR_DEPOSIT ... ENCOUNTER_DEPOSIT ... }`), a genuine interface that doesn't start with `I` at all. Because the naming heuristic both over- and under-counts in this module, this audit instead grepped every file module-wide for a literal `public interface`/`public @interface` declaration: **8 real interfaces exist** — `ITimeZoneService.java`, `ITimeZoneDao.java`, `IError.java`, `IEncounterTypeMasterConstant.java`, `IBillingStatusMasterConstant.java`, `IServiceIdentityDao.java`, `ICommonConstants.java`, and `DepositTypes.java`. All 8 have zero catch blocks by construction (interfaces cannot contain method bodies with `try`/`catch` in this codebase's pre-Java-8-default-methods style).
- **Pure entity/model/DTO/mapper files (zero catch blocks, non-interface): 1,402 of 1,422 files (98.6%)** — this is `1,422 total − 12 files with ≥1 catch − 8 interfaces`. This is the number that explains the module's finding-to-file ratio: unlike every prior audit in this series, where the audited module's own controller/DAO/service layers were the thing being scanned, here the overwhelming majority of files are JPA `@Entity`/DTO/mapper classes for other modules' domains (OTIMS, BloodBank, OPD, ADT, CSSDMaster, radiology, ER, QMS, blood bank, doctor, asset management, and Billing's own 191-file entity subtree) with no methods containing exception handling at all.
- **Scope has no `src/test/java` directory** — same as every prior module in this series; all 1,422 files are `src/main/java`.
- This audit does **not** re-scan `legacy/Billing`, `legacy/Global`, `legacy/ADT`, `legacy/BloodBank`, `legacy/CSSDMaster`, `legacy/Pharmacy`, `legacy/DietAndKitchen`, `legacy/OTIMS`, or any other module — it is Entity-only, matching this task's scope. In particular, the extensive reverse-import counts cited above (e.g. "331 files in legacy/Global import GlobalCommonDateUtils") describe *those other modules'* dependency on this one; they are not themselves re-audited findings and do not appear in `docs/AUDIT_Global_exceptions.md` or `docs/AUDIT_Billing_exceptions.md` unless those audits independently found catch-level issues in their own files.
