# Audit: Silent Exception-Swallow Patterns — legacy/HIS-WAR module

*Read-only audit, 2026-07-06. Same method as `docs/AUDIT_Billing_exceptions.md`, `docs/AUDIT_Global_exceptions.md`, `docs/AUDIT_ADT_exceptions.md`, `docs/AUDIT_BloodBank_exceptions.md`, `docs/AUDIT_CSSDMaster_exceptions.md`, `docs/AUDIT_Pharmacy_exceptions.md`, `docs/AUDIT_DietAndKitchen_exceptions.md`, and `docs/AUDIT_OTIMS_exceptions.md`; scope here is the HIS-WAR module — the top-level Spring Boot WAR shell of the application: scheduled/manual batch jobs for midnight billing posting, room-rent charge posting, doctor-share and Tally accounting integration (`com/param/batchjobs`), the HL7 inbound/outbound messaging subsystem (`com/param/hl7`), the app's one and only centralized exception-handling package (`com/param/exception`), plus JWT/CORS/rate-limit filters, JDBC/session bootstrap, and Spring config (`com/param/comman`, `com/param/config`, `com/param/filter`, `com/param/jdbc`).*

**Scope:** every `.java` file under `legacy/HIS-WAR` (54 files, all under `src/main/java` — no `src/test/java` directory exists in this module). 172 raw `catch(` occurrences found by grep; 142 structurally live catch blocks parsed after excluding 30 dead/commented-out catches (see Method).

**Method:** read-only. Automated structural parse (comment/string-aware brace matching, split across three parallel research passes covering the batch-jobs package, the HL7 package, and the remaining misc/filter/exception-package files) of every `catch` block, classified by body content, cross-checked by manual sampling — every file in `com/param/batchjobs/scheduler` and `com/param/batchjobs/service` was independently re-read and line-verified by hand (not just taken from the automated pass), along with `ExceptionDao.java`, `JwtTokenFilter.java`'s two catches, and the `Hl7MessageService.java` line-58 multi-catch — all matched their classification. The parser was validated against a raw `catch\s*(` grep count (172 raw vs. 142 structurally valid — the 30-occurrence gap was manually confirmed to be entirely commented-out/dead code, overwhelmingly concentrated in one file: `RoomRentChargesBatch.java` alone accounts for 23 of the 30 dead catches, via two entire `/* ... */`-fenced legacy scheduled-job methods, `midnightBatch()` (lines 113–221, 17 dead catches) and an alternate `postRoomRent()` (lines 224–266 within the same comment block, 4 dead catches), plus a separate dead `claimSendToSmartSystem()` alternate implementation (lines 281–417, 1 dead catch) and a dead `syncSchedulingLogs()` (lines 601–609, 1 dead catch). This looks like an abandoned first draft of the exact same batch-job chain that was later reimplemented live in `MidNightBatchWithTimeZone.java` and `RevertAllocatedQuantity.java` (identical method names — `midnightBatch`, `postRoomRent` — and identical Tally/room-rent call sequence), left in place rather than deleted. The remaining 7-catch gap is `Hl7MessageService.java` (5 dead catches: one `/* */`-fenced `catch (IOException e) {}` plus four individual `//`-commented catch lines scattered through the file) and one dead catch each in `LoadTimeZone.java` (an entire `onApplicationEvent` method fenced out) and `HISBean.java` (an entire `@Scheduled processEvent()` method fenced out). No file under `legacy/` was modified.

**Definition used (per task, identical to every prior audit in this series):** a finding is any catch block that is (a) empty, (b) returns `null`/a generic hardcoded error with no logging of the real cause, or (c) neither logs (via a real logger call) nor rethrows. Catch blocks that call a logger (`logger.error(...)`, etc.) or that `throw`/rethrow are excluded as non-findings.

**1 of 54 files imports a real logging library** (`org.slf4j.Logger`, in `GlobalExceptionHandler.java` only) — a higher *proportion* (1.9%) than Pharmacy (6/758, 0.8%), though a far smaller absolute count, and still well below Billing (28/558, 5%). Every other prior module (OTIMS 0/92, DietAndKitchen 0/124, ADT 0/589, BloodBank 0/161, CSSDMaster 0/128) had zero. HIS-WAR is only the third module in this series (after Billing and Pharmacy) to show any real logger usage at all, and it is the first module where the logger that exists is actually invoked correctly on every catch that has access to it (both of `GlobalExceptionHandler`'s two catches call `logger.error(...)` with the real exception).

**61 billing-critical findings (71.8% of all findings), concentrated in 6 of the module's 54 files**, plus 2 additional billing-critical files with zero findings (see caveats): `MidNightBatchWithTimeZone.java` (39 findings — by far the largest single file in the audit series' history), `Hl7MessageService.java` (11), `RoomRentChargesBatch.java` (3), `ExecuteBatchForcefully.java` (4), `TDoctorShareImpl.java` (2), and `Hl7MessageDaoImpl.java` (2). All were caught via the forward-import criterion (direct `import com.param.billing.*` / `com.param.global.billing.*`), two also via the filename/path keyword criterion (`RoomRentChargesBatch.java` matches `charge`). This is the largest and most severe billing-critical finding set of the whole series so far — unlike OTIMS (23 findings in 2 files) or Pharmacy, HIS-WAR's batch-job layer is the actual orchestrator that posts room-rent charges, doctor-share splits, and Tally general-ledger entries every night, and its failure-handling is uniformly silent.

**The `com/param/exception` package is genuinely wired Spring machinery, not dead scaffolding — but it is functionally near-moot given the rest of the module's behavior, and its own backstop is broken by the same defect it exists to catch.** `GlobalExceptionHandler.java` is a real `@ControllerAdvice` with `@ExceptionHandler` methods that Spring MVC's `ExceptionHandlerExceptionResolver` invokes automatically for any exception that escapes a `@Controller`/`@RestController` method uncaught — this is correctly registered, non-dead infrastructure, and its own two catches are the only ones in the entire module that log via a real logger and are therefore excluded as non-findings. However: (1) no other catch block anywhere in the module's other 171 raw catches was found (via grep) to explicitly construct or delegate to `GlobalExceptionHandler`, `ExceptionDao`, `BackLogService`, or `ErrorLog` — local catches simply swallow everything before an exception could ever reach a controller boundary; (2) exceptions thrown inside servlet `Filter`s (e.g. `JwtTokenFilter`) architecturally cannot reach a `@ControllerAdvice` at all, since filters run before Spring MVC's dispatch/exception-resolution machinery even engages; and (3) the handler's own backstop persistence path — `GlobalExceptionHandler` → `BackLogService.createErrorLog` (its real "post to Backlog.com" ticket-creation call is itself commented out, leaving only a DB insert) → `ExceptionDao.addErrorLog`, which does perform a genuine `INSERT INTO public.exception_log(...)` — has its own empty `catch(Exception e){}` (line 48), so if the INSERT itself fails, that failure is silently swallowed with no record anywhere. A second, separate `exception_log`-writing method exists in `BatchDaoImpl.addExceptionLog()` (used only by the batch-job error-collection pattern described below) with the identical empty-catch defect. Genuinely centralizing exception handling per the mission's #1 priority will require (a) routing local catches to rethrow instead of swallow so exceptions actually reach `GlobalExceptionHandler`, and (b) fixing both `ExceptionDao`'s and `BatchDaoImpl`'s own catches so the persistence backstop is reliable.

## Methodology caveats (read before acting on this list)

- **Billing-critical determination, walked through criterion by criterion.** (a) package check — no file lives under `com/param/billing/` or `com/param/global/billing/`; all 54 files are under `com/param/batchjobs`, `com/param/comman`, `com/param/config`, `com/param/exception`, `com/param/filter`, `com/param/hl7`, or `com/param/jdbc`. **Zero hits.** (b) filename/path keyword check (`payment|invoice|tariff|discount|deposit|fund|insurance|razorpay|pesapal|charge|voucher|refund|bill|consumption|collection|sanction|mpesa|ccavenue`, with the `(?<!dis)charge` discharge-exclusion) — **3 filename hits**: `RoomRentChargesBatch.java`, `RoomRentBatchChargesServiceImpl.java`, and the interface `IRoomRentBatchChargesService.java` (the latter has zero catch blocks by construction). (c) reverse-import check — whether `legacy/Billing` or `legacy/Global` (or any of the other 7 already-audited modules) imports anything from any HIS-WAR package — **zero hits**; in fact zero other modules in the whole repo import from any HIS-WAR package at all, confirming HIS-WAR is a top-level leaf/shell module that depends on everything else, not the reverse. (d) forward-import check — whether any HIS-WAR file imports `com.param.billing.*` or `com.param.global.billing.*` directly, or directly references a billing DTO/service type inline — **9 files hit**: `RoomRentChargesBatch.java` (12 `com.param.billing.global.smartcard.dto.*` imports, `IBillingMasterDao`, `PaymentRecieptMasterDto`), `MidNightBatchWithTimeZone.java` (`IBillingMasterDao`, `ITDoctorShareService`), `RoomRentBatchChargesServiceImpl.java` (`IAutoPostingConfigDao`, `AutoPostingServicesConfigDto`), `TDoctorShareImpl.java` (`IBillingDetailsDao`, `IBillingMasterDao`, `IDoctorReferralShareDao`, `IDoctorShareDao`, plus several billing DTOs), `Hl7MessageDaoImpl.java` and `Hl7MessageService.java` (both import `com.param.global.billing.controller.BillingException`; `Hl7MessageService.java` also imports `com.param.billing.global.dto.EncounterPaymentDto`), and `ExecuteBatchForcefully.java`/`LoadTimeZone.java` (both import `com.param.billing.common.Response` — see the dedicated judgment-call note below). **Per this series' established file-level propagation convention** (see the OTIMS audit's `OTReservationDaoImpl.java` footnote), billing-critical status applies to every finding in a qualifying file, not just the specific catch that touches billing logic — this is why, e.g., all 39 `MidNightBatchWithTimeZone.java` findings are billing-critical even though several (SMS reminders, CSSD sterilization stock, ICU utilization) are not themselves monetary.
- **`com.param.billing.common.Response` is a judgment call, flagged but not reclassified.** `ExecuteBatchForcefully.java` and `LoadTimeZone.java` both import `com.param.billing.common.Response` instead of the near-identical `com.param.global.common.Response` wrapper class used by every other file in this module (`BatchDaoImpl`, `RevertAllocatedQuantity`, `MidNightBatchWithTimeZone`, etc.) — this looks like it could be a copy-paste/package-naming artifact (two nearly-duplicate generic REST-response wrapper classes, one incidentally sitting inside the `com.param.billing` package tree) rather than deliberate billing coupling. It does not change either file's classification: `ExecuteBatchForcefully.java` is independently billing-critical because its four endpoints directly invoke `doctorShare.getDoctorShareService()` (calls into `TDoctorShareImpl`, itself billing-critical) and `roomRentBatchChargesServ.template()` (calls into the room-rent batch chain); `LoadTimeZone.java` is independently billing-critical because it also imports `com.param.billing.global.transaction.dto.TDoctorShareRespDto` directly — though as noted below, `LoadTimeZone.java`'s only catch is dead code, so it contributes zero findings either way.
- **Two files are billing-critical by import but contribute zero findings to the table, because their catches are clean.** `RoomRentBatchChargesServiceImpl.java` (2 catches, both `throw e;`) and `LoadTimeZone.java` (1 catch, but it sits entirely inside a commented-out `onApplicationEvent` method — see the dead-code gap above, so it's not live at all). These are worth the owner's awareness as billing-critical files that are *not* part of the problem, unlike the six billing-critical files that are.
- **A judgment call was made NOT to extend billing-critical status to files that only call into billing-adjacent code transitively (through another class), consistent with the OTIMS audit's treatment of `OTReservationServiceImpl`/`OTReservationController`.** `BatchDaoImpl.java` and `RevertAllocatedQuantity.java` both sit immediately upstream/downstream of the billing-critical batch chain — `RevertAllocatedQuantity.java`'s `midNightBatch()`, `roomRentMidNightBatch()`, `ForceFullyMidNightBatch()`, and `doctorShare()` methods are the `@Scheduled`/manual triggers that *call* `MidNightBatchWithTimeZone.midnightBatch/postRoomRent/doctorShare` (billing-critical), and `BatchDaoImpl.java` backs the `m_batch_log_room_rent` dedup/tracking table used by that same chain — but neither file itself imports `com.param.billing.*`/`com.param.global.billing.*` or references a billing DTO/service type inline. Both are kept **peripheral**, matching this series' convention that delegation alone (calling a method on a class that happens to be billing-critical) does not independently qualify a file — only a file's own direct import/reference does.
- **`JwtTokenFilter.java` presents a similar judgment call in a different form: URL string literals, not imports.** Twelve occurrences of `requestUrl.contains("/api/billing/...")` (e.g. `/api/billing/bill/service/cancel`, `/api/billing/kiosk/saveAndPay`) gate which request paths this JWT/domain-validation filter treats specially — a genuine, deliberate reference to billing API routes for security purposes — but the file never imports a billing package or type, so it does not meet criterion (d) as literally defined (import or direct DTO/service reference). Kept **peripheral**, flagged for the owner's awareness since this file's two findings (lines 628, 631) mean that JWT/CORS validation failures on billing-adjacent endpoints are also silently converted to a generic 401/502 with no server-side record.
- **The `charge` keyword required the same discharge-collision exclusion ADT, Pharmacy, and OTIMS needed.** Genuine `charge` hits (post-exclusion) are confined to the already-billing-critical `RoomRentChargesBatch.java`/`RoomRentBatchChargesServiceImpl.java`/`IRoomRentBatchChargesService.java` trio, plus `MidNightBatchWithTimeZone.java` (`ChargePriceIndicator`-adjacent Tally posting method names) and `JwtTokenFilter.java`/`ExecuteBatchForcefully.java` (both already covered above). `discharge`-collision false positives were excluded in `SwaggerConfiguration.java`, `AdtA02MessageBuilder.java`, `AdtA08MessageBuilder.java` (both HL7 `PV2.expectedDischargeDateTime`/`dischargeDisposition` fields — standard HL7 vocabulary, not billing), `Hl7MessageDaoImpl.java`, and `Pv1_2Dto.java` — none of these five files' `discharge` hits are billing-related.
- **`fund`/`refund` produced one genuine (not false-positive) hit, reinforcing rather than expanding the billing-critical set.** `postAdvanceRefund(unitIds)` appears in both `MidNightBatchWithTimeZone.java` (line 145, live) and `RoomRentChargesBatch.java` (line 167, inside the dead-code block) — both files are already billing-critical via the forward-import criterion, so this doesn't add any new file.
- **`collection` produced zero hits anywhere in this module** (unlike OTIMS's `CollectionUtils` false positive) — there is no generic-collections-utility naming collision to exclude here.
- **`SwaggerConfiguration.java`'s `billing` hits are a clean false positive, not a real import.** It contains string literals (`"BILLING"`, `RequestHandlerSelectors.basePackage("com.param.billing")`) used purely to group Swagger/OpenAPI UI documentation by package prefix — no actual `import` statement and no catch blocks in this file at all (0 catches). Excluded.
- **A new sub-pattern first appears in this audit: an in-memory error-collection pattern that is closer to a real audit trail than any prior module's finding, but still doesn't meet the strict definition.** 27 of `MidNightBatchWithTimeZone.java`'s findings (lines 99–229 in `midnightBatch()`, lines 254–281 in `postRoomRent()`) follow the shape `catch(Exception e){ errorList.add(genarateDto(e.getCause().toString(), "methodName", "stepName", unitIds.toString())); }` — each catch *does* reference the exception (via `e.getCause().toString()`), builds a structured `ExceptionDto`, and appends it to an in-memory list that the method later iterates and attempts to persist via `batchDao.addExceptionLog(exceptionDto)` (itself wrapped in a **multi-catch**, `catch (ApplicationException | SQLException e) { e.printStackTrace(); }`, at lines 239 and 290 — the first multi-catch clauses found anywhere in this audit series). This is a materially more deliberate attempt at error visibility than an empty catch or `printStackTrace()`-only pattern seen elsewhere — but per the strict definition it is still a finding (no real logger call, no rethrow), and the persistence step it feeds into (a) only prints to console on failure (no logger, no rethrow — also a finding) and (b) even when it succeeds, delegates to `BatchDaoImpl.addExceptionLog()`, whose own catch (line 328) is empty, so a persistence failure there is silently and totally lost. Classified `other` (references the exception, does something beyond nothing, but doesn't meet the log-or-rethrow bar), with this note attached to each of the 27 occurrences plus the 2 multi-catch occurrences (29 `other`-classified findings total from this sub-pattern) so they're distinguishable from the module's more common empty-catch (`silent-swallow`) pattern.
- **The most severe individual finding in the module is `TDoctorShareImpl.java` lines 95 and 313** — `getDoctorShareService()` and `getDoctorReferralShareService()`, the methods that calculate and post doctor revenue-share and referral-share amounts off billing details, both wrap their entire processing loop in `catch(Exception e){ }` (empty) and then unconditionally `return new Response<>(SUCCESS, SUCCESS_CODE, null, null, null);` immediately afterward, regardless of whether the loop completed, partially completed, or failed on the first iteration. This is a textbook fabricated-success pattern on a billing-critical revenue-calculation path — not classified `status-masks-failure` (the catch body itself is empty, not `return null;`, so it doesn't meet that severity's strict definition), but functionally equivalent in effect: the caller cannot distinguish "all doctor shares posted" from "posting failed after doctor #1 of 50."
- **The DAO/scheduler layer's `HibernateException`-then-`Exception` double-catch-then-rethrow pattern appears in `BatchDaoImpl.java`**, but unlike every prior module, most of its instances **do** rethrow (13 of 18 catches) — this file is closer to "properly propagating" than the dominant pattern elsewhere in the series, with only 5 exceptions (the two `getMACANDIP()`/`addBathLog()` empty catches, the `batchJobToUpdateAppointmentStatus()` pair, and the ironic `addExceptionLog()` empty catch — see below).
- **A second, distinct instance of "the exception-logger's own exception handling is broken" was found, independent of the `com/param/exception` package.** `BatchDaoImpl.addExceptionLog(ExceptionDto)` (line 312) is `MidNightBatchWithTimeZone`'s persistence target for its in-memory `errorList` (see above) and performs its own raw-SQL `INSERT INTO public.exception_log(...)` — but its own `catch(Exception e){}` (line 328) is empty, so if that INSERT fails, the batch-job error record is lost with no trace at all, on top of the `ExceptionDao.addErrorLog()` defect already covered in the Summary.
- **Multi-catch clauses** (`catch (TypeA | TypeB e)`) — **3 found, the first in this audit series** (every prior module — Billing, Global, ADT, BloodBank, CSSDMaster, Pharmacy, DietAndKitchen, OTIMS — had zero). Two are in `MidNightBatchWithTimeZone.java` (lines 239, 290: `catch (ApplicationException | SQLException e) { e.printStackTrace(); }`, classified `other`, billing-critical); one is in `Hl7MessageService.java` (line 58: `catch (BillingException | HL7Exception | IOException e) { }`, empty, classified `silent-swallow`, billing-critical).
- **`status-masks-failure`** (the `return null;`-only pattern) — **zero instances** in this module, same as every prior audit. Several catches in this module do have a `return null;`/`return false;` sitting immediately *after* the catch block at the method level (e.g. `BatchDaoImpl.getMACANDIP()`, `MidNightBatchWithTimeZone.checkBatchJobExecutedOrNotForpostRoomRent/checkBatchJobExecutedOrNotFormidnightBatch/saveLog`) — these are **not** reclassified as `status-masks-failure`, consistent with the strict rule that the catch body *itself* must be exactly `return null;` for that severity; here the catch bodies are empty and the `return null;` is method-level fallthrough, so they remain `silent-swallow`.
- **3 files are pure interfaces** (`IBatchDao.java`, `IDoctorShare.java`, `IRoomRentBatchChargesService.java`) with zero catch blocks by construction, checked by the same "second character uppercase" convention used in the OTIMS audit (no naming collisions like OTIMS's `Intra*` classes exist in this module — every `I*.java` file in HIS-WAR is a genuine interface).
- **A small set of files have nonzero catches but zero findings, because every catch in them is clean** — worth the owner's awareness as existing "good" patterns: `GlobalExceptionHandler.java` (2/2 log via real logger — the only such file in the module), `RoomRentBatchChargesServiceImpl.java` (2/2 rethrow), `ReceiverApplication.java` (1/1 rethrow, wraps as `HL7Exception`), and `ContentCachingRequestWrapper.java` (1/1 rethrow, wraps as `IllegalStateException`). 13 of `BatchDaoImpl.java`'s 18 catches and 13 of `Hl7MessageDaoImpl.java`'s 15 catches also properly rethrow (though both files still have findings among their remaining catches).
- **This audit does not re-scan** `legacy/Billing`, `legacy/Global`, `legacy/ADT`, `legacy/BloodBank`, `legacy/CSSDMaster`, `legacy/Pharmacy`, `legacy/DietAndKitchen`, `legacy/OTIMS`, `legacy/Entity`, or any other module — it is HIS-WAR-only, matching this task's scope.
