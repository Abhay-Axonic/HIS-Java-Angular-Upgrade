# Audit: Silent Exception-Swallow Patterns — legacy/Inventory module

*Read-only audit, 2026-07-06. Same method as `docs/AUDIT_Billing_exceptions.md`, `docs/AUDIT_Global_exceptions.md`, `docs/AUDIT_ADT_exceptions.md`, `docs/AUDIT_BloodBank_exceptions.md`, `docs/AUDIT_CSSDMaster_exceptions.md`, `docs/AUDIT_Pharmacy_exceptions.md`, `docs/AUDIT_DietAndKitchen_exceptions.md`, and `docs/AUDIT_OTIMS_exceptions.md`; scope here is the Inventory module — hospital store/stock management, covering nursing consumable/non-billable consumption, scrap & asset-disposal witness-approval workflows, stock adjustments (stop-transaction, upload/compute/confirm stock, variance approval), opening-balance/implant stock setup, and store operations (material inward/issue/return, indent, shelf allocation, batch change, drug recall, returnable gatepass) under `com/param/inventory/{nursing,scrap,stock,stockAdjustments,store}`.*

**Scope:** every `.java` file under `legacy/Inventory` (299 files, all under `src/main/java` — no `src/test/java` directory exists in this module). 304 `catch` blocks structurally parsed.

**Method:** read-only. Automated structural parse (comment/string-aware brace matching, Python script) of every `catch` block, classified by body content, cross-checked by manual sampling across layers (controller, DAO, service) and both exclusion categories (rethrow and — since there are zero real logger calls in this module — the "logged" category was checked and confirmed empty rather than assumed). Spot-checked: the 6 `status-masks-failure` (`return null;`-only) findings opened directly in `StopTransactionService.java`/`UploadStockDao.java`/`UploadStockController.java`; the 6 `other` (printStackTrace/println-only) findings opened directly across `UploadStockApprovalService.java`, `ConfirmStockService.java`, `StoreStockDao.java`, `MaterialReturnDao.java`, `ReturnableGatepassDao.java`; the dominant new sub-pattern (`new ErrorResponse(code, message, ex)`, 231 occurrences) confirmed against `ErrorResponse.java`'s actual constructor source in `legacy/Entity`; all 6 non-finding "properly rethrows" exclusions opened directly (`WitnessApprovalService.java`, `MaterialIssueAcceptanceDao.java` ×2, `MaterialReturnAcceptanceDao.java` ×2, `ReturnableGatepassDao.java`) and confirmed each has its own separately-tracked sibling catch that is a genuine finding, not merged away by the parser; and the billing-critical null result, checked from all four angles below. The parser itself was first validated against a raw `catch\s*(` grep count (311 raw occurrences vs. 304 structurally valid — the 7-occurrence gap was manually confirmed to be entirely commented-out/dead code, spread across 6 files rather than concentrated in one or two as in prior modules: `ScrapRequestController.java` (1, inside a `/*...*/`-fenced dead `@RequestMapping` method, lines 48–63), `WitnessApprovalService.java` (2, inside a `/*private CommonResponse allocateItemQuantity...*/`-fenced dead method, lines 162–199), `OpeningBalanceImplantController.java` (1, inside a `/* ... */`-fenced dead method, lines 137–154), `ConfirmStockDao.java` (1, a single `//`-commented-out line), `MaterialInwardController.java` (1, inside a `/*@RequestMapping...*/`-fenced dead method, lines 65–78), and `MaterialPickerController.java` (1, inside a large Javadoc-style `/** ... */` block containing a whole dead example method with its own `catch`) — the same scaffolding/dead-code pattern noted in every prior module in this series, just more distributed here. No file under `legacy/` was modified.

**Definition used (per task, identical to every prior audit in this series):** a finding is any catch block that is (a) empty, (b) returns `null`/a generic hardcoded error with no logging of the real cause, or (c) neither logs (via a real logger call) nor rethrows. Catch blocks that call a logger (`logger.error(...)`, etc.) or that `throw`/rethrow are excluded as non-findings.

## Methodology caveats (read before acting on this list)

- **Billing-critical heuristic returned zero hits, checked from every angle used in prior audits — including the two candidates the task explicitly flagged (scrap/disposal, consumption tracking).** (a) package check: no file lives under `com/param/billing/` or `com/param/global/billing/` — every file is under `com/param/inventory/{nursing,scrap,stock,stockAdjustments,store}` or `com/param/global/dto/items` (a shared item/UOM DTO package, not billing). **Zero hits.** (b) path/filename keyword check (`payment|invoice|tariff|discount|deposit|fund|insurance|razorpay|pesapal|charge|voucher|refund|bill|consumption|collection|sanction|mpesa|ccavenue`, with the `(?<!dis)charge` exclusion): the only filename-level matches are 11 files in `com/param/inventory/nursing/{controller,service,dao,dto}/nonBillableConsumption/` — matching both the `bill` and `consumption` keywords. But the package/class name is literally **"non-billable" consumption** — nursing-department stock consumption that is explicitly *not* charged to a patient bill (the opposite of a billing hook) — confirmed by reading `NonBillableConsumptionController.java`/`ConsumptionService.java`/`ConsumptionDao.java` in full: none imports anything billing-related, all imports are to shared entity/master/global-util packages. This is the same kind of keyword collision ADT/Pharmacy hit with `discharge`, just on `bill`/`consumption` instead of `charge` — flagged, not reclassified. No other filename in the module matches any keyword. (c) reverse-import check — whether `legacy/Billing` or `legacy/Global` imports anything from `com.param.inventory.*` — **zero hits** (confirmed with a repo-wide grep; the only modules that import `com.param.inventory.*` at all are `legacy/Procurement` and `legacy/LIS`, for an unrelated shared `AbstractDao` naming collision, not this module's actual DAOs). (d) forward-import check — whether any Inventory file imports `com.param.billing.*` or `com.param.global.billing.*` directly — **zero hits**; a repo-wide case-insensitive content grep for the literal substring `billing` anywhere in the module's source (not just imports) also returned **zero hits** (note: `Billable`/`nonBillable` do not contain the substring `billing`, so they did not trigger this check — only the keyword-list check in (b) caught them).
- **A genuine content-level judgment call, found but not promoted to billing-critical: `ReturnableGatepassService.java`/`ReturnableGatepassDao.java`/`ReturnableGatepassApprovalService.java` compute a `TotalDiscount`/`ActualDiscountPercentage` for items being returned to a vendor via a "gatepass."** This is a real monetary calculation living inside the Inventory module itself, surfaced by a content-level (not filename-level) search for `discount` — but per this series' criterion (b), only filename/path matches count, and `discount` does not appear in any of these files' names. Criteria (c) and (d) also came back empty for these specific files (no billing package import, not imported by Billing/Global). This reads as vendor-return bookkeeping (goods physically leaving the store back to a supplier, with a discount percentage recorded against the batch) rather than patient billing, and Inventory has no dedicated billing-package dependency anywhere to suggest otherwise — but it is flagged for the owner's awareness as a real financial calculation living outside the Billing module, consistent with the conservative, heuristic-not-data-flow-analysis approach used throughout this series. It did not change any classification.
- **The `collection` keyword produced one false-positive-only result, not a domain collision worth flagging further.** All 7 content-level hits are `java.util.Collections.sort/reverse/emptyList` calls (a generic Java collections utility), unrelated to billing "collections" (payment collection) — the same category of false positive noted in the OTIMS audit's `Test.java`/`CollectionUtils` finding.
- **A new dominant sub-pattern first appears in this audit: 231 of 298 findings (77.5%) use `catch (Exception ex) { return new ResponseEntity<>(new ErrorResponse(code, message, ex), HttpStatus.INTERNAL_SERVER_ERROR); }` (or the `ResponseEntity`-free `Response<>` equivalent), almost exclusively in the controller layer.** This looked, at first automated pass, like it might belong to the "generic hardcoded, no reference" bucket used in prior audits — but manually opening `legacy/Entity/src/main/java/com/param/common/dto/ErrorResponse.java` showed its constructor actually calls `ex.printStackTrace(new PrintWriter(writer))` (capturing the full stack trace as a string) and `ex.getMessage()`, and returns both in the HTTP response body sent to the caller. So these catches *do* reference the exception, more thoroughly than any prior module's pattern — but per this series' own definition (c), the test is whether the catch logs via a real logger or rethrows, not whether it references the exception at all; since this codebase has 0/299 logger imports, none of this diagnostic detail is ever persisted server-side, only exposed in the client-facing response. Classified `silent-swallow` (not a new severity), with distinct note text so it's searchable separately from the empty-catch and hardcoded-no-reference variants. Flagged for the owner as a secondary concern beyond "no server-side record": returning a raw exception stack trace in an API response body is also an information-disclosure consideration worth addressing whenever this pattern is eventually routed to the centralized handler.
- **`status-masks-failure` (the `return null;`-only pattern) is nonzero for the first time in this series: 6 instances**, all manually opened and confirmed genuine — `StopTransactionService.java` (4: lines 474, 497, 522, 533 — every catch in `removeItemsByProductId`, a second overload, `removeItembyItemId`, and `CheckStopTransactionDetail`), `UploadStockDao.java` (1: line 233), `UploadStockController.java` (1: line 219). All four `StopTransactionService.java` instances follow the exact same shape: a happy-path builds and returns a `CommonResponse`/success value, and the catch discards the exception and returns bare `null` instead — meaning callers of these particular methods cannot distinguish "operation succeeded with no result" from "operation threw an exception," a stronger form of the silent-swallow problem than the response-object patterns elsewhere in this module.
- **6 findings fall outside both dominant patterns and were individually reviewed**, split across `no-reference hardcoded` (a hardcoded-string `Response<>`/`Response(null,null,null,null,null)` return with no exception reference, or a boolean flag silently reset to `false` — `UploadStockService.java:573`, `StopTransactionDao.java:260/277/293`, `ComputeStockDao.java:254`, `NonBillableConsumptionController.java:152`) and `other` (5 `printStackTrace()`-only catches — `UploadStockApprovalService.java:268`, `ConfirmStockService.java:414/440`, `StoreStockDao.java:1361`, `MaterialReturnDao.java:315` — plus 1 `System.out.println(e)`-only catch, `ReturnableGatepassDao.java:349`, the least-informative variant since it only prints the exception's `toString()`, no stack trace, same as the two OTIMS instances of this pattern). All 6 confirmed by direct manual inspection of the source.
- **The DAO-layer `HibernateException`-then-`Exception` double-catch template that dominated every prior module's top-ranked files is nearly absent here.** Only 5 `HibernateException` catches exist in the entire module (vs. hundreds in ADT/BloodBank/CSSDMaster/DietAndKitchen/Pharmacy/OTIMS), and all 5 properly rethrow (`throw new HibernateException(he.getMessage())`) — they are 5 of this module's 6 total non-findings. This module's DAO layer instead mostly uses a single bare `catch (Exception e) { }` per method, or (in `MaterialIssueAcceptanceDao.java`/`MaterialReturnAcceptanceDao.java`/`ReturnableGatepassDao.java`) a nested `try { ... catch(HibernateException){throw...} catch(Exception){} } catch(Exception){}` structure where the outer catch is also empty — each inner/outer pair was manually confirmed to be two genuinely separate catch blocks (the parser correctly counts them individually, not merged), with the `HibernateException` one properly rethrowing and its Exception sibling(s) a finding.
- **Layer breakdown by sub-pattern confirms a clean architectural split**: of 298 findings, 232 are in controllers (231 `ErrorResponse`-pattern + 1 hardcoded), 61 are in DAOs (31 empty + 4 hardcoded/flag-reset + 3 `other` + 1 status-masks-failure — plus 5 `HibernateException` non-findings not counted here), and 26 are in services (18 empty + 1 hardcoded + 3 `other` + 4 status-masks-failure, all 4 in `StopTransactionService.java`). Controllers wrap everything in a response object (still a finding per this series' definition); DAOs and services below them mostly discard silently.
- **Multi-catch clauses** (`catch (TypeA | TypeB e)`) — **zero** occurred in this module, same as every prior audit in this series.
- **Zero files in this module have catch blocks but zero findings** (i.e., no file exists where every catch properly rethrows) — unlike OTIMS, which had 3 such "clean" service classes. Every one of the 57 files in Inventory that contains at least one catch block contains at least one finding.
- **Scope has no `src/test/java` directory** — same as CSSDMaster, Pharmacy, DietAndKitchen, and OTIMS; all 299 files are `src/main/java`.
- **66 of the 299 files are pure interfaces** (`IScrapRequestDao.java`, `IUploadStockService.java`, etc.), zero catch blocks by construction, all individually confirmed to contain an actual `interface` keyword declaration (not just an `I`-prefixed class). A naive `I*.java` filename glob overcounts to 84, because 18 DTO classes also happen to start with the letter `I` (`ItemRequest.java`, `ItemResponse.java`, `IssueBatch.java`, and similarly-named variants scattered across `dto` packages) — the correct interface count, checked by the same second-character-uppercase convention used in the OTIMS audit, is 66. The remaining 176 non-interface files have zero catch blocks: the large majority are pure DTO/request/response data-holder classes with no methods beyond getters/setters, and a smaller number (roughly 40) are Service/DAO implementation classes (concentrated in the `scrap` and `store` sub-packages, e.g. `ScrapRequestService.java`, `MaterialInwardDao.java`, `OpeningBalanceService.java`) that contain no local `try/catch` of their own — they delegate to other layers without local exception handling, so their exceptions simply propagate uncaught to the caller (a different, not-inherently-bad pattern from the ones catalogued here, but worth the owner's awareness as inconsistent error-handling coverage within the same module).
- **The parser is structural, not control-flow-aware**, identical caveat to every prior audit in this series: a catch block containing `throw` anywhere in its body is treated as "properly rethrows" and excluded, even if a nested conditional path could still silently fall through without throwing.
- This audit does **not** re-scan `legacy/Billing`, `legacy/Global`, `legacy/ADT`, `legacy/BloodBank`, `legacy/CSSDMaster`, `legacy/Pharmacy`, `legacy/DietAndKitchen`, `legacy/OTIMS`, `legacy/Entity`, or any other module — it is Inventory-only, matching this task's scope. `ErrorResponse.java` (in `legacy/Entity`) was opened only to confirm what its constructor does with the exception argument passed to it from Inventory's catch blocks; that file itself was not audited for its own exception handling.
