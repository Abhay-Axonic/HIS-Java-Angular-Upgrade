# Audit: Silent Exception-Swallow Patterns — legacy/LIS module

*Read-only audit, 2026-07-06. Same method as `docs/AUDIT_Billing_exceptions.md`, `docs/AUDIT_Global_exceptions.md`, `docs/AUDIT_ADT_exceptions.md`, `docs/AUDIT_BloodBank_exceptions.md`, `docs/AUDIT_CSSDMaster_exceptions.md`, `docs/AUDIT_Pharmacy_exceptions.md`, `docs/AUDIT_DietAndKitchen_exceptions.md`, and `docs/AUDIT_OTIMS_exceptions.md`; scope here is the LIS module (Laboratory Information System) — sample/order transaction and result-entry workflow for biochemistry, microbiology, serology and histopathology, plus shared unit/global master data (parameters, panels, machines, antibiotics, incubation, specimen types) — under `com/param/lis/{transaction,microbiology,serology,histopathology,unit,global,common,reports,exception}`.*

**Scope:** every `.java` file under `legacy/LIS` (631 files, all under `src/main/java` — no `src/test/java` directory exists in this module). 2,459 `catch` blocks structurally parsed.

**Method:** read-only. Automated structural parse (comment/string-aware brace matching, written as a standalone Python script) of every `catch` block, classified by body content, cross-checked by manual sampling (spot-checked empty-catch findings across controller/dao/service/utility layers, the `getMessage()`-referenced sub-case, all 4 `status-masks-failure` `return null;` catches, all 4 `other`/printStackTrace-or-println findings, several logged+rethrown and rethrow-only exclusions in both DAO and service files, the multi-catch check (none found), the billing-critical file set, and every file in the raw/structural gap — all matched their classification). The parser itself was first validated against a raw `catch\s*(` grep count (2,483 raw occurrences vs. 2,459 structurally valid — the 24-occurrence gap was manually confirmed to be entirely commented-out/dead code, spread across 16 files: three files (`DayMasterController.java`, `DayMasterDaoImpl.java`, `DayMasterServiceImpl.java`) each have their single method fully `/* ... */`-fenced; `CommonDateUtils.java` has 5 dead catches (3 whole commented-out methods — `getFirstDateOfMonth`, `getLocalTime`, `getTodaysDate` — plus 2 catches referenced only inside larger block comments); `RackMasterDaoImpl.java` has 5 dead catches across three separately-fenced commented blocks; the remaining 10 files (`CommonListController.java`, `IncubationTestServiceImpl.java`, `PrerequisitesMasterServiceImpl.java`, `TSubSpecimemDaoImpl.java`, `OutSourcePendingListForSampleDispatchServiceImpl.java`, `LabTransactionDaoImpl.java`, `ParameterMasterController.java`, `SingleParamTestMasterController.java`, `LabTemplateServiceImpl.java`, `PanelTestServiceImpl.java`, `StorageLocationMasterServiceImpl.java`) each have exactly one dead catch inside a single commented-out method or block — the same scaffolding-leftover pattern noted in every prior audit in this series). No file under `legacy/` was modified.

**Definition used (per task, identical to every prior audit in this series):** a finding is any catch block that is (a) empty, (b) returns `null`/a generic hardcoded error with no logging of the real cause, or (c) neither logs (via a real logger call) nor rethrows. Catch blocks that call a logger (`logger.error(...)`, etc.) or that `throw`/rethrow are excluded as non-findings.

## Summary

- **Total catch blocks parsed:** 2,459
- **Total findings (silent-swallow pattern matches):** 118
- **Non-findings:** 2,341 total — 1,225 properly log via a real logger call (of which 1,142 also rethrow after logging, and 83 log but do **not** rethrow — still correctly excluded as non-findings under this series' definition, since logging alone satisfies clause (c), but flagged below as a distinct sub-pattern not seen at this scale in any prior module); 1,116 properly rethrow (`throw`) with no logger call at all.
- **By severity:** silent-swallow = 110, other = 4, status-masks-failure = 4
- **By path:** billing-critical = 12, peripheral = 106

**124 of 631 files (19.7%) import a real logging library** (`org.apache.log4j.Logger`) — **by a wide margin the highest rate seen in this series**, compared to OTIMS (0/92), DietAndKitchen (0/124), ADT (0/589), BloodBank (0/161), CSSDMaster (0/128), Pharmacy (6/758, 0.8%), and Billing (28/558, 5%). Every one of the 124 logger-importing files was verified to genuinely call `logger.error(...)` inside at least one catch (no case of importing the logger without using it, and no case of calling `logger.xxx(...)` without a backing import — checked both directions module-wide). This is concentrated almost entirely in the `histopathology`, `microbiology`, `serology`, and most of the `transaction` and `unit` sub-packages, following a consistent `logger.error("Exection", e); throw e;` (sic, "Exection" is a module-wide typo) copy-paste template; the `common/`, `exception/`, and `reports/utility` packages, plus most `global/` master-data DAOs, were left out of this pattern and dominate the findings below. This is the first module in this series where the dominant failure mode is *not* "no logging infrastructure exists" — it clearly does, and is used correctly in the large majority of this module's catches — but rather a substantial, still-real minority of catches (mostly older master-data DAOs) that were never migrated to it.

**12 billing-critical findings (10.2% of all findings), concentrated across 5 of the module's 631 files** — `LabTransactionServiceImpl.java` (6), `BiochemReportReleaseController.java` (3), `BioChemResultEntryController.java` (1), `LabTransactionController.java` (1), and `BioChemResultEntryServiceImpl.java` (1). These 5 files are part of an 8-file billing-critical set found via the forward-import criterion (see caveats) — the other 3 billing-critical files (`ReportHandOverServiceImpl.java`, `BiochemReportReleaseServiceImpl.java`, `SerologyResultController.java`) have zero findings themselves (every catch in them logs or rethrows properly), so they contribute to the billing-critical *file* count but not the findings table.

## Methodology caveats (read before acting on this list)

- **Billing-critical determination required the forward-import criterion, and it needed unusually careful handling in this module — this is the key methodological finding of this audit.** Checked from every angle used in prior audits:
  - **(a) package check** — zero hits. No LIS file lives under `com/param/billing/` or `com/param/global/billing/`; all 631 files are under `com/param/lis/*`.
  - **(b) filename/path keyword check** (`payment|invoice|tariff|discount|deposit|fund|insurance|razorpay|pesapal|charge|voucher|refund|bill|consumption|collection|sanction|mpesa|ccavenue`, with the `(?<!dis)charge` exclusion) — 6 filename hits, **all false positives, checked individually**: `VoucherCodes.java` is a generic random-code-string generator utility (`Random`-based, used for miscellaneous code generation, not payment vouchers) with **zero catch blocks** at all; and the 5 `PhlebotomistHomeCollection*` files (`Controller`, `ServiceImpl`, `IPhlebotomistHomeCollectionservice`, `IPhlebotomistHomeCollectionDao`, `PhlebotomistHomeCollectionDaoImpl`, `PhlebotomistHomeCollectionDto`) all use "Collection" to mean a phlebotomist visiting a patient's home to *collect a sample* — a lab-logistics term, not payment collection — confirmed by checking these files for any `charge`/`payment`/`amount`/`bill` content (zero hits) and their imports (only generic `com.param.global.common.*`, no billing package). Content-level keyword grep also surfaced `payment` (26 files), `insurance` (21), `bill` (40), `collection` (46), `charge` (7), `tariff` (3), `discount` (1), `voucher` (1) — these are almost all patient-demographic fields (e.g. a patient's insurance/payment-mode metadata passed through as a DTO field, not computed or acted on) and were not independently promoted to billing-critical unless the file also satisfied criterion (d); see below for the one place this needed a real judgment call.
  - **(c) reverse-import check** — zero hits. Neither `legacy/Billing` nor `legacy/Global` imports anything from `com.param.lis.*` (only `legacy/HIS-WAR`, out of this audit's scope, does).
  - **(d) forward-import check, the operative criterion** — LIS does not literally import `com.param.billing.*` or `com.param.global.billing.*` (zero such import statements exist), but **10 files genuinely import and/or implement billing-named symbols from `com.param.global.{dao,service,dto,common}`**: `com.param.global.dao.IUnitApplicationBillingConfigurationDao`, `com.param.global.service.IUnitApplicationBillingConfigurationService`, `com.param.global.dto.BillingMasterDto`, and `com.param.global.common.IBillingCommonConstants`. These packages are not literally named `.billing.`, but tracing `IUnitApplicationBillingConfigurationDaoImpl` (in `legacy/Global`) shows it `extends GenericDao<UnitApplicationBillingConfiguration, Integer>`, and that entity class lives at `legacy/Entity/src/main/java/com/param/billing/global/transaction/config/model/UnitApplicationBillingConfiguration.java` — a genuine billing-module entity, reached through a Global-package facade. This satisfies this series' "...or call into a billing service/DTO" clause of criterion (d), the same way OTIMS's forward-import determination worked through the `com.param.global.billing.*` package directly. **8 files genuinely call methods on this DAO/service (not just declare an unused `@Autowired` field):** `BioChemResultEntryServiceImpl.java`, `ReportHandOverServiceImpl.java`, `BiochemReportReleaseServiceImpl.java`, `LabTransactionServiceImpl.java`, `BiochemReportReleaseController.java`, `LabTransactionController.java`, `SerologyResultController.java`, `BioChemResultEntryController.java` — invoking `getURLForPdfGeneration(...)`, `getUnitApplicationBillingConfigByOrgUnit(...)`, and `getPublicUrl(...)` to resolve per-organization/unit report-hosting and PDF-generation URLs that are stored in the billing-configuration table. These calls are about configuration lookup, not fee computation itself — but per this series' established file-level-propagation convention (see the OTIMS audit's `OTReservationDaoImpl.java`/`ProcedureTemplateServiceImpl.java` precedent, applied regardless of which specific method within the file is billing-related), **every catch in these 8 files is billing-critical**, not just the ones on the line that calls the billing DAO/service.
  - **A related false positive was found and deliberately excluded: `IBillingCommonConstants` is not a billing-computation interface.** It's a flat constants file (`String`/`Integer` fields like `BILL_NUMBER`, `SAMPLE_NUMBER`, `ORDER_NUMBER`, `DEPOSIT_PENDING`, `ENCOUNTER`, `ADMISSION`, `BLOOD_BAG_NUMBER`, etc.) that is really a **hospital-wide document/sequence-numbering registry**, misleadingly filed under a "Billing" name even though most of its constants (encounter numbers, blood-bag numbers, admission IDs) have nothing to do with money. `SpecimanReceiptServiceImpl.java` and `LabTransactionServiceImpl.java` both `implement IBillingCommonConstants` purely to access these shared numbering constants. For `LabTransactionServiceImpl.java` this doesn't matter (it's independently billing-critical via the real DAO-call criterion above); but **`SpecimanReceiptServiceImpl.java` is *not* counted billing-critical**, since implementing this constants interface is its *only* billing-adjacent signal and it never calls an actual billing DAO/service — a deliberate exclusion, not an oversight.
  - **A second near-miss, also deliberately not reclassified: `BioChemResultEntryDaoImpl.java` imports `com.param.global.dto.BillingMasterDto` but never uses it beyond the import statement** (a dead/unused import, confirmed by grep — the symbol appears nowhere else in the file). Not treated as an independent billing-critical trigger.
  - **A third, more substantive near-miss, flagged for the owner's awareness without changing any classification: an `isPreOrPostBilling` `Character` flag is threaded through 11 files** (`SearchDto.java`, `ILabTransactionDao.java`/`LabTransactionDaoImpl.java`/`ILabTransactionService.java`/`LabTransactionServiceImpl.java`/`LabTransactionController.java`, and the parallel `ISpecimanReceiptDao.java`/`SpecimanReceiptDaoImpl.java`/`ISpecimanReceiptService.java`/`SpecimanReceiptServiceImpl.java`/`SpecimanReceiptController.java` set) — 60 occurrences total — gating whether a phlebotomy/specimen-receipt worklist query runs *before or after* the patient's OPD bill has been generated. This is a genuine domain-level linkage between LIS's sample-collection workflow and the billing lifecycle, exactly the "test order → charge" pattern this task's brief called out to watch for. However, it is a plain method parameter, not an import of or call into a billing service/DTO/entity — so per this series' strict, mechanical 4-criterion method it does **not** independently trigger billing-critical status for the `SpecimanReceipt*` files (which otherwise meet none of the four criteria). This is the same category of judgment call as OTIMS's `Deposite` case and DietAndKitchen's `paymentEntitlementId` field — noted, not acted on.
  - **Net result:** 8 billing-critical files, 12 billing-critical findings (5 of the 8 files have findings; 3 have none — every catch in `ReportHandOverServiceImpl.java`, `BiochemReportReleaseServiceImpl.java`, and `SerologyResultController.java` properly logs or rethrows).
- **The raw-vs-structural gap (2,483 raw vs. 2,459 structural, a 24-occurrence gap) is entirely dead/commented-out scaffolding code**, spread across 16 files as detailed in the Method section above — every one individually opened and confirmed genuinely comment-fenced (not a parser miscount) before being excluded. This is the same "dead scaffolding" pattern noted in every prior audit in this series, just spread across more files here given the module's much larger size.
- **Multi-catch clauses** (`catch (TypeA | TypeB e)`) — **zero** occurred in this module, same as every prior audit in this series.
- **`status-masks-failure`** (the bare `return null;` pattern) — **4 instances, all in a single file: `legacy/LIS/src/main/java/com/param/lis/global/common/CommonUtils.java`** (lines 33, 58, 82, 124), a shared numeric-formatting/string-generation utility class (not a DAO/service/controller). This is worth flagging distinctly: in every prior module where this pattern occurred it was scattered across several files; here it is concentrated entirely in one shared utility, meaning any caller relying on `CommonUtils`'s number-formatting helpers to signal failure via a non-null return is exposed to the same masked-failure risk everywhere that utility is called.
- **The `other` category (4 findings) splits evenly between two distinct sub-patterns, both previously seen in this series but confirmed independently here.** Two `printStackTrace()`-only findings, both in `TTemplateResultDaoImpl.java` (lines 197 and 199 — the file's `HibernateException`-then-`Exception` double-catch pair, each clause containing only `he.printStackTrace();` / `e.printStackTrace();`). Two `System.out.println(e)`-only findings, in `BiochemReportReleaseController.java` (line 1101) and `ClinicalInterventionProcedureDaoImpl.java` (line 98) — even less informative than `printStackTrace()` since `System.out.println` on an exception only prints its `toString()` (class + message), no stack trace. **Two near-misses were checked and correctly excluded, not double-counted:** a third `printStackTrace()` call exists at `TSubSpecimemDaoImpl.java:79`, but it sits inside the same dead/commented-out `updateSubSpecimenDetails` method already excluded in the raw/structural gap above; and a fourth `System.out.println(e)` call exists at `LabTransactionDaoImpl.java:4460`, but that catch *also* calls `logger.error("Exception", e)` on the next line, so it is correctly classified as a non-finding (properly logged) rather than `other`.
- **A genuinely new sub-pattern in this series: 83 catches call a real logger but do *not* rethrow** (as opposed to the 1,142 that log-and-rethrow, and the 1,116 that rethrow with no log call at all). These remain correctly excluded as non-findings under this series' definition — clause (c) only requires logging *or* rethrowing, not both — but they represent a materially different risk profile than every other non-finding in this series: the failure is recorded server-side (unlike every true finding in this table) but execution continues past the catch as if nothing happened (unlike a rethrow, which lets the centralized handler or an upstream caller react). This is worth the owner's attention as a distinct middle category, even though it is out of scope for this audit's finding count.
- **This module has an active, wired-up centralized exception handler that no prior module in this series exhibited: `legacy/LIS/src/main/java/com/param/lis/exception/handler/RestExceptionHandler.java` is a genuine `@ControllerAdvice` class with multiple `@ExceptionHandler` methods** (for `EntityNotFoundException`, generic `Exception`, JPA's `EntityNotFoundException`, and `DataIntegrityViolationException`), with zero catch blocks of its own. Combined with the module-wide logging discipline noted above, LIS is the first module observed with both a working per-catch logging pattern in a majority of its files *and* a live centralized handler — but its actual reach depends entirely on exceptions being allowed to propagate past local try/catch blocks, which the 1,116 properly-rethrowing catches would do and the 118 findings in this table, by definition, would not.
- **The DAO layer's `HibernateException`-then-`Exception` double-catch pattern remains the single most common shape among findings that are *not* logged**, especially in `global/dao/*MasterDaoImpl.java` master-data classes (`AntibioticAddtionClassMasterDaoImpl`, `AntibioticsGroupMasterDaoImpl`, `AntibioticsMasterDaoImpl`, `BlockMasterDaoImpl`, `ColonyMasterDaoImpl`, `IncubationPeriodMasterDaoImpl`, `IncubationTestMasterDaoImpl`, `SpecimanMasterDaoImpl`, `UnitMasterDaoImpl`, and others) — almost all following an identical 3-CRUD-method template with 3 findings each, strongly suggesting a single copy-pasted master-data DAO template that was never migrated to the `logger.error(...)` pattern used elsewhere in the module.
- **By layer, findings break down as: 75 in DAO classes, 22 in shared `common`/utility classes, 12 in service classes, and 9 in controller classes** — the DAO layer dominates numerically (as in every prior module), but the concentration of findings in `common/` utility classes (`CommonDateUtils.java` alone accounts for 14, the single largest count of any file in this audit) is new: in prior modules, shared-utility classes were rarely the top-ranked file.
- **Interface file count required the same "second-character-uppercase" convention correction used in the OTIMS audit, and it undercounted here too.** By that naming convention, 184 of 631 files are interfaces. A content-level check (`public interface` declarations) found 188 — **4 more genuine interfaces that don't match the naming convention**: three have a lowercase-second-letter typo baked into the original source (`IincubationObservationDao.java`, `ImicroscopicExaminationDetailsMaster.java`, `IincubationObservationService.java` — evidently meant to be `IIncubation...`/`IMicroscopic...`), and one (`LabTemplateService.java`) is a genuine interface with no `I`-prefix at all. All 188 content-verified interfaces have zero catch blocks, confirmed.
- **Of the 631 total files, 443 are non-interface implementation files** (631 − 188). **400 of these have zero findings**: 231 have at least one catch block, all of which properly log and/or rethrow; 169 have zero catch blocks at all (pure DTOs, config classes, and other exception-handling-free code). **43 files have at least one finding.**
- **The parser is structural, not control-flow-aware**, identical caveat to every prior audit in this series: a catch block containing `throw` anywhere in its body is treated as "properly rethrows" and excluded, even if a nested conditional path could still silently fall through without throwing.
- **Scope has no `src/test/java` directory** — same as CSSDMaster, Pharmacy, DietAndKitchen, and OTIMS — all 631 files are `src/main/java`.
- This audit does **not** re-scan `legacy/Billing`, `legacy/Global`, `legacy/ADT`, `legacy/BloodBank`, `legacy/CSSDMaster`, `legacy/Pharmacy`, `legacy/DietAndKitchen`, `legacy/OTIMS`, `legacy/Entity`, `legacy/HIS-WAR`, or any other module — it is LIS-only, matching this task's scope. In particular, it does not audit `legacy/Global`'s `UnitApplicationBillingConfigurationDaoImpl.java`/`UnitApplicationBillingConfigurationServiceImpl.java` (which LIS calls into) or `legacy/Entity`'s `UnitApplicationBillingConfiguration.java` entity, both referenced above only to establish the billing-critical determination for LIS's own files.
