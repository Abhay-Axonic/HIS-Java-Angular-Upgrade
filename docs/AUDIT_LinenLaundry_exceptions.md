# Audit: Silent Exception-Swallow Patterns — legacy/LinenLaundry module

*Read-only audit, 2026-07-06. Same method as `docs/AUDIT_Billing_exceptions.md`, `docs/AUDIT_Global_exceptions.md`, `docs/AUDIT_ADT_exceptions.md`, `docs/AUDIT_BloodBank_exceptions.md`, `docs/AUDIT_CSSDMaster_exceptions.md`, `docs/AUDIT_Pharmacy_exceptions.md`, `docs/AUDIT_DietAndKitchen_exceptions.md`, and `docs/AUDIT_OTIMS_exceptions.md`; scope here is the LinenLaundry module (linen/laundry stores workflow — indent, indent approval, issue, issue-list, issue acceptance, return, return acceptance, rejected-linen acceptance, and send-to-condemnate — under nine feature packages beneath `com/param/linenLaundry`).*

**Scope:** every `.java` file under `legacy/LinenLaundry` (54 files, all under `src/main/java` — no `src/test/java` directory exists in this module). 37 `catch` blocks structurally parsed.

**Method:** read-only. Automated structural parse (comment/string-aware brace matching) of every `catch` block, classified by body content, cross-checked by manual sampling (every one of the 9 controller files that contains a catch block was opened and read in full, not just sampled, since the module is small; the `ErrorResponse(code, message, ex)` pattern used in every single finding was independently traced to its constructor in `legacy/Entity/src/main/java/com/param/common/dto/ErrorResponse.java` to confirm it performs no server-side logging — it only captures `ex.getMessage()` and a manually-built stack-trace string onto the response DTO sent back to the HTTP caller). The parser itself was first validated against a raw `catch\s*(` grep count (40 raw occurrences vs. 37 structurally valid — the 3-occurrence gap was manually confirmed to be entirely commented-out/dead code, all three inside `RejectedLinenAcceptanceController.java`: one method (`getRejectLinenAcceptanceList`, catch at what would be line 56) is fenced in a `/* ... */` block from lines 46–61, still inside the class body; the other two (`getRejectLinenAcceptanceDetails` and `saveRejectLinenAcceptance`, catches at lines 73 and 92) sit in a second `/* ... */` block spanning lines 63–99 — and that second block is physically *outside* the class's own closing brace (line 62), i.e. genuinely dead scratch code left after the class ends, which would not even compile if uncommented as-is. Both fenced blocks were opened and visually confirmed, not inferred). No file under `legacy/` was modified.

**Definition used (per task, identical to every prior audit in this series):** a finding is any catch block that is (a) empty, (b) returns `null`/a generic hardcoded error with no logging of the real cause, or (c) neither logs (via a real logger call) nor rethrows. Catch blocks that call a logger (`logger.error(...)`, etc.) or that `throw`/rethrow are excluded as non-findings.

## Methodology caveats (read before acting on this list)

- **This module's architecture is structurally different from every prior module in this series, and that difference is the main methodological finding here.** In OTIMS/DietAndKitchen/Pharmacy/ADT/etc., the DAO layer paired a `HibernateException` catch with an `Exception` catch on almost every method (the dominant source of findings). In LinenLaundry, **zero of the 8 DAO implementation files and zero of the 9 Service implementation files contain a single `try`/`catch` block anywhere** (confirmed with `grep -c 'try\s*{'` across every non-interface DAO/service file in the module — all returned 0). Exceptions thrown by Hibernate/`getSession()` calls in the DAO layer propagate unhandled all the way up through the Service layer to the Controller, which is the *only* layer in this module that ever catches anything. This means all 9 controllers, and only the 9 controllers, hold every catch block in the module.
- **Billing-critical determination returned zero hits on all four criteria, checked explicitly rather than assumed from the task's own hint that linen/laundry is "typically operationally-isolated" (same caution DietAndKitchen used).** (a) package check: no file lives under `com/param/billing/` or `com/param/global/billing/` — all 54 files are under `com/param/linenLaundry/*`. **Zero hits.** (b) path/filename keyword check (`payment|invoice|tariff|discount|deposit|fund|insurance|razorpay|pesapal|charge|voucher|refund|bill|consumption|collection|sanction|mpesa|ccavenue`, with the `(?<!dis)charge` exclusion available if needed) — **zero filename matches**, and a content-level case-insensitive grep across every file's full text for the same keyword list also returned **zero matches** (no `charge`/`discharge`-collision judgment call was even needed here, unlike ADT/Pharmacy/OTIMS, because the string `charge` does not appear anywhere in this module at all). (c) reverse-import check — `grep -rl 'com.param.linenLaundry' legacy/Billing legacy/Global` returned **zero hits**; no file in Billing or Global imports anything from this module. (d) forward-import check — `grep -rn 'import com.param.billing\|import com.param.global.billing' legacy/LinenLaundry` returned **zero hits**; this module imports nothing from either billing package. A repo-wide reverse check (`grep -rl 'com.param.linenLaundry' legacy --include=*.java`, excluding the module itself) found exactly one hit outside Billing/Global: `legacy/HIS-WAR/src/main/java/com/param/config/SwaggerConfiguration.java`, which is Swagger/API-documentation wiring, not a billing dependency — confirmed as an unambiguous false positive, not reclassified.
- **`sendToCondemnate` has no DAO package of its own — the only feature package in the module without one.** `SendCondemnateService.java` reads store/status/indent-type lookup data directly via `IGlobalDao` (an injected shared DAO from the Global module), not a LinenLaundry-owned DAO. This has no effect on billing-critical classification (`IGlobalDao` is a generic lookup DAO, not a billing dependency) but is noted for the owner as an architectural inconsistency worth flagging alongside the exception-handling findings.
- **Every one of the 37 findings shares one identical shape, a new sub-pattern for this series**: `catch (Exception ex) { return new ResponseEntity<Object>(new ErrorResponse("HIS-NNNN", "Error while ...", ex), HttpStatus.INTERNAL_SERVER_ERROR); }`. This was traced directly into `ErrorResponse`'s constructor (`legacy/Entity/src/main/java/com/param/common/dto/ErrorResponse.java`): it calls `ex.printStackTrace(new PrintWriter(writer))` into a `StringWriter` and stores the result as a `stackTrace` field, plus `ex.getMessage()` as a `summary` field — both serialized into the HTTP 500 response body. This is a materially richer variant of the `e.getMessage()`-in-payload sub-pattern first seen in OTIMS (34 findings there): instead of just the message string, the **entire stack trace** is captured and shipped to the HTTP caller. But per this series' own definition it is still a finding — `ErrorResponse`'s constructor contains no logger call of any kind (confirmed: no `org.slf4j`/`org.apache.log4j` import anywhere in that file), so nothing is ever persisted server-side; only a client that inspects the raw 500 response body ever sees the failure detail, and operators have no log record at all. Classified `silent-swallow` (not `status-masks-failure`, which per the Billing audit's definition is reserved for a bare `return null;`, and not `other`, which is reserved for console-only prints) with a shared note text across all 37 rows.
- **Multi-catch clauses** (`catch (TypeA | TypeB e)`) — **zero** occurred in this module, same as every prior audit in this series.
- **`status-masks-failure`** — **zero instances**. Every finding returns a `ResponseEntity<Object>` wrapping a populated `ErrorResponse`, never a bare `null`.
- **No `HibernateException` catch anywhere in the module** (`grep -rn HibernateException` returned zero hits) — a direct consequence of the DAO layer never catching anything (see first caveat above). This is the first module in the series with zero `HibernateException` references at all.
- **No `printStackTrace()`-only or `System.out.println(...)`-only catches** (the `other` category seen in Billing/DietAndKitchen/OTIMS) — zero instances; every catch in this module does the `ErrorResponse` construction described above, never a bare console print.
- **17 of the 54 files are pure interfaces** (`ILinenIndentDao.java`, `ILinenReturnAcceptanceService.java`, etc., using the same second-character-uppercase convention as the OTIMS audit) with zero catch blocks by construction. A naive `I*.java` filename glob overcounts to 19, because `ItemRequest.java` and `ItemResponse.java` (two plain DTO classes under `linenIndent/dto`) also start with the letter `I` — both excluded by the second-character check (`t` is lowercase), confirmed by opening both files (`public class ItemRequest` / `public class ItemResponse`, not interfaces).
- **17 non-interface DAO/Service implementation files (8 DAO + 9 Service) are "clean" in a different sense than every prior module**: they have zero findings not because their catches properly rethrow (the OTIMS/DietAndKitchen pattern), but because **they contain no `try`/`catch` at all** — exceptions simply propagate. This is a distinct, newly-observed variant of "clean file" for this series and is called out explicitly so it isn't misread as evidence of good exception hygiene; it just means the swallow point is relocated one layer up, into the controller, rather than eliminated.
- **11 files are plain DTOs** (`LinenRequest.java`, `LinenResponse.java`, `Carrier.java`, `RejectedLinenRequest.java`, etc.) with zero catch blocks by construction — pure data holders with only getters/setters/builder-style add-methods.
- **Scope has no `src/test/java` directory** — same as CSSDMaster, Pharmacy, DietAndKitchen, and OTIMS; all 54 files are `src/main/java`.
- **The parser is structural, not control-flow-aware**, identical caveat to every prior audit in this series: a catch block containing `throw` anywhere in its body would be treated as "properly rethrows" and excluded — moot in this module, since a repo-wide `grep -rn '\bthrow\b'` (excluding `throws Exception` in method signatures) found **zero explicit `throw` statements anywhere in the module**.
- This audit does **not** re-scan `legacy/Billing`, `legacy/Global`, `legacy/ADT`, `legacy/BloodBank`, `legacy/CSSDMaster`, `legacy/Pharmacy`, `legacy/DietAndKitchen`, `legacy/OTIMS`, `legacy/Entity`, or any other module — it is LinenLaundry-only, matching this task's scope. (The one exception traced outside the module boundary — `ErrorResponse.java` in `legacy/Entity` — was read only to confirm what LinenLaundry's own catch blocks do with the exception object; `legacy/Entity` itself was not audited.)
