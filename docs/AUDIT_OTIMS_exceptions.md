# Audit: Silent Exception-Swallow Patterns — legacy/OTIMS module

*Read-only audit, 2026-07-06. Same method as `docs/AUDIT_Billing_exceptions.md`, `docs/AUDIT_Global_exceptions.md`, `docs/AUDIT_ADT_exceptions.md`, `docs/AUDIT_BloodBank_exceptions.md`, `docs/AUDIT_CSSDMaster_exceptions.md`, `docs/AUDIT_Pharmacy_exceptions.md`, and `docs/AUDIT_DietAndKitchen_exceptions.md`; scope here is the OTIMS module (Operation Theatre Information Management System) — procedure/OT scheduling, reservation, checklist, equipment/staff scheduling, and pre/intra/post-operative documentation under `com/param/otims/{controller,dao,service}`, plus one stray scratch controller under `com/param/test`.*

**Scope:** every `.java` file under `legacy/OTIMS` (92 files, all under `src/main/java` — no `src/test/java` directory exists in this module). 284 `catch` blocks structurally parsed.

**Method:** read-only. Automated structural parse (comment/string-aware brace matching) of every `catch` block, classified by body content, cross-checked by manual sampling (spot-checked empty-catch findings across controller/dao/service layers, both exclusion categories — rethrow and logged — the `e.getMessage()`-referenced sub-case, the two `System.out.println(exception)`-only findings, the multi-catch check (none found), the 3-file raw/structural gap, and the billing-critical file set directly against source; all matched their classification). The parser itself was first validated against a raw `catch\s*(` grep count (287 raw occurrences vs. 284 structurally valid — the 3-occurrence gap was manually confirmed to be entirely commented-out/dead code: a `/* ... */`-fenced `addSample` template method left over from scaffolding, found in `ChecklistItemMasterController.java` (1 dead catch), `OTIMSDashboardController.java` (1 dead catch), and `OTReservationController.java` (1 dead catch) — the exact same dead scaffolding pattern noted in the Billing/Pharmacy/DietAndKitchen audits, just copy-pasted into three more controllers here). No file under `legacy/` was modified.

**Definition used (per task, identical to every prior audit in this series):** a finding is any catch block that is (a) empty, (b) returns `null`/a generic hardcoded error with no logging of the real cause, or (c) neither logs (via a real logger call) nor rethrows. Catch blocks that call a logger (`logger.error(...)`, etc.) or that `throw`/rethrow are excluded as non-findings.

## Methodology caveats (read before acting on this list)

- **Billing-critical determination required the forward-import criterion, not the filename criterion — this is the key finding of this audit.** Checked from every angle used in prior audits: (a) package check — no file lives under `com/param/billing/` or `com/param/global/billing/`; all 92 files are under `com/param/otims/{controller,dao,service}` or `com/param/test`. **Zero hits.** (b) path/filename keyword check (`payment|invoice|tariff|discount|deposit|fund|insurance|razorpay|pesapal|charge|voucher|refund|bill|consumption|collection|sanction|mpesa|ccavenue`) — **zero filename matches** anywhere in the module. (c) reverse-import check, whether `legacy/Billing` or `legacy/Global` imports anything from `com.param.otims.controller.*`, `com.param.otims.dao.*`, or `com.param.otims.service.*` (the actual packages scanned in this audit) — **zero hits**. (d) forward-import check, whether any OTIMS file imports `com.param.billing.*` or `com.param.global.billing.*` directly — **2 hits**: `ProcedureTemplateServiceImpl.java` (imports `com.param.global.billing.dto.AdmissionListIpdChargesResDto` and `com.param.global.billing.service.IContractConsumptionService`, and calls `consumeServiceFromContract`/`getSerivceRateGlobal` inside a method literally named `getProcedureConfigureOnOTBillingCompletion` — computing/consuming a patient's contract tariff rate for an OT procedure at billing completion time) and `OTReservationDaoImpl.java` (imports `com.param.global.billing.controller.BillingException` and throws it from two DAO methods — those two specific catches are non-findings/properly-rethrow, but the file's other 18 catches, on OT reservation CRUD methods in the same class, are findings and inherit the file's billing-critical status per this series' file-level heuristic). **Per this series' established convention (see Pharmacy audit, footnote on `WalkInSalesController.java`), billing-critical status is applied at the file level once criterion (d) is met — every finding in a billing-critical file is marked billing-critical, not just the specific catch block that touches billing logic.** This is why all 18 `OTReservationDaoImpl.java` findings are billing-critical even though only 2 of its 20 catches actually reference `BillingException`.
- **A separate, easy-to-misread reverse-import result does NOT add any file to the billing-critical set, and is called out here specifically so it isn't mistaken for one.** `legacy/Billing/src/main/java/com/param/procedure/**` (12 files: `ProcedureReqDaoImpl`, `OtCompletionMedicalGasDaoImpl`, `OTServiceDaoImpl`, `OTCompletionDetailsDaoImpl`, `OtCompletionEquipmentDaoImpl`, `OtCompletionStaffDaoImpl`, `ProcedureOrderDaoImpl`, `OTCompletionCssdKitDaoImpl`, `ProcedureOrderServiceImpl`, and their `I*Dao` interfaces) import `com.param.otims.model.*` — but that package is **not** part of `legacy/OTIMS` at all; it's a shared entity/model package that physically lives in `legacy/Entity/src/main/java/com/param/otims/model/`, a separate Maven module. None of those imports resolve to any of the 92 files scanned in this audit (which are all `com.param.otims.controller/dao/service`, not `com.param.otims.model`). The package-name collision (`com.param.otims.*` used by both a shared entity module and this module's own DAO/service/controller layer) is real and worth flagging for the owner — `legacy/Billing` clearly depends on OT-completion resource/equipment/staff/medical-gas/CSSD-kit *entities* that share OTIMS's package namespace, which is architecturally significant for future refactoring — but it does not change any classification in this audit, since criterion (c) is scoped to files actually inside `legacy/OTIMS`.
- **The `deposit` keyword surfaced a genuine judgment call that was NOT reclassified.** Content-level (not filename-level) matches for `Deposite` [sic — misspelled throughout the source] appear in `OTReservationServiceImpl.java`, `IOTReservationService.java`, `IOTReservationDao.java`, `OTReservationController.java`, and `OTReservationDaoImpl.java`, all around a single method chain: `getOTReservationListByPatientIdForDeposite`, which runs a named query (`GET_RESERVED_PROCEDURES_BY_PATIENT_ID_FOR_DEPOSITE`) to list a patient's OT-reserved procedures that require an advance deposit — clearly a billing-adjacent screen. However: the `OTReservationServiceImpl.java` catch wrapping this specific method properly rethrows (non-finding, see line ~511), and `OTReservationServiceImpl.java`/`OTReservationController.java`/the two interfaces are kept **peripheral** in this audit because they don't independently satisfy any of the four criteria (no billing import, no monetary calculation performed in the file itself — they only delegate to the DAO). `OTReservationDaoImpl.java` is already billing-critical for the unrelated `BillingException` import reason above, so its copy of this same method's catch (line 377, empty, a finding) is already counted correctly. This is a judgment call flagged for the owner's awareness, consistent with the conservative, heuristic-not-data-flow-analysis approach used throughout this series (same treatment as the DietAndKitchen `paymentEntitlementId` DTO field and the Pharmacy `consumption` subsystem) — it did not change any classification beyond what criterion (d) already determined.
- **The `charge` keyword required the same discharge-collision exclusion ADT and Pharmacy needed.** `PostOperativeCareServiceImpl.java` contains `isDischarge`/`setIsDischarge` (patient discharge flag on a prescription DTO) — excluded via the same `(?<!dis)charge` logic, a false collision, not billing-related. No genuine (non-`discharge`) `charge` hits exist anywhere in this module — unlike Pharmacy's `otherCharges` package, OTIMS has no dedicated charge-configuration subsystem of its own (that logic, per the forward-import finding above, lives in `legacy/Billing`'s `IContractConsumptionService`, which OTIMS merely calls into).
- **`collection` produced one false-positive hit, not a domain collision worth flagging.** `Test.java` imports `org.springframework.util.CollectionUtils` — a generic Java collections utility, unrelated to billing "collections" (payment collection). Excluded as an unambiguous false positive.
- **A new sub-pattern first appears in this audit: catches that pass `e.getMessage()` into the response payload instead of a hardcoded string, but still never log through a real logger and never rethrow.** 34 findings across 10 files (`IntraOperativeDetailsController`, `OTIMSDashboardController` ×9, `OTReservationController` ×8, `PostOperativeCareController`, `PostOperativeDetailsController` ×2, `PreOperativeDetailsController` ×6, `ProcedureTemplateController` ×5, `PreOperativeDetailsDaoImpl` ×2) fit this shape: `catch (Exception e) { return new Response<>(ERROR, ERROR_CODE, e.getMessage(), null, null); }`. This is marginally better for the *caller* than the hardcoded-message pattern seen in every prior module (the HTTP client at least sees the real exception message string), but by this series' own definition it is still a finding — the failure is never logged or persisted anywhere on the server side (there is no logger call anywhere in this codebase, per the 0/92 logger-import count above), so operators have no server-side record of the failure; only the calling client — if it happens to display the raw error string — ever sees it. Classified `silent-swallow`, not `status-masks-failure` (that label is reserved for the bare `return null;` pattern per the Billing audit's definition), with a distinct note text so this sub-pattern is searchable separately from the hardcoded-message and empty-catch variants.
- **Two findings use `System.out.println(exception)` instead of `printStackTrace()` or a real logger — a variant not seen in any prior audit in this series.** Both are in `PreOperativeDetailsDaoImpl.java` (lines 161 and 163: `catch (HibernateException he) { System.out.println(he); }` / `catch (Exception e) { System.out.println(e); }`). This is even less informative than the `printStackTrace()`-only pattern (Billing, DietAndKitchen) — `System.out.println` on an exception object calls its `toString()`, printing only the class name and message, with **no stack trace at all** — but it shares the same core defect (console-only, not persisted, no status signal). Classified `other`, consistent with how `printStackTrace`-only catches were classified in every prior audit, with a note explicitly distinguishing it from the stack-trace-bearing `printStackTrace()` variant.
- **The DAO layer's `HibernateException`-then-`Exception` double-catch pattern is dominant** in this module, same as every prior audit: nearly every DAO method (`ChecklistItemMasterDaoImpl`, `ChecklistMasterDaoImpl`, `ChecklistMasterDetailsDaoImpl`, `EquipmentSchedulingDaoImpl`, `NotesMasterDaoImpl`, `OTIMSDashboardDaoImpl`, `OTReservationDaoImpl`, `OtSchedulingDaoImpl`, `StaffSchedulingDaoImpl`, and others) follows the shape `catch (HibernateException he) { ... } catch (Exception e) { ... }`, both clauses empty or returning a generic hardcoded error. This repeats so consistently across otherwise-unrelated master-data DAOs that it almost certainly reflects a single copy-pasted DAO template, not independently-written bugs — same conclusion as every prior module in this series.
- **Multi-catch clauses** (`catch (TypeA | TypeB e)`) — **zero** occurred in this module, same as every prior audit in this series.
- **`status-masks-failure`** (the `return null;`-only pattern from BR-003/BR-005) — **zero instances** in this module. Every non-empty finding returns a `Response`-style object with a hardcoded `ERROR` status or the exception's message, not a bare `null`.
- **Three non-interface classes have zero findings, and all three are clean for the same reason: every catch in them properly rethrows.** `IntraOperativeDetailsServiceImpl.java`, `PostOperativeCareServiceImpl.java`, and `PostOperativeDetailsServiceImpl.java` each wrap their DAO calls in `catch (Exception e) { throw e; }` — a small, positive counter-example to the module's otherwise-dominant swallow pattern, worth the owner's awareness as an existing "good" pattern that could be extended elsewhere rather than reinvented.
- **`com/param/test/Test.java` is a leftover scratch/demo controller, not a JUnit test**, mapped to `/otims/test` with a trivial `return "Hello";` inside its try block (the catch can never actually fire) plus a `main()` method fenced with dead/commented experimental code (an LLM-prompt-building snippet referencing "radiology report" generation, unrelated to OTIMS proper — likely copy-pasted or prototyped from elsewhere and abandoned). Its one catch block is still empty and is counted as a finding (line 21) per the mechanical definition used throughout this series, but the owner should know this endpoint is not live application logic in the same sense as the rest of the module.
- **Scope has no `src/test/java` directory** — same as CSSDMaster, Pharmacy, and DietAndKitchen — all 92 files are `src/main/java`.
- **39 of the 92 files are pure interfaces** (`IChecklistItemMasterDao.java`, `IOTReservationService.java`, etc.) with zero catch blocks by construction — not double-counted as "clean" implementation files. (Note: a naive `I*.java` filename glob overcounts to 43, because four `IntraOperative*.java` implementation classes also happen to start with the letter `I`; the correct interface count, checked by convention — second character uppercase — is 39.)
- **The 3-occurrence gap between raw `catch(` grep (287) and structurally valid catches (284) is entirely dead/commented-out code**: a `/* ... */`-fenced `addSample` scaffolding method (with its own internal empty catch) appears, unused, in `ChecklistItemMasterController.java` (lines 24–41), `OTIMSDashboardController.java`, and `OTReservationController.java` — each manually opened and confirmed to be genuinely comment-fenced (not a parser miscount) before being excluded. This is the same scaffolding artifact noted in the DietAndKitchen and Pharmacy audits, just propagated into three more controllers here.
- **The parser is structural, not control-flow-aware**, identical caveat to every prior audit in this series: a catch block containing `throw` anywhere in its body is treated as "properly rethrows" and excluded, even if a nested conditional path could still silently fall through without throwing.
- This audit does **not** re-scan `legacy/Billing`, `legacy/Global`, `legacy/ADT`, `legacy/BloodBank`, `legacy/CSSDMaster`, `legacy/Pharmacy`, `legacy/DietAndKitchen`, `legacy/Entity`, or any other module — it is OTIMS-only, matching this task's scope. In particular, it does **not** audit `legacy/Entity/src/main/java/com/param/otims/model/*` (a different module, despite the shared package prefix — see the reverse-import caveat above) or `legacy/Billing/src/main/java/com/param/procedure/*` (which consumes those entities).
