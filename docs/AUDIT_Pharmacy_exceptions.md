# Audit: Silent Exception-Swallow Patterns — legacy/Pharmacy module

*Read-only audit, 2026-07-06. Same method as `docs/AUDIT_Billing_exceptions.md`, `docs/AUDIT_Global_exceptions.md`, `docs/AUDIT_ADT_exceptions.md`, `docs/AUDIT_BloodBank_exceptions.md`, and `docs/AUDIT_CSSDMaster_exceptions.md`; scope here is the Pharmacy module (walk-in/OP sales and billing, IP/nursing consumable and medication issue-return, narcotics, theatre management, QMS kiosk/token queueing, master data for items/tariffs/insurance, and prescription/qms sub-packages).*

**Scope:** every `.java` file under `legacy/Pharmacy` (758 files, all under `src/main/java` — no `src/test/java` directory exists in this module). 773 `catch` blocks structurally parsed.

**Method:** read-only. Automated structural parse (comment/string-aware brace matching) of every `catch` block, classified by body content, cross-checked by manual sampling (spot-checked findings across every severity category, both exclusion categories — rethrow and logged — the empty-catch/return-null/generic-error/printStackTrace-only sub-cases, the multi-catch check (none found), and the billing-critical file set directly against source; all matched their classification). The parser itself was first validated against a raw `catch\s*(` grep count (791 raw occurrences vs. 773 structurally valid — the 18-occurrence gap was manually confirmed to be entirely commented-out/dead code, e.g. `BillSalesReturnController.java`, whose entire body is `//`-prefixed, and a `/* ... */`-fenced javadoc example in `ItemService.java`). No file under `legacy/` was modified.

**Definition used (per task, identical to the Billing/Global/ADT/BloodBank/CSSDMaster audits):** a finding is any catch block that is (a) empty, (b) returns `null`/a generic hardcoded error with no logging of the real cause, or (c) neither logs (via a real logger call) nor rethrows. Catch blocks that call a logger (`logger.error(...)`, etc.) or that `throw`/rethrow are excluded as non-findings.

## Methodology caveats (read before acting on this list)

- **billing-critical vs peripheral required a heuristic extension for this module, unlike ADT/BloodBank/CSSDMaster.** The baseline heuristic (identical to prior audits) is: (a) lives under a `com/param/billing/` or `com/param/global/billing/` package (none do — Pharmacy has no such package); (b) path/filename contains a payment/invoice/tariff/discount/deposit/fund/insurance/razorpay/pesapal/charge/voucher/refund/bill/consumption/collection/sanction/mpesa/ccavenue keyword; or (c) is one of the classes directly imported *by* `legacy/Billing` or `legacy/Global` (0 hits both directions — confirmed no file under `legacy/Billing` or `legacy/Global` imports `com.param.pharmacy.*`). Criteria (a) and (c) contribute zero, same as every prior module. Criterion (b) alone matched 59 files. **But unlike ADT/BloodBank/CSSDMaster, Pharmacy is not a purely clinical module — it directly calls into billing** (per the task's own framing: "Pharmacy has its own sale/bill/payment flows"). A direct check of `import` statements found **23 Pharmacy files that import `com.param.billing.*` or `com.param.global.billing.*` directly** (the *reverse* direction from criterion (c) — Pharmacy consuming Billing's API, not Billing consuming Pharmacy's). 14 of those 23 do not match any filename/path keyword and would have been invisible to the baseline heuristic — most notably **`WalkInSalesController.java`**, which imports `com.param.global.billing.dto.CommonBillingItemsDto`, `com.param.global.billing.dto.PharmacyBillCommonDto`, `com.param.global.billing.service.IBillingService`, `com.param.global.dto.BillingMasterDto`, and `IUnitApplicationBillingConfigurationService` — a walk-in-sales controller that constructs and submits billing DTOs directly, and (per the task's own hint) exactly the kind of file this audit was told to expect. Also caught only by this extension: `SalesReturnService.java`, `SalesWorkListService.java`, `CrashCartApprovalService.java`, and 10 more (full list in the raw scan). **This audit treats "criterion (b) path/filename keyword" UNION "criterion (d), new: direct `import com.param.billing.*`/`com.param.global.billing.*`" as billing-critical** — 73 files total, 21 of which have at least one finding (99 findings). Anyone re-running or extending this heuristic on remaining modules should check for this reverse-import pattern too, not just the filename keyword.
- **The `charge` keyword required the same special case ADT needed.** Pharmacy has its own `nursing/discharge/` package (patient-discharge medication reconciliation, ~13 files) where a plain substring match on `charge` would wrongly flag the entire discharge-summary/medication-reconciliation subsystem as billing-critical. The heuristic excludes `charge` when it's part of `discharge` (regex `(?<!dis)charge`), same as ADT. Unlike ADT (where the net effect was zero matches after exclusion), Pharmacy **does** have a genuine, non-`discharge` `charge` hit: the `master/global/{controller,service,dao,dto}/otherCharges/` package (8 files, "other charges" = miscellaneous billing line-items) — confirmed billing-critical by both keyword and semantics. No findings currently land in those 8 files (they have no catch blocks with findings in this pass), but they remain correctly flagged in the billing-critical file set for any future work.
- **`consumption` is a domain word worth flagging even though it was not excluded.** Two distinct Pharmacy subsystems match this keyword: `nursing/pharmacy/.../billableConsumption` and `.../returnBillableConsumption` (explicitly "billable" — unambiguous billing intent, 9 findings) and `nursing/crashCart/.../CrashCartConsumption` (crash-cart stock depletion tracking — less obviously monetary, but crash-cart items are typically billed to the patient on use, and `CrashCartApprovalService.java` itself imports `com.param.global.billing.*` per the criterion-(d) finding above, corroborating that this subsystem does feed billing). Both were kept as billing-critical per the same conservative, heuristic-not-data-flow-analysis approach used throughout this audit series — this is a judgment call flagged for the owner's awareness, not a confirmed false positive like the ADT/CSSDMaster `charge`/`discharge` and BloodBank `collection` collisions.
- **`bill` is Pharmacy's single largest keyword match (28 files)** and is unambiguous in every case — `BillListController`/`BillListService`/`BillListDao`, `BillSalesReturnController` (entirely commented-out/dead), `BillableConsumption*`, `BillSaveRequest`, etc. No collision or false-positive risk found for this keyword in this module.
- **The parser is structural, not control-flow-aware**, identical caveat to every prior audit in this series: a catch block containing `throw` anywhere in its body is treated as "properly rethrows" and excluded, even if a nested conditional path could still silently fall through without throwing.
- **`other` (printStackTrace-only) was tightened during this audit's own build.** An earlier pass of the parser classified any catch body containing `printStackTrace()` as `other`, regardless of what else the body did. Manual spot-checking caught that several Pharmacy catch bodies do `ex.printStackTrace(); return new ResponseEntity<>(new ErrorResponse(...), HttpStatus.INTERNAL_SERVER_ERROR);` — i.e. printStackTrace *plus* a substantive, exception-referencing, real-status-code generic error response, not "printStackTrace and nothing else." Those are classified `silent-swallow` (generic-error-response sub-case, printStackTrace noted in the row's Notes) to match the Billing/BloodBank precedent, where `other` is reserved for catch bodies where printStackTrace truly is the only thing that happens in that catch clause (the method's own fallback, if any, sits after the try/catch, not inside it — same "catch body only" scoping rule the CSSDMaster audit used for its empty-catch classification). All 11 `other` findings in this table were individually confirmed to have no substantive return statement inside the catch body itself.
- **`status-masks-failure`** (the `return null;`-only pattern from BR-003/BR-005) has **4 instances**: `FormulationTypeAndROAController.java:144`, `ItemController.java:222`, `BillableConsumptionService.java:917` (an unusual `try { throw new Exception(); } catch (Exception e) { return null; }` self-thrown/self-caught construct), and `BillListService.java:724` — 2 billing-critical (`BillableConsumptionService`, `BillListService`), 2 peripheral.
- **Multi-catch clauses** (`catch (TypeA | TypeB e)`) — **zero** occurred in this module, same as every prior audit in this series.
- **Scope has no `src/test/java` directory** — same as CSSDMaster; all 758 files are `src/main/java`.
- This audit does **not** re-scan `legacy/Billing`, `legacy/Global`, `legacy/ADT`, `legacy/BloodBank`, or `legacy/CSSDMaster` (already catalogued in their own audit docs) or any other module — it is Pharmacy-only, matching this task's scope.
