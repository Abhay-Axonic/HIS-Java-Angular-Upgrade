# Audit: Silent Exception-Swallow Patterns — legacy/Procurement module

*Read-only audit, 2026-07-06. Same method as `docs/AUDIT_Billing_exceptions.md`, `docs/AUDIT_Global_exceptions.md`, `docs/AUDIT_ADT_exceptions.md`, `docs/AUDIT_BloodBank_exceptions.md`, `docs/AUDIT_CSSDMaster_exceptions.md`, `docs/AUDIT_Pharmacy_exceptions.md`, `docs/AUDIT_DietAndKitchen_exceptions.md`, and `docs/AUDIT_OTIMS_exceptions.md`; scope here is the Procurement module — vendor quotations/enquiries/negotiations, purchase requests and purchase orders, good receipt notes (GRN) and GRN settlement, consignment stock (PO invoicing, returns, patient consumption), work orders (creation, negotiation, QR-based selection), physical inspection, loan-in/loan-out of assets, and implant indent/return acceptance, under `com/param/procurement/{consignment,loanInOut,purchase,quotation,workOrder}/{controller,dao,service}` plus a handful of shared DTOs/entities under `com/param/entity` and `com/param/global`.*

**Scope:** every `.java` file under `legacy/Procurement` (511 files, all under `src/main/java` — no `src/test/java` directory exists in this module, the same as every prior module in this series). 561 `catch` blocks structurally parsed.

**Method:** read-only. Automated structural parse (comment/string-aware brace matching) of every `catch` block, classified by body content, cross-checked by manual sampling (spot-checked empty-catch and generic-hardcoded findings across controller/dao/service layers, both exclusion categories — rethrow, spot-checked across `PurchaseRequestApprovalService.java`, `BonusUomMapperDaoImpl.java`, and `PurchaseOrderDetailsDaoImpl.java` — and logged, of which this module has zero real occurrences; the module's dominant `new ErrorResponse(code, message, ex)` payload sub-case; the two `status-masks-failure` bare-`return null;` findings; the 9 `printStackTrace()`-only and 1 `System.out.println()`-only findings; the multi-catch check, none found; the 18-occurrence raw/structural gap; and the billing-critical file set) directly against source; all matched their classification. The parser itself was first validated against a raw `catch\s*(` grep count (579 raw occurrences vs. 561 structurally valid — the 18-occurrence gap was manually confirmed to be entirely commented-out/dead code spread across 12 files: whole methods or individual `catch` clauses fenced by `/* ... */` block comments, e.g. `ConsignmentStockPOInvoiceServicesImpl.java`, `ConsignmentStockReturnService.java`, `ConsignmentStockReturnController.java`, `PurchaseRequestService.java`, `OtherChargesPOMapperDaoImpl.java`, `BonusUomMapperDaoImpl.java`, `PurchaseOrderUomMapperDaoImpl.java`, `PurchaseOrderController.java`, `PurchaseOrderApprovalController.java`, `WorkOrderNegotiationController.java`, `WorkOrderSelectionController.java` — the same dead-scaffolding/commented-out-endpoint pattern noted in every prior audit in this series, just spread across more files simply because Procurement (511 files) is the largest module audited so far). No file under `legacy/` was modified.

**Definition used (per task, identical to every prior audit in this series):** a finding is any catch block that is (a) empty, (b) returns `null`/a generic hardcoded error with no logging of the real cause, or (c) neither logs (via a real logger call) nor rethrows. Catch blocks that call a logger (`logger.error(...)`, etc.) or that `throw`/rethrow are excluded as non-findings.

## Methodology caveats (read before acting on this list)

- **Billing-critical determination, criterion by criterion.**
  - **(a) Package check** — exactly **one** hit: `legacy/Procurement/src/main/java/com/param/global/billing/dto/PaymentReceiptDetailsDto1.java` lives directly under a `com/param/global/billing/` package inside this module. It is a plain DTO (vendor payment mode/amount/bank/cheque fields for a GRN payment) with **zero catch blocks**, so it contributes 0 findings, but it is flagged here for completeness since it is a genuine, if inert, package-check hit.
  - **(b) Filename/path keyword check** — 6 files with live findings: the `invoice` keyword catches `ConsignmentStockPOInvoiceController.java` (8), `ConsignmentStockPOInvoiceDaoImpl.java` (6), and `ConsignmentStockPOInvoiceServicesImpl.java` (2) — vendor invoicing for consignment-stock purchase orders; the `consumption` keyword catches `PatientConsumptionController.java` (7), `PatientConsumptionDao.java` (8), and `PatientConsumptionService.java` (1) — recording which consignment-stock items a patient actually consumed, which is what drives the patient's bill. Several other keyword hits exist but contribute 0 findings because they are pure DTOs/interfaces/mappers with no catch blocks at all: `ConsignmentStockPODetailResponseDto.java`, `ConsignmentStockPORequestDto.java`, `ConsignmentStockPOResponseDto.java`, `IConsignmentStockPOInvoiceService.java`, `IConsignmentStockPOInvoiceDao.java`, the whole `OtherCharges`/`PoOtherChargesMapper`/`GRNOtherChargesMapper` family (the `charge` keyword), and nine `patientConsumption` DTOs. No `(?<!dis)charge`-style discharge collision actually arose in this module (unlike ADT/Pharmacy/OTIMS) — Procurement has no discharge-adjacent vocabulary at all — and the `collection` keyword produced zero filename hits (no `java.util.Collection`-style false positive risk to exclude, unlike OTIMS's `Test.java`). `fund`, `deposit`, `tariff`, `insurance`, `voucher`, `refund`, `sanction`, `mpesa`, `ccavenue`, `razorpay`, and `pesapal` all produced zero filename/path hits anywhere in this module.
  - **(c) Reverse-import check** — **zero hits.** Neither `legacy/Billing` nor `legacy/Global` imports anything from `com.param.procurement.*`.
  - **(d) Forward-import check (Java-level)** — two genuine, but inert, hits: `GrnSettledRequest.java` imports `com.param.global.billing.dto.PaymentReceiptDetailsDto` (the real class, defined in `legacy/Global/src/main/java/com/param/global/billing/dto/PaymentReceiptDetailsDto.java`), and `ServiceWorkOrderCreationServiceImpl.java` imports `com.param.global.billing.dao.IVendorServiceRateConfigDao` (defined in `legacy/Global`) and genuinely calls `iVendorServiceRateConfigDao.getVendorRatesListForService(...)` to fetch vendor service billing rates for a work order. Both are real cross-module billing dependencies, but **both files have zero catch blocks** (`GrnSettledRequest.java` is a plain request DTO; `ServiceWorkOrderCreationServiceImpl.java` has no try/catch anywhere in its 129 lines), so neither contributes any findings — a billing-critical file with nothing to propagate, the same shape as `IContractConsumptionService`-calling files noted in the OTIMS audit.
  - **A deliberately-excluded near-miss, called out so it isn't mistaken for a hit.** `GoodReceiptNoteService.java` (1 finding, line 1782, empty catch) contains the import statement `import com.param.global.billing.dto.PaymentReceiptDetailsDto1;`, which textually matches the criterion-(d) pattern `com.param.global.billing.*`. However, `PaymentReceiptDetailsDto1` (note the trailing "1") is **not** the real `legacy/Global` class — it is a Procurement-local duplicate physically defined at `legacy/Procurement/src/main/java/com/param/global/billing/dto/PaymentReceiptDetailsDto1.java` (the same file that satisfies criterion (a) above), which merely happens to sit in a package namespace named `com.param.global.billing` inside Procurement's own source tree — almost certainly a copy/paste of the real Global DTO that was then locally forked and given a "1" suffix, rather than a genuine cross-module dependency. `GrnSettledRequest.java` (0 findings) imports both the real `PaymentReceiptDetailsDto` and the local `PaymentReceiptDetailsDto1` side by side, confirming the two are different classes with near-identical names. Because `GoodReceiptNoteService.java`'s only "billing" import resolves locally and its own filename/path do not match the keyword criterion, this audit keeps it **peripheral**, consistent with this series' practice of favoring the substantive dependency over the textual pattern (see OTIMS's analogous `com.param.otims.model` vs. `com.param.otims.{dao,service,controller}` package-collision caveat).
  - **(d, extended) Forward-dependency via raw SQL against the billing schema — this audit's headline finding.** Two DAOs contain native/raw SQL (via `createSQLQuery`) that directly joins the PostgreSQL `billing` schema's tables: `ServiceWorkOrderCreationDaoImpl.java` joins `billing.m_billing_master`, `billing.t_bill_payee_details`, and `billing.t_billing_details` to resolve a work order's bill/payee/line-item details (6 findings, all empty `HibernateException`-then-`Exception` catches); `NewWorkOrderCreationDaoImpl.java` joins `billing.m_billing_master mbm on mbm.billing_master_id = request.bill_id` in at least three separate query-building methods to resolve the bill linked to a work-order request (40 findings, the largest single-file count in this audit, at lines 201-2140, plus the two `printStackTrace()`-only findings at 819/821). Criterion (d) as literally stated in this series ("import `com.param.billing.*`/`com.param.global.billing.*` directly, or call into a billing service/DTO") is framed around Java-level dependencies; this audit treats a DAO method's native SQL reading/joining the `billing` schema's core billing-master/bill-details tables as a materially equivalent, arguably stronger, form of "calling into billing" than an import statement, since it depends directly on billing's live data shape. This is flagged explicitly as an interpretive extension, not a literal reading of the criterion, for the owner's awareness — if the owner wants a narrower, Java-import-only definition applied retroactively, these 46 findings (2 files) would move from billing-critical to peripheral, but the underlying architectural coupling (procurement work orders reading billing's schema directly via raw SQL, bypassing any Java service boundary) is real either way and worth flagging on its own merits.
  - **File-level propagation rule** (same convention as every prior audit in this series): once a file meets any criterion, every finding in that file is billing-critical, not just the specific catch block that touches billing logic. This is why all 40 `NewWorkOrderCreationDaoImpl.java` findings are billing-critical even though only a handful of its query-building methods actually contain the `billing.m_billing_master` join — the rest of the file's catches are on the same class's other work-order-request CRUD methods.
- **The raw-vs-structural gap (579 raw `catch\s*(` matches vs. 561 structurally valid) is entirely dead/commented-out code, spread across 12 files** (up from 3 files in OTIMS, reflecting this module's larger size): `ConsignmentStockPOInvoiceServicesImpl.java` (2), `ConsignmentStockReturnService.java` (2), `ConsignmentStockReturnController.java` (1), `PurchaseRequestService.java` (1), `OtherChargesPOMapperDaoImpl.java` (2), `BonusUomMapperDaoImpl.java` (2), `PurchaseOrderUomMapperDaoImpl.java` (2), `PurchaseOrderController.java` (1), `PurchaseOrderApprovalController.java` (1), `WorkOrderNegotiationController.java` (1), `NewWorkOrderCreationController.java` (1, a commented-out trailing `//		} catch (Exception e) {` line), and `WorkOrderSelectionController.java` (2) — each manually opened and confirmed to be genuinely `/* ... */`-fenced (whole disabled endpoint methods, in most cases) rather than a parser miscount, before being excluded. Same scaffolding/dead-endpoint artifact noted in every prior audit in this series.
- **A new dominant sub-pattern, specific to Procurement, that did not appear at scale in any prior module: `catch (Exception ex) { return new ResponseEntity<>(new ErrorResponse(code, message, ex), HttpStatus...); }`.** 323 findings across 46 files — **63% of all findings in this module**, making it the dominant pattern here (versus empty-catch, which dominated every prior module and is "only" 130/515 = 25% of findings in Procurement). `ErrorResponse` (`legacy/Entity/src/main/java/com/param/common/dto/ErrorResponse.java`) is a shared DTO whose constructor calls `ex.printStackTrace(new PrintWriter(writer))` into a string field (`stackTrace`) and `ex.getMessage()` into another (`summary`) — meaning these catches capture the *full* stack trace and message into the HTTP response body, strictly richer than OTIMS's bare `e.getMessage()`-in-payload pattern (only 4 findings/2 files here: `PurchaseRequestController.java`, `ConsignmentStockReturnController.java`). Despite being richer, this is still classified `silent-swallow` per this series' own definition: there is no real logger call anywhere in this codebase (0/511 files), so the failure is never persisted server-side — only a client that specifically inspects the response body's `stackTrace`/`summary` fields ever sees the real cause, and nothing is written to any server-side log or monitoring system. One further, single occurrence (`PatientConsumptionService.java` line 1096) does `catch (Exception e) { return e; }` — returning the bare exception object itself (the enclosing method's return type evidently permits it) — classified the same way, with a distinct note.
- **`status-masks-failure`** (the bare `return null;` pattern) — **2 instances**, both peripheral: `GoodReceiptNoteDao.java` line 130 (`getDiscountTypeById`, silently returns `null` when a `DiscountType` lookup finds nothing, with a comment `// Handle the case when DiscountType with the given ID does not exist` — the comment itself, stripped during parsing, does not change the classification since it isn't a logger call) and `VendorNegotiationDao.java` line 192.
- **10 findings use `e.printStackTrace()` only (console, not persisted) and 1 uses `System.out.println(e)` only**, both classified `other` per this series' convention. The `printStackTrace()` findings are in `ImplantReturnAcceptanceController.java`, `GoodReceiptNoteController.java`, `GoodReceiptNoteDao.java` (×2), `PurchaseRequestApprovalDao.java`, `VendorSelectionController.java`, `PhysicalInspectionService.java`, and `NewWorkOrderCreationDaoImpl.java` (×2, the only overlap with the billing-critical raw-SQL file). The single `System.out.println(e)` finding is in `BarcodeDao.java` line 291 — same defect noted in the OTIMS audit (no stack trace at all, console-only, not persisted).
- **Multi-catch clauses** (`catch (TypeA | TypeB e)`) — **zero** occurred in this module, same as every prior audit in this series.
- **The DAO layer's `HibernateException`-then-`Exception` double-catch pattern is dominant among the empty-catch findings**, same shape as every prior audit: nearly every DAO method across `NewWorkOrderCreationDaoImpl`, `ServiceWorkOrderCreationDaoImpl`, `PhysicalInspectionDao`, `ConsignmentReturnDao`, `ConsignmentStockReturnDao`, `GoodReceiptNoteDao`, and others follows `catch (HibernateException he) { } catch (Exception e) { }`, both clauses empty — almost certainly a single copy-pasted DAO template, not independently-written bugs, the same conclusion as every prior module.
- **91 of the 511 files are pure interfaces** (`IConsignmentStockPOInvoiceDao.java`, `IVendorServiceRateConfigDao`-style names, etc.) with zero catch blocks by construction, verified by the same "second character uppercase" convention used in the OTIMS audit — not double-counted as clean implementation files. A naive `I*.java` filename glob overcounts to 132, because 41 non-interface implementation classes and DTOs also happen to start with the letter `I` in this module (considerably more than OTIMS's 4, because Procurement has large `Implant*` and `ItemRequest*`/`ItemResponse*` feature families — e.g. `ImplantReturnAcceptanceController.java`, `ImplantIndentService.java`, `ItemRequestDto.java`, `ItemResponse.java`); all 91 files matched by the correct convention were spot-verified to actually contain an `interface` keyword declaration, with zero exceptions.
- **341 of the 420 non-interface implementation files (81%) have zero findings** — of these, 331 have no catch blocks at all (pure DTOs, JPA entities, mappers, request/response POJOs — the module's dominant file shape, since Procurement has an unusually large DTO surface for its controller/service/DAO count), and **10 have catch blocks where every single one properly rethrows** — a small, positive counter-example pattern, worth the owner's awareness the same way OTIMS flagged 3 such files: `BonusUomMapperDaoImpl.java`, `OtherChargesPOMapperDaoImpl.java`, `PurchaseOrderDetailsDaoImpl.java`, `PurchaseOrderUomMapperDaoImpl.java`, `LocalPurchaseRequestService.java`, `LocalPurchaseRequestApprovalService.java`, `PurchaseRequestService.java`, `PurchaseRequestApprovalService.java`, `WorkOrderQEntryDao.java`, and `WorkOrderQEntryService.java`.
- **Scope has no `src/test/java` directory** — same as CSSDMaster, Pharmacy, DietAndKitchen, and OTIMS — all 511 files are `src/main/java`.
- **The parser is structural, not control-flow-aware**, identical caveat to every prior audit in this series: a catch block containing `throw` anywhere in its body is treated as "properly rethrows" and excluded, even if a nested conditional path could still silently fall through without throwing.
- This audit does **not** re-scan `legacy/Billing`, `legacy/Global`, `legacy/ADT`, `legacy/BloodBank`, `legacy/CSSDMaster`, `legacy/Pharmacy`, `legacy/DietAndKitchen`, `legacy/OTIMS`, `legacy/Entity`, or any other module — it is Procurement-only, matching this task's scope. In particular, it does not audit `legacy/Global/src/main/java/com/param/global/billing/*` (the real billing DTOs/DAOs referenced above) or `legacy/Entity/src/main/java/com/param/common/dto/ErrorResponse.java` (the shared response DTO whose constructor behavior is described above) — both are read-only reference lookups to explain Procurement's own findings, not part of this audit's scanned file set.
