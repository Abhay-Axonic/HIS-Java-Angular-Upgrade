# DB/SQL Risk Audit — Legacy Codebase

*Read-only audit, 2026-07-04. Part of the whole-codebase optimization-readiness audit (see also: AUDIT_WholeCodebase_patterns.md, AUDIT_TestCoverage.md, AUDIT_JavaUpgradeBlockers.md, AUDIT_Angular18Blockers.md, AUDIT_BillingRisk.md). No code, SQL, or config was changed. Per CLAUDE.md, Phase 2 (DB verification/optimization) happens only after exception handling is fixed, and per RULES.md all DB changes follow Expand-Migrate-Contract — so this is preparatory research only; no remediation is proposed here.*

This is a read-only, research-only pass across `legacy/` (all modules — Billing, Global, ADT, LIS, Pharmacy, Inventory, Procurement, BloodBank, AssetManagement, OTIMS, DietAndKitchen, CSSDMaster, Abdm, HIS-WAR, LinenLaundry) plus the raw DDL under `legacy/Database/`. `legacy-codewhale-attempt/` was not re-audited — per docs/BUSINESS_RULE_MANIFEST.md (BR-004) it is an existing reference/baseline copy of the same code, not a separate live path. Findings are grouped by root-cause pattern, ranked by (count × severity), with true one-offs called out separately.

## Ranked risk patterns

### 1. SQL/HQL built by string concatenation (SQL-injection-shaped) — systemic, highest count
- 620 files across the codebase call `.createQuery(`, `.createSQLQuery(`, or `.createNativeQuery(` at all; 906 files use the safe parameterized style (`setParameter`/`setString`/`setLong`/`setInteger`), so parameterization is the *majority* pattern.
- However, 363 call sites concatenate a variable directly inside the `createQuery(...)`/`createSQLQuery(...)` argument list, and 451 files declare a `hql`/`sql`/`query` string variable built via `+`/`+=` concatenation before passing it to Hibernate.
- Narrowing to the classic injection signature — a variable spliced between two string literals, `"...WHERE x=' " + var + " '..."` — 124 files / 164 lines match, concentrated in `Billing` (largest single contributor, e.g. `MCompanyInvoiceMasterDaoImpl.java`, `BillingMasterDaoImpl.java`, `InterimHandoverMasterDaoImpl.java`, `CompanyContractDaoImpl.java`, `TDoctorShareDaoImpl.java`), then `Global`, `ADT`, `LIS`, `Abdm`, `HIS-WAR`.
- Confirmed user/business-input-reachable examples (not just internal constants):
  - `BloodBankStockDetailsDaoImpl.java:111` — `createSQLQuery(" update blood_bank.t_blood_red_cell set blood_confirmation_status = 6 where red_cell_id = "+redCellId+" ")` — a raw SQL **UPDATE** with an unparameterized ID.
  - `ConsignmentStockPOInvoiceDaoImpl.java:307` — `invoiceNumber` spliced into a WHERE clause.
  - `AbdmCredentialDaoImpl.java` (multiple sites) — `genderId`, `organization_id`, and a `consent_id` value spliced into UPDATE/WHERE clauses.
  - `BatchDaoImpl.java:51,152` — `date`/`timeZone` spliced into WHERE clauses.
  - `PatientRegistrationDaoImpl.java:3041` — `"select * from patient_master pmd where patient_code ='"+patientRegistrationDto.getUhidNumber()+"'"` — patient UHID (user-supplied lookup key) concatenated directly into a `SELECT *`, combining this pattern with finding #4 below.
  - `GlobalOrganisationMasterDaoImpl.java:322-327` — see one-off below: uses `PreparedStatement` but still concatenates a lowercased/trimmed `orgName` directly into the SQL text instead of using a bind parameter, which defeats the purpose of `PreparedStatement` entirely.

### 2. Missing/inconsistent transaction boundaries around multi-step writes — high severity, uneven coverage
- `@Transactional` is present somewhere in 898 files codebase-wide, but coverage is very uneven by module (files with `@Transactional` anywhere / total `*ServiceImpl.java` files):
  - LIS 80/87 (92%), CSSDMaster 15/15 (100%), Procurement 3/3 (100%), Billing 49/67 (73%) — reasonably covered.
  - Global 116/278 (42%), BloodBank 12/30 (40%), Pharmacy 3/8 (38%), DietAndKitchen 5/14 (36%), OTIMS 2/13 (15%), ADT 12/68 (18%), AssetManagement 1/5 (20%) — large gaps.
- At the DAO layer specifically, 11 `Billing` DAO implementation files each contain 2+ direct Hibernate `save`/`saveOrUpdate` calls (candidate multi-write sequences) and **none** of the 11 have `@Transactional` anywhere in the file — meaning any transaction demarcation for these, if it exists, must come entirely from a caller several layers up, which was not verified here.
- As a positive control: `BillingMasterServiceImpl.collectPayment` and `.collectPaymentFromEncounter` — the payment-critical methods already flagged in BR-007/BR-008 — are both explicitly `@Transactional`, so the highest-risk payment path is covered. The gap pattern above is concentrated in the lower-profile modules/DAOs, not the audited billing payment flow.

### 3. Query-in-a-loop (N+1) pattern — medium severity, broad
- Of the files containing a `for (...)` loop inside a `*ServiceImpl.java`, 93 files have a DAO-method call within the first few lines of the loop body — a heuristic N+1 signature (a DAO round-trip per iteration rather than a single batched/joined query).
- JPA entity mappings themselves are not the main contributor here: only 2 explicit `FetchType.EAGER` declarations exist codebase-wide (both in `Entity`), and 813 `@OneToMany` associations rely on JPA's default (LAZY), so the N+1 risk is concentrated in hand-written loop-driven DAO calls rather than in eager collection mappings.

### 4. `SELECT *` in application code — lower severity, schema-fragility
- 17 occurrences across `Entity` (6, several as `@NamedNativeQuery` definitions calling into the billing package-consumption log functions and a prefix-number function), `Global` (4, including the injection-combined `PatientRegistrationDaoImpl.java:3041` line and a `UserRoleMapperDaoImpl.java` pair that wraps two dynamically-built UNION subqueries in `select * from (...)`), `LIS` (1, a `public static final String query = "SELECT * FROM ABC WHERE a=:a"` in `CommonUtils.java` — looks like leftover placeholder/test code), and `Billing` (1, `BillingMasterDaoImpl.java:4378`, a Tally-interface reconciliation query).

### 5. Raw JDBC `Statement`/misused `PreparedStatement` — small count, notable because of what it's paired with
- Only 8 `createStatement()` (non-prepared) call sites exist, in `GlobalServiceMapperServiceDaoImpl.java`, `OrderDetailsMasterDaoImpl.java`, `PatientRegistrationDaoImpl.java`, and `GlobalDao.java` — small in count, but the surrounding module (`Global`) is otherwise dominated by Hibernate, so these are outliers worth checking individually.
- 25 files use `PreparedStatement` correctly by name, but at least one of them (`GlobalOrganisationMasterDaoImpl.java`, see one-off below) builds the SQL text with concatenation before calling `prepareStatement(...)`, which negates the safety `PreparedStatement` would otherwise provide.

## One-off findings

**A. Hardcoded live database credentials and third-party secrets committed to the repo (security-critical, separate from the SQL-risk analysis above).**
- `legacy/devops/jdbc.<env>preprod.properties` — 10 files (`oysterpreprod`, `athaayupreprod`, `meditestpreprod`, `smepreprod`, `mrrchpreprod`, `queenspreprod`, `smetwopreprod`, `nchpreprod`, `hisqa`, `bpppreprod`), each with a live `jdbc.url` (host/IP + DB name), `jdbc.username`, and `jdbc.password` in plaintext or trivially-decoded base64 (e.g. `QXhvbmljQDIwMjQ=` → `Axonic@2024`).
- `legacy/HIS-WAR/src/main/resources/jdbc.properties` — same pattern for a live QA Postgres instance, plus a live Razorpay `key.id`/`secret.id` pair and an SMTP mail account password, all in plaintext.
- `legacy/Global/src/main/java/com/param/global/org/dao/GlobalOrganisationMasterDaoImpl.java:322-327` — a hardcoded production-looking AWS RDS connection string (`his-mumbai-rds....rds.amazonaws.com`) with a plaintext username/password embedded directly in Java source, combined with the `PreparedStatement`-defeated concatenation noted in pattern #1.
- `legacy/Billing/.../dao/BillingMasterDaoImpl.java:1134,1463,3652` — hardcoded MySQL connection to a separate "smartlink" smart-card interface database (`192.168.1.64:3307`) with a personal-looking developer credential (`"Vishal"`/`"Vishal"`).
- `legacy/Global/.../dao/PatientRegistrationDaoImpl.java:3671-3673` — a hardcoded Microsoft SQL Server connection string to an external host (`202.149.218.166`, database `shreedb`) using the SQL Server **`sa`** (built-in administrator) account with a plaintext password — the highest-privilege credential found in the audit, to what appears to be a third-party/partner system. **Correction (independent Checker review, 2026-07-04):** this entire method (`patientRegisterONP`, lines ~3666-3704) is wrapped in a block comment — it is dead, commented-out code, not an active runtime connection. The leaked credential is still a real disclosure (it sits in source/version-control history and could be live on the actual SQL Server regardless of whether this code path runs), but it is not currently being executed by the application.

**B. The core billing table's foreign keys are declared separately from its `CREATE TABLE` block, and are more complete than an inspection of that block alone suggests.** **Correction (independent Checker review, 2026-07-04): the original version of this finding claimed `billing.m_billing_master` had no FK constraints at all, including on `patient_id` — that claim is FALSE and has been replaced below.** The table's own `CREATE TABLE` statement in `legacy/Database/HIS-SME-DDL_20210430_150255584.sql` declares only `pk_billing_master_id PRIMARY KEY (billing_master_id)`, but a full-file search (not just the `CREATE TABLE` block) finds three `ALTER TABLE ONLY billing.m_billing_master ADD CONSTRAINT ...` statements roughly 103,000 lines later in the same dump: `fk_bill_status_id FOREIGN KEY (bill_status_id) REFERENCES billing.m_billing_status_master(bill_status_id)`, `fk_patient_id FOREIGN KEY (patient_id) REFERENCES patient.t_patient_registration(patient_id)`, and `fk_visit_type_id FOREIGN KEY (visit_type_id) REFERENCES public.m_visit_type_master(visit_type_id)`. So `patient_id`, `bill_status_id`, and `visit_type_id` **are** protected by real foreign keys. The narrower, verified finding: `encounter_id`, `unit_id`, `organisation_id`, `admission_id`, `counter_id`, `bill_cancel_by`, `bill_cancel_reason_id`, `old_bill_id`, `dr_note_against_billid`, `against_bill_id`, and `print_given_by` genuinely have no FK anywhere in the dump (re-confirmed by the same full-file search) — referential integrity for those specific columns is enforced only in application code, not the database.

**C. Financial amounts are widely typed `double precision` (floating point) rather than `numeric`/`decimal`.** Across the DDL dump, 462 columns whose names suggest money (`amount`/`amt`/`total`/`discount`/`tax`/`gst`/`price`/`balance`/`fee`/`charge`) are declared `double precision`, versus only 76 declared `numeric`. In `billing.m_billing_master` itself: `net_amount`, `discount_amount`, `total_bill_amount`, `outstanding`, `gst`, `concession_amount`, `round_off`, and `cr_amount` are all `double precision` and all nullable. This is a direct tension with `RULES.md`'s own circuit-breaker condition ("any invoice or billing amount differs from the legacy calculation by more than $0.01") — floating-point arithmetic on these columns is a structural source of exactly that class of discrepancy, independent of any application-code bug. (See also AUDIT_BillingRisk.md, which covers the application-layer `double`-for-currency counterpart of this same root cause.)

**D. Database-side triggers/functions duplicate or fully own billing/accounting business logic, invisible to the application layer ("two sources of truth").** `legacy/Database/Trigger.sql`, `Procedure.sql`, `Funcations.Sql`, `Views.sql`, and `Rollback.sql` are each effectively empty (1–22 bytes, placeholder/stub content only) — the actual current trigger/function/procedure definitions (20 triggers, 282 functions, 8 procedures — 302 total) live only inside the single 4.8 MB `HIS-SME-DDL_20210430_150255584.sql` dump, not in a reviewable per-object file. Within that dump:
  - `public.reset_balance_amount_trigger` / `reset_balance_amount_proc()` — a trigger function that silently caps `billing.m_preauth_master.balance_amount` to `authorized_amount` on update, i.e. it enforces a billing business rule (a balance can never exceed its authorization) directly in Postgres, independent of whatever validation the Java layer does.
  - `public.postbillrefund(dateoftrans)` — a large PL/pgSQL procedure that computes and inserts refund/payee-wise ledger entries into `public.t_tally_interface` (the Tally accounting export) by joining and summing across `m_credit_note_master`, `t_credit_note_detail`, `t_billing_details`, `m_billing_master`, and `t_payment_refund_master` — real financial aggregation logic that exists only in the database and is not visible to, or covered by, any Java service/test in `legacy/`.
  - `public.post_doc_share_data` / `postdocsharedata` / `advamount` / `orderedamountforadmittedpatient` — further billing-amount/doctor-share computation functions in the same category, alongside application-layer equivalents already known from `BillingMasterServiceImpl.java`/`TDoctorShareDaoImpl.java` — the two are not confirmed to agree because they were not diffed against each other in this audit.
