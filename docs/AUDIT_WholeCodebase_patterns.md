# Audit: Whole-Codebase Optimization-Readiness Patterns — legacy/ (all modules)

*Read-only audit, 2026-07-04. Part of the whole-codebase optimization-readiness audit (see also: AUDIT_TestCoverage.md, AUDIT_JavaUpgradeBlockers.md, AUDIT_Angular18Blockers.md, AUDIT_SQLRisk.md, AUDIT_BillingRisk.md — the plain-English "what to fix first" recommendation lives at the end of AUDIT_BillingRisk.md's companion summary in this doc set). No code was modified.*

**Scope:** every `.java` file under `legacy/` across all 17 Maven modules (Abdm, ADT, AngularSpring, AssetManagement, Billing, BloodBank, CSSDMaster, DietAndKitchen, Entity, Global, HIS-WAR, Inventory, LinenLaundry, LIS, OTIMS, Pharmacy, Procurement, RabbitMQ), plus `legacy/Database` (raw SQL) and `legacy/HIS-WAR/src/main/webapp` where relevant. Total: 8,256 `.java` files (`legacy/his-maven-jars` excluded as vendored binaries, not source).

**Method:** read-only. Real `grep`/`perl` searches run against the working tree, counts shown next to each finding are actual command output, not estimates. Each pattern below was spot-checked by reading 1–3 concrete hits to confirm the grep wasn't a false positive (confirmed cases are noted).

**Relationship to `docs/AUDIT_Billing_exceptions.md`:** that audit fully catalogued silent-swallow catch-block findings *inside* `legacy/Billing` (767 findings across 2,411 catch blocks in 558 files) and is not repeated here. Everything below is either (a) the same class of defect but in the other 16 modules, which that audit never touched, or (b) a materially different defect category (secrets, resource leaks, God classes, validation, duplication, etc.) that applies codebase-wide including Billing.

## One-offs

- **`legacy/Global/src/main/java/com/param/global/dao/PatientPOCMasterDaoImpl.java:202`** — a hardcoded literal `String API_KEY = "41194";` used inline in a DAO (not a controller/service), suggesting a static integration key baked directly into a data-access class rather than externalized config — worth flagging separately from the general "hardcoded secrets" cluster (#4) because of the unusual layer (DAO) it lives in, which may indicate the key is actually a lookup/reference-data ID misnamed as an "API_KEY" rather than a real secret; needs a human to confirm which it is before triage.
- **`legacy/ADT/src/main/java/com/param/adt/common/IMailConstants.java:9`** and **`legacy/Global/src/main/java/com/param/global/mail/IMailConstants.java:16`** — the *same* SMTP password (`"cht12345"`/`"Cht@12345"`, with the old value left commented out alongside it: `//"Cool1234"`) is duplicated in two modules' constants files. This is both a secret-in-source issue (#4) and a duplicate-file issue (#8) simultaneously, but the specific detail — a *previous* password value left in a comment right next to the *current* one — is a distinct disclosure risk (reveals credential-rotation history/pattern) worth calling out on its own.
- **`legacy/ADT/src/main/java/demo.java:39`** — a file literally named `demo.java` sitting in `src/main/java` (not `src/test`), containing `String password = "1234";`. This looks like a scratch/demo file that was never removed before commit and would compile into the production module. One-off because it's not a recurring shape — it's a single stray file that shouldn't exist in `src/main` at all.
- **`legacy/Abdm/src/main/java/com/param/AbdmCredentialDaoImpl.java`** at 25,382 lines is not just the largest God class (#6) — it's nearly 3x the size of the next-largest file in the entire codebase and lives in the `Abdm` module (India's Ayushman Bharat Digital Mission integration, external-govt-facing), meaning the module most exposed to an external national health API is also the single most unreviewable file in the repository. This combination of factors (external-facing + extreme size) elevates it above a routine God-class entry and probably warrants being the first item picked up when #6 is acted upon.
