## 1. `aiButtonConfiguration` — review first, given severity

**Paths:** `aiButtonConfiguration` (legacy state url `/aiButtonConfiguration`, controller `aiButtonConfugurationController.js` — real filename typo, missing the second "r"). **No `moduleId` gate on either app** — legacy's own `.state()` registration has no `resolve` block (confirmed via `states_enriched.json`, `has_resolve: false`), matching its sibling `aIButtonMaster`; the rebuild's route deliberately has no `canActivate` guard either, to match. Reachable to any logged-in user. Nav: "Ward/Unit Master" section, titled "AI Button Configuration", sitting directly under "AI Button Master" (`aIButtonMaster`, batch 10, same `button_master` table).

**Test data / environment note:** this dev DB (`his_local`) is **missing the `public.button_master_config` table entirely** (confirmed via direct `psql`, same class as this table's sibling gap already flagged for `button_master`) — every real Save on **both** apps genuinely fails server-side with a caught `HibernateException` in this environment. This blocks a full end-to-end Save round trip on either app here; it does not block exercising every other part of the screen (dropdown loads, config-fetch, the two-step edit flow, the redundant-column display, and — usefully — the exact failure-handling behavior this screen's most important findings are about). Because DOM clicks are unreliable on this legacy app per this project's standing practice, the live verification behind the findings below used direct `$scope.$apply`/scope-method calls on legacy and `ng.getComponent`/direct method calls on the rebuild, with a patched `XMLHttpRequest.prototype.send` (legacy) / patched service method (rebuild) to capture exact outgoing payloads — not a plain click-through. If you want to reproduce the findings yourself with real DOM clicks, expect the same real POST failures described below on both apps until `button_master_config` exists in this environment.

**Needs your explicit sign-off on — SEVERITY-1, most important item in this whole checklist:**
- **`BR-PENDING-aibuttonconfiguration-stale-configid` — Save can silently overwrite an unrelated, previously-saved config instead of creating a new one.** Legacy's `$scope.configId` is set exactly once, inside `editButtonMaster`, and is **never reset anywhere else in the controller**. Live-verified on real, unmodified legacy: edit config A (its `configId`, e.g. 555, gets captured) → save → **without ever calling `editButtonMaster` again**, switch to a genuinely new, unrelated Doctor+Button combination and Save — the outgoing POST **still carries `configId:555`**. Since `UserRoleMasterDaoImpl.saveConfig` branches purely on `configId != null`, this silently **UPDATEs/overwrites config #555** instead of inserting a new row, and a completely ordinary "Updated successfully" toast fires, giving no indication that a different, previously-saved, unrelated record was just clobbered. **Fixed in the rebuild** — `saveConfig()` always computes the outgoing `configId` as `this.editFlag() ? this.configId : null` at send time, never trusting a leftover field. **Also fixed in legacy itself**, independently: `fix/aibuttonconfiguration-stale-configid-silent-overwrite` (commit `7872b3b6`) has been reviewed, approved, and merged into `main` (merge commit `c649f1e5`) — `getDoctorChange`/`getSpecialityChange`/`setButton` now reset `configId`/`editFlag` on every genuinely fresh selection (closing both the originally-reported bug and a second bypass found during review: abandoning an edit via the modal's Cancel/X, which never touched scope state at all, then picking fresh criteria). What you're approving in *this* checklist is only whether the rebuild's own client-side correction is acceptable to ship as part of batch 25 — the legacy side is already resolved and merged, separately.
- **`BR-PENDING-aibuttonconfiguration-silent-save-failure` (Pending, no separate urgency)**: legacy's `saveConfig()` shows a toast only on success; both its failure branch and its `.catch(){}` are completely empty — live-verified (forced via this dev DB's own missing-table failure) zero DOM feedback of any kind. Fixed in the rebuild only: any non-success response or HTTP error now shows a real error toast.
- **`BR-PENDING-aibuttonconfiguration-tag-checkbox-desync` (Pending, no separate urgency)**: the 4 tag checkboxes are visually driven by flags `editButtonMaster` sets and never resets (PatientName isn't even read from the record at all), while what's actually persisted is driven by a completely separate, never-synchronized, controller-lifetime array — live-verified a checked `@Gender` tag silently vanishing from a Save that never touched the checkbox, and the inverse leak (a tag checked once staying set and leaking into a later, unrelated record). Fixed in the rebuild only: flags are derived fresh from the record on every edit-open, rebuilt fresh at save time.
- **Faithful reproduction, no action needed**: redundant Configuration-Name/Button columns; CREATE-only duplicate-name/speciality guard (a real `growl.error` fires, but the create form still fully resets as if it had succeeded); unconditional server-side `status='A'` reset on every save (editing a deactivated config silently reactivates it — backend Java behavior, out of scope for this Angular-only rebuild); two-step pencil-then-gear edit flow; misdirected `statusChanged` dropdown-reload instead of table-reload.
- **Environment gap, not a bug, awareness only**: `public.button_master_config` doesn't exist in this dev DB, blocking a full real Save round trip on either app equally. Not fixed here (out of scope, same class as other local-dev-DB-drift entries); flag for whoever owns dev-environment schema completeness.
