# Decision Needed: `legacy/Entity` has no path to the centralized exception handler

**Status: Interim safe default applied to all 56 findings (2026-07-06) — logging added everywhere, nothing rethrown anywhere. Owner input wanted on the long-term architecture.**

## What this is about

Every prior module fixed in this exception-handling series (Billing, Global, ADT, BloodBank, CSSDMaster, Pharmacy, DietAndKitchen, OTIMS, Abdm, HIS-WAR, Procurement, AssetManagement, Inventory, LIS) used the same mechanical fix for a silently-swallowed catch: add a `log4j` logger, then `throw new ServiceException(e.getMessage())`. `ServiceException` (`com.param.global.common.ServiceException`, in `legacy/Global`) is a `RuntimeException`, and `legacy/Global`'s `BillingExceptionController` (`@ControllerAdvice`) has a `@ExceptionHandler(ServiceException.class)` that turns it into a clean HTTP 500 with a logged root cause — the "centralized global exception handler" `CLAUDE.md`/`RULES.md` require every error to reach.

`legacy/Entity` cannot use that fix. Two separate blockers, discovered while fixing `docs/AUDIT_Entity_exceptions.md`'s 56 findings:

1. **`legacy/Entity` has no dependency on `legacy/Global`** (confirmed: `Entity/pom.xml` has zero references to the `Global` artifact). `Global` depends on `Entity`, not the other way around — `Entity` is the more foundational module. Importing `com.param.global.common.ServiceException` from Entity code would require a dependency Maven can't satisfy without introducing a cycle (`Entity → Global → Entity`).
2. **`legacy/Entity` has no logging framework at all** — no `log4j`, no `slf4j`, nothing declared in its `pom.xml`. Every prior module already had (or could add) a `log4j` `Logger` field for free; Entity cannot import `org.apache.log4j.Logger` either.

This isn't a one-off — it affects **all 56 findings across all 12 catch-bearing files in this module**, not just the 41 billing-critical ones in `GlobalCommonDateUtils.java`/`TimeZoneComponent.java`/`MpesaUtility.java`. Every file in Entity is in the same boat.

There's a second reason to be more careful here than in any prior module: **blast radius**. `GlobalCommonDateUtils.java` alone is imported by 78 files in `legacy/Billing` and 331 files in `legacy/Global` (per the audit's reverse-import count); `TimeZoneComponent.java` by 90 + 232. These are static date/timezone utility methods called deep inside other methods' bodies across the whole app — not outermost Controller/Service methods that already return a `Response`/`CommonResponse` status object. Converting all 41 billing-critical catches to an unconditional `throw` (even if a compatible exception type existed) would, for the first time in this series, risk introducing a *new* unhandled exception in the middle of otherwise-successful billing computations across hundreds of call sites that have never been individually audited for how they'd react to that. Every other module's fix stayed inside a single Controller/Service/DAO method's own error-response contract; this one would ripple outward through code this task's scope never touched.

## What was done (interim, applied without further owner sign-off)

All 56 catches now log the real exception — using `java.util.logging.Logger` (JDK built-in, needs no new dependency) — instead of being silently discarded. Nothing was converted to a `throw`; every method's existing return-value/control-flow behavior (return `null`, return a partial/default value, fall through) is completely unchanged. This is a strict improvement (every one of these failures is now visible somewhere, where previously all 56 vanished with zero trace) with **zero change to any method's observable behavior** — the same "log-only, no behavior change" interim standard already used for the batch-continuation cases in `docs/DECISION_NEEDED_HISWAR_BatchContinuation.md`, `docs/DECISION_NEEDED_LoanInOutService_ApproveBatchContinuation.md`, and `docs/DECISION_NEEDED_WitnessApprovalService_BatchContinuation.md` — just triggered here by an architectural gap instead of a batch-continuation risk. No compile changes were needed elsewhere; this module's own build is green.

One caveat on this interim step, so it isn't relied on more than it should be: `java.util.logging` output isn't wired into whatever aggregates `log4j` output for the rest of the app (if anything does) — these 56 log lines go to the JVM's default JUL handlers, not necessarily the same place `logger.error(...)` calls in every other module land. This is still strictly better than "nowhere at all," but the owner should know it isn't the same centralized-log destination as everywhere else until Option B or C below is chosen.

## What we still need from you

- **Option A (current interim default):** keep logging only, no throwing, permanently. Entity's 56 findings stay visible in logs but never reach `BillingExceptionController`. Lowest risk, but the mission's "no error may be silently swallowed, ever, anywhere" rule is only half-satisfied (visible, but not routed to the centralized handler) for this one module, indefinitely.
- **Option B — give Entity its own lightweight unchecked exception + extend `BillingExceptionController`:** define a small `RuntimeException` subclass inside Entity itself (no new dependency needed, since `RuntimeException` is `java.lang`), then add one new `@ExceptionHandler` clause to `legacy/Global`'s `BillingExceptionController` for it. This is the architecturally cleanest fix and satisfies the routing requirement literally, but it's a change to a shared, already-relied-upon file outside this module's scope, and touches how every currently-uncaught exception from Entity-originated code would surface — worth its own review before any of the 56 catches are converted to throw.
- **Option C — add `legacy/Entity` as a dependency of nothing, and instead have each of Entity's 400+ *callers* wrap their own call sites** in a try/catch that logs and rethrows `ServiceException` at the call site (in `Global`/`Billing`, where `ServiceException` is already available) — pushing the fix outward instead of inward. This avoids any change to Entity or to `BillingExceptionController`, but means auditing and fixing potentially hundreds of call sites instead of 12 files, and two of those call sites (`GlobalCommonDateUtils`/`TimeZoneComponent`) are used so pervasively that this could be a larger effort than every other module's fix combined.
- **Option D — do nothing further, accept Option A as permanent policy specifically for foundational/shared-utility modules** (Entity, and potentially any future module in the same architectural position), on the reasoning that these are qualitatively different from Controller/Service/DAO layers and the existing per-module `@ControllerAdvice` pattern was never designed to reach this deep into the call stack anyway.

No further code changes will be made here until you choose, beyond what's already applied (logging added everywhere, behavior otherwise unchanged in all 56 locations).
