# Decision Needed: GlobalOrganisationMaster's list-all and bulk-provisioning endpoints remain unscoped after BR-132 — deliberately not stopgapped, need an actual authorization-model decision

**Prepared:** 2026-07-31, found during the Phase 1 org/unit-trust sweep and BR-132's fix of `GlobalOrganisationMasterDaoImpl`'s record-level endpoints. No further application code has been touched to produce this document beyond what BR-132 already fixed — investigation and options only.

**Headline — BR-132 fixed every endpoint in `OrganizationMasterController` that acts on ONE specific, already-existing organization record identified by a client-supplied id (`updateOrganizationStatus`, `updateOrganizationMaster`, `getOrganizationById`, `saveOrganizationImage`/`updateImagePath`). Three things in the same controller were deliberately left out, because the same "clamp to the caller's own verified org" fix either doesn't apply to their shape or would break their stated purpose. They remain exactly as insecure as everything else was before tonight's fixes — this document exists so that gap isn't silently forgotten.**

---

## 1. What's still open, and why each one didn't fit BR-132's fix

**`GET /createorgfoldermanually` and `GET /createunitfoldermanually`** (`OrganizationMasterController.java:166-223`) — bulk utility endpoints. Each iterates `getActiveOrganizationList()`/`getActiveUnitListForFolderCreation()` (every active org/unit in the system, unfiltered) and calls `bucketUtility.create(...)` + `updateOrganizationFolderPath`/`updateFolderPath` for every single one in a loop. There is no request body, no target id — the endpoint's entire purpose is to operate across every tenant in one call. Structurally, "clamp organizationId to the caller's own org" doesn't apply here; doing so would make the loop iterate a list of one (the caller's own org) and defeat the endpoint's actual job (backfilling folders for orgs that don't have one yet, system-wide). Currently: **any authenticated user, from any org, can trigger either of these** — there is no role check, and no scoping check would even make sense as a fix given the endpoint's design.

**`GET /allArganizationList/{offSet}/{noOfRecords}` and `GET /organization/active`** — list-all-organizations reads. Both return every organization in the system (name, address, contact, etc.) to any authenticated caller, regardless of org. Lower severity than the record-level write findings BR-132 closed (read-only, no single-org semantics to scope to — the endpoint's contract is "list everything"), but still a real cross-tenant disclosure: any hospital's own staff account can currently enumerate every other hospital tenant's organization-level contact/address details on this platform.

**`POST /organization/save`** (`saveOrganizationMaster`) — creates a brand-new organization (a new tenant), including auto-provisioning a `SuperAdmin` user for it with a hardcoded password (`"Axonic@1111&"`, `GlobalOrganizationMasterServiceImpl.java:138`, flagged here for awareness — a separate concern from this document's IDOR scope, not a decision covered by this file). There is no existing target record to compare a new organization's id against, so "clamp to caller's own org" is not a meaningful fix shape — but there is also currently no authorization check of any kind gating who may call this endpoint and mint a new tenant.

## 2. The underlying gap, common to all three

Investigated directly during BR-132: `isSuperUser` — the only candidate role marker on `UserMaster`/`UnitMaster` — is stored but **never read or enforced anywhere** in the Java backend. There is no mechanism, broken or otherwise, that currently distinguishes a "platform administrator" (someone who should legitimately manage/onboard organizations across the whole system) from a regular hospital org's own local admin. All three endpoints above are reachable by any authenticated user today, with zero role gate.

This is the same root gap that made `updateOrganizationStatus` (BR-132) severe, but the fix shape is different: BR-132's fix works because "the caller should only affect their own org" is unambiguously the correct rule for a record-level operation. For these three, "only affect your own org" is either impossible to apply (the bulk utilities, by design, must touch every org) or arguably wrong (list-all and org-creation may legitimately need to remain available to *some* class of user broader than "just their own tenant" — that's exactly the undefined "platform admin" concept this document is asking about).

## 3. What has and hasn't been verified

- **Confirmed via direct source read:** all three endpoints' code paths, the absence of any `isSuperUser`/role check anywhere in `OrganizationMasterController`, `GlobalOrganizationMasterServiceImpl`, or the JWT/filter chain for these specific routes.
- **Not live-exploited separately** — the underlying "any authenticated user can call this" fact is already established by BR-132's investigation of the same controller (`isSuperUser` unused, no role gate), not re-demonstrated here with fresh attack traffic, since the conclusion (no check exists) doesn't need a live proof beyond the source read.
- **Not checked:** whether any OTHER controller in the codebase has a working, enforced role-check pattern that could be reused here (e.g., a `@PreAuthorize`-style gate used correctly elsewhere) — if one exists, it would substantially change the proposed-fix section below from "design a new concept" to "wire up an existing one. Worth a quick check before Phase 2 scoping this."

## 4. Options for the owner

1. **Define a real "platform admin" concept and gate all three on it.** Requires a decision on what that means concretely — a new `is_platform_admin` flag on `UserMaster` actually enforced by a filter/interceptor, or reusing/fixing `isSuperUser` to actually mean something, or an entirely separate authentication surface for platform operations (e.g., a distinct login flow/token scope). This is real authorization-model design work, not a copy of tonight's `VerifiedIdentityService` stopgap pattern — flagging so it's sized correctly relative to everything else in the Phase 2 queue.
2. **Interim stopgap for the two list-read endpoints only**, leaving the bulk utilities and org-creation open: clamp `allArganizationList`/`organization/active` to return only the caller's own org (closes the read-disclosure at the cost of breaking any legitimate current use of that screen as a multi-org list — same tradeoff BR-132 avoided applying to the record-level endpoints, but arguably more acceptable here since it's read-only and reversible once real role-gating exists).
3. **Hold all three, logged as a known gap**, tracked alongside the rest of the "not yet modeled" authorization surface (same bucket as this document's own headline gap) until Phase 2's broader authorization-model work addresses it deliberately, rather than three more one-off patches.

No fix has been proposed or implemented beyond the analysis above. Given this needs an actual design decision the same way `updateOrganizationStatus` initially seemed to (before investigation showed that one had a clean, low-risk fix available) — recommend option 3 for now, revisited explicitly once Phase 2's authorization-model sizing is on the table, rather than patched ad hoc alongside unrelated fixes.
