# Decision Needed: ScheduledLogsScheduler.java — Batch-Continuation Risk

**Status:** Pending owner decision — 2026-07-06 (interim safe-default fix already applied, see below)
**Related:** `docs/AUDIT_Global_exceptions.md` (14 peripheral findings), `docs/REVIEW_global-peripheral-exceptions.md`, `docs/BUSINESS_RULE_MANIFEST.md` BR-PENDING-global-peripheral-exceptions
**Precedent:** HIS-WAR's `MidNightBatchWithTimeZone.java`/`BatchDaoImpl.java` (BR-029, `docs/DECISION_NEEDED_HISWAR_BatchContinuation.md`), Procurement's `LoanInOutService.approveLoanInOut` (`docs/DECISION_NEEDED_LoanInOutService_ApproveBatchContinuation.md`), Inventory's `WitnessApprovalService.updateWitnessApproval` (`docs/DECISION_NEEDED_WitnessApprovalService_BatchContinuation.md`)

## Why this is held back

`ScheduledLogsScheduler.java` is the only file in the entire 8,040-finding peripheral audit whose class carries `@Scheduled` methods (confirmed by cross-checking the audit's finding-file list against every `@Scheduled`-annotated class in `legacy/Global`). It has 14 findings, all originally empty/`printStackTrace()`-only catches, and every one of them sits in a position where converting to the standard `throw new ServiceException(...)` fix would create a **worse** regression than the batch-continuation pattern seen in prior modules — not just "abort the rest of the loop," but **permanently disable the entire scheduled job**.

### The two @Scheduled methods

1. **`syncSchedulingLogs()`** (`@Scheduled(fixedDelay = 120000, initialDelay = 60000)`) — runs every 2 minutes. It uses a static guard flag, `isExecuted`, set to `'Y'` at the top of the method body and reset to `'N'` only at the very end of the `try` block, **after** the `for (ScheduleLogsResDto logsDto : listScheduleLogsDto)` loop over every pending sync record completes normally. There is no `finally` block.
   - **12 of the 14 findings** (lines for `PATIENT_MASTER`, `MODALITY_MASTER`, `UNIT_MASTER`, `ORGANIZATION_MASTER`, `DOCTOR_MASTER`, `APPOINTMENT_MASTER`, `DOCTOR_SCHEDULE`, `DOCTOR_CHARGES`, `ADMISSION_DETAILS`, `APPOINTMENT_DETAILS`, `PATIENT_DOCUMENT_MAPPER`, `PATIENT_KIN_DETAILS`) are each a `switch`-case's own inner `try/catch`, one per pending record, inside that same `for` loop. This is a textbook batch-continuation risk: converting any one of these to `throw` would abort the `for` loop on the first bad record in a run, leaving every *other* pending record in that batch unsynced.
   - **Worse:** because `isExecuted` is only reset to `'N'` after the loop finishes without exception, a thrown exception from inside the loop would leave `isExecuted` stuck at `'Y'` forever — the `if (isExecuted == 'N')` guard at the top of every future invocation would then never pass again, and the sync job would silently stop running entirely until the application is restarted. This is a pre-existing latent bug in the guard's `finally`-less design, unrelated to this fix, but it means the blast radius of "just add a throw" here is not "skip some records," it's "the whole real-time HIS↔MyLife sync feature quietly dies until someone restarts the app" — with no error surfaced anywhere, since nothing downstream is watching for a scheduled job that stopped running.
   - The remaining **1 of these 12** is the method's own outer catch (wraps the entire `try`, including the loop) — same `isExecuted`-stuck risk applies to it directly.

2. **`syncPathalogyReport()`** (`@Scheduled(fixedDelay = 120000, initialDelay = 60000)`) — the **14th finding** is this method's own outer catch. It uses an analogous static guard, `isLabReportSync`, with the identical reset-only-on-normal-completion pattern. Unlike `syncSchedulingLogs`, this method does not loop per-record with its own try/catch (the whole batch is POSTed in one HTTP call), so it is "only" the stuck-flag risk, not also a mid-loop-abort risk — but the stuck-flag risk alone is enough to disable this job the same way.

## Interim fix already applied (no owner sign-off needed — matches HIS-WAR/Procurement/Inventory precedent)

Per this project's established practice for batch-continuation risk (BR-029, and the un-numbered Procurement/Inventory decisions), an interim **log-only** fix has already been applied to all 14 findings: a class-level `org.apache.log4j.Logger` was added, and every one of the 14 catch bodies now calls `logger.error(<context>, e)` — but **no catch was converted to `throw`, and no control flow changed**. Every sync failure is now visible in the centralized log for the first time (previously: 12 silently discarded, 2 `printStackTrace()`-only), while the existing swallow-and-continue behavior (and the existing, separate `isExecuted`/`isLabReportSync` stuck-flag latent bug) is preserved exactly as today. This is a Refactoring (Safe) change — no caller-visible or scheduler-visible behavior differs — logging was added, nothing else.

## What still needs an owner decision

The standard `throw`-based fix is **not** recommended as-is for any of these 14 findings, for the reasons above. Two independent things would need to happen before a "real" fix (one that actually surfaces a hard failure instead of only a log line) is safe here:

1. **Fix the stuck-flag bug first, separately.** Wrap the guard-reset (`isExecuted = 'N'` / `isLabReportSync = 'N'`) in a `finally` block so it always resets regardless of how the try block exits — this is a pre-existing bug independent of this exception-handling audit, but it must be fixed before converting any catch in these methods to `throw`, or every thrown exception reintroduces the "job dies until restart" risk this decision doc is about.
2. **Then, separately decide per-catch whether to convert to `throw`:**
   - For the 12 per-record catches inside `syncSchedulingLogs`'s loop: even with the `finally` fix in place, a `throw` still aborts processing of every other pending record in that 2-minute run (they'd simply be retried on the *next* run 2 minutes later, since they'd remain marked pending — worth confirming that's true by checking `markScheduleLogsCompleted`/`markScheduleLogsError` are the only state transitions and nothing else assumes single-attempt processing). If confirmed, throwing may be acceptable once the flag bug is fixed, since the retry-on-next-run behavior bounds the damage to a 2-minute delay per affected record rather than losing it entirely.
   - For the 2 outer-catch findings: converting these to `throw` is comparatively low-risk once the `finally` fix lands, since there is nothing calling these `@Scheduled` methods synchronously — Spring's scheduler will simply log the exception itself and try again on the next `fixedDelay` tick.

No code beyond the interim logging change has been touched. This file is intentionally excluded from every parallel fix batch in this cycle.
