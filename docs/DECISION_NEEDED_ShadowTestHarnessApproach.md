## 2. Harness approach: **(c) both, split by what each component actually needs** — not a coin flip between (a) and (b)

**Recommendation: characterization tests for the calculation *engine* (Rank 1-4 above), record/replay reserved for the *system-level* save-bill integrity check (Rank 5) and cross-cutting regression once the harness exists — and record/replay cannot start today regardless, for a reason that needs your decision, not mine.**

### Why characterization tests first, and why they're feasible right now

- Ranks 1-4 are all clean-signature service methods (`Response method(SomeReqDto)`) with **no Spring context, no HTTP request, no session state required to call directly** — confirmed by reading the actual method signatures, not assumed. That means a characterization test is literally: construct a `BillPaymentCollectionReqDto`/`ContractConsumptionDto` by hand (or via a small builder), call the real method against a real Hibernate session pointed at a disposable Postgres schema, and snapshot the output.
- Zero of the 18 modules have a real test today (`AUDIT_TestCoverage.md`: 2 modules have the unmodified `mvn archetype:generate` stub, 16 have nothing), and CI passes `-Dmaven.test.skip=true` on every build path — so there is no existing test debt to reconcile, no flaky suite to inherit, and nothing currently gates deploys on tests passing or failing. This is a clean slate, which favors starting with the fast, deterministic, engineer-authored form (characterization) over the slower, harder-to-triage form (replay) as the *first* increment.
- Characterization tests double as the **documentation this codebase doesn't have anywhere else**: `docs/GLOSSARY.json`'s money-term definitions (`net_amount`, `due_amount`, `self_payable`, `credit_payable`, `available_deposit`, `available_cap`) are all currently `status: "proposed"`, inferred from field names, not confirmed. A characterization test that pins "given these inputs, `collectPayment` currently returns this `dueAmount`" is the fastest way to turn a proposed glossary definition into a confirmed one — run it, read the actual output, ask you to confirm it's what the term is supposed to mean.

### Why record/replay against real historical data is the *second* wave, not skippable, but also not startable today

RULES.md item 2 says "shadow testing with real historical transactions" — that's not optional, and characterization tests alone don't satisfy it, because hand-picked inputs can't be trusted to cover the *actual* input distribution this system has seen in production (edge cases nobody thought to write by hand: a real deposit that was partially consumed three different ways before a refund, a real contract with a second-round co-pay split against a cap that was already 98% exhausted, etc.). Record/replay is exactly the right tool for that — but two things block starting it today, and both are decisions for you, not something I can resolve by re-verifying code:

1. **No real historical transaction data is reachable from here.** The local dev Postgres is seeded synthetic/test data only (`docs/LOCAL_DEV_SETUP_NOTES.md`, and the session-log trail of BR-079 through BR-086 master-data seeding — all additive `INSERT`s of structural lookup data, not real patient/billing history). There is no production or staging DB connection available in this environment, and standing one up means a real data-access decision (PHI/compliance scope, read replica vs. export, anonymization requirements) that only you can make.
2. **Even once real data is reachable, "replay" needs a byte-identical *comparison* target, and the current legacy behavior includes known bugs that would poison a naive replay** — see Part 3 below. Recording real historical outputs and replaying them against a *new* implementation only tells you the new implementation matches legacy *if* you've already decided which of legacy's quirks (RISK-1's drift, ONE-OFF-2's ±1.00 tolerance, RISK-5's silent `Math.abs`) are being preserved on purpose vs. fixed on purpose. That triage is exactly what `AUDIT_BillingRisk.md`'s "what must happen before RISK-1/2/4 are touched" sequencing already calls for — this document doesn't re-litigate that audit's sequencing, it assumes it.

**So, concretely, proposed sequencing:**
1. **Now:** characterization tests against Ranks 1-4, using hand-constructed inputs plus the *existing* seeded local-dev data as a source of realistic-shaped (if not historically-real) fixtures. This is scoped, startable immediately, and needs no new access grant.
2. **Your decision needed, in parallel:** whether/how to get read access to a real (anonymized or scoped) historical transaction sample, for record/replay. Until that's decided, item 1 proceeds without being blocked by it.
3. **Once both exist:** record/replay runs the *same* characterized entry points against real historical inputs, and any case where legacy behavior surprises the characterization tests (an input shape nobody hand-wrote) becomes a new characterization test — closing the loop, not a one-time run.
4. **RULES.md's named synthetic edge cases** (month-end, fiscal quarter-end, Dec 31, Feb 29 leap year, timezone-shift variants) are characterization tests by construction (hand-constructed dates), not replay — they belong in wave 1 regardless of the data-access decision, and RISK-4 (zero-timezone-aware date handling, 180/180 unsafe formatter instantiations) makes them especially likely to catch something real.

## 3. What "byte-identical" verification actually means here — read before anyone writes a test

This has to be explicit up front because the honest answer is uncomfortable: **the harness cannot verify "nothing changed" against a mathematically correct ideal, because legacy never had one.** It can only verify "this specific implementation, with its specific floating-point rounding at its specific accumulation order, is reproduced bit-for-bit." That's a narrower, weirder claim than "byte-identical" usually implies, for three concrete, audit-confirmed reasons:

1. **The database columns themselves are `double precision`, not `numeric`.** `AUDIT_SQLRisk.md` (one-off C): 462 money-suggestive columns are `double precision` versus 76 `numeric`, including `net_amount`, `discount_amount`, `outstanding`, `gst`, `concession_amount`, `round_off`, and `cr_amount` on `billing.m_billing_master` itself. This means "byte-identical" cannot mean "matches to the cent" in a decimal sense — it has to mean **bit-identical IEEE 754 double reproduction**, because a value that's *decimally* correct but computed via a different operation order than legacy (even an operation order that's mathematically equivalent, like `(a+b)+c` vs `a+(b+c)`) can produce a different `double` bit pattern, and that difference is real and observable once stored.

2. **Four incompatible rounding rules already coexist in legacy, sometimes on the same value in the same method.** `AUDIT_BillingRisk.md` RISK-2, grep-verified: `BigDecimal.setScale(2, ROUND_HALF_EVEN)` (45 sites), `ROUND_HALF_UP` (1 site, but it's baked into a DTO setter so it fires on every assignment), `Math.round(x*100.0)/100.0` (15 sites), bare `Math.round(x)` with no `*100` scaling — i.e. rounding to the nearest **whole currency unit** (8 sites, all in `BillingMasterController.java`), and a `DecimalFormat("#.##")` format-then-reparse string round-trip (116 sites). The audit found `BillingMasterServiceImpl.java:1978` rounding `dueAmount` one way and line 2206 re-rounding the *same value* a different way, moments later, in the same method. A "byte-identical" claim has to specify **which of these four rules a given entry point is being checked against**, because the codebase itself doesn't apply one consistently — the harness has to characterize *per call site*, not assume a single global rounding contract exists to check against.

3. **The system's own integrity check already tolerates ±1.00 — 100x looser than RULES.md's own $0.01 breaker.** ONE-OFF-2: `saveBill`'s client-vs-server total reconciliation accepts any difference within ±1 whole currency unit before flagging a mismatch. This is the codebase's own tacit admission that its current floating-point output is *not* internally self-consistent to the cent — so a shadow-test harness that naively diffs new-vs-legacy output to the cent, using RULES.md's stated $0.01 tolerance, would flag legacy-vs-legacy noise (re-running the *same* unmodified code twice, if any of the ~150+ duplicated co-pay-split call sites have order-of-operation nondeterminism from unordered collection iteration) as a false failure before a single line of new code is even touched.

**What this means "the harness confirms nothing changed" has to actually mean, concretely:**

- **For characterization tests (wave 1):** the assertion is "this exact method, called with this exact input, still produces this exact `double` bit pattern (or this exact rounded-to-scale `BigDecimal`, if the call site under test already goes through one of the four rounding engines) as it did when the test was recorded" — not "the math is correct." A characterization test passing is not a claim that the underlying calculation is right; RISK-1/RISK-2/ONE-OFF-2 already prove several of them aren't. It is a claim that whatever the calculation currently does, a future change to that code path (a Java-version bump, a refactor, a real bug fix) either preserves it exactly or the test fails and forces a conscious decision — logged as a Behavioral Change per RULES.md, exactly as CLAUDE.md/RULES.md already require.
- **The $0.01 circuit-breaker tolerance is for *production* shadow-test comparisons of new-implementation-vs-legacy on live/historical traffic (wave 2+), not for wave-1 characterization tests, which should assert exact bit/scale equality with zero tolerance** — because wave 1's whole purpose is pinning current behavior precisely enough that "did this change" is unambiguous. Using a loose tolerance in wave 1 would let a real regression hide inside the tolerance band.
- **Before wave 2 (real-data replay) can report a meaningful pass/fail against the $0.01 breaker, someone has to first decide, call-site by call-site, which of RISK-1/2/4/5/ONE-OFF-2's current quirks are being preserved on purpose and which are being fixed on purpose** — otherwise "the new code differs from legacy by $0.02" is indistinguishable between "real regression" and "we finally fixed the whole-unit-rounding bug in `BillingMasterController.java` on purpose." This triage is `AUDIT_BillingRisk.md`'s own recommended next step, not a new requirement invented here.
