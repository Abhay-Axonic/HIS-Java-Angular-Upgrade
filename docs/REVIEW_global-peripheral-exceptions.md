## Methodology

This fix cycle used two distinct mechanisms, applied in sequence:

1. **AI-driven batch fixes** (the bulk of the 8,011 standard-fix findings): parallel fix passes over `docs/AUDIT_Global_exceptions.md`'s peripheral rows, following the exact pattern already established and owner-approved starting with BR-006 — replace an empty/`printStackTrace()`-only/console-only catch body with `logger.error(<exception>.getMessage(), <exception>)` followed by `throw new ServiceException(...)` (or `BillingException`, matching the file's pre-existing convention where one existed), adding a class-level logger to any file that lacked one. The two findings groups requiring different treatment (fabricated-success, `ScheduledLogsScheduler.java`'s batch-continuation risk) were identified during this pass and explicitly excluded from the batch assignment lists rather than force-fixed, consistent with this project's established practice (BR-007/008, BR-012, BR-021, Abdm's BR-PENDING-abdm-exceptions).

2. **A mechanical Python script** (`legacy/fix_unreachable.py`, committed in `b47f4135`, removed as a stray scratch file in `ea65b198` — its logic is preserved here for the record since it no longer exists in the tree): once a catch block unconditionally `throw`s instead of falling through, Java's definite-reachability rule turns any trailing `return` statement after the (former) fallthrough into a compile error (`unreachable statement`) — the same mechanical consequence documented by hand in BR-006/007/009/010/011 for smaller files. Given the scale here (738 files), this cleanup was automated instead of done by hand: the script ran `mvn -pl Global -am compile -DskipTests -o`, parsed every `[ERROR] <file>:[line,col] unreachable statement` line, and for each one either deleted the now-dead trailing `return` statement or, where a closing brace shared the same physical line as the `return`, preserved the brace and removed only the `return`. It iterated this compile-parse-patch loop (up to 400 iterations) until a compile produced zero unreachable-statement errors, and would stop and print raw output for manual review if it ever encountered a compile error it didn't recognize as this specific pattern, or a trailing statement that didn't look like a plain `return`. This is the same fix applied by hand in every prior module's cycle — the script only changes *how* the leftover dead-code line was found and removed, not the resulting code shape or the underlying decision (a `return` that can only be reached by falling through a catch that used to swallow the exception is unreachable once that catch always throws).

   Because the original AI-driven session was interrupted mid-cycle, the working tree at resumption had a mix of already-fixed and not-yet-fixed catch blocks plus a set of unreachable-statement compile errors from the fixes already applied. Commit `b47f4135` ("Continue Global peripheral exception-handling fix: resolve all remaining unreachable-statement compile errors from interrupted session") is the point where the script's cleanup pass and the session's resumption were both folded into a single commit — there was no earlier commit on this branch capturing the pre-interruption state, so `b47f4135` is this branch's first commit and already contains the full 738-file result.

## The 15 held-back fabricated-success findings

Full detail in `docs/DECISION_NEEDED_Global_Peripheral_FabricatedSuccess.md`; summarized here and in the `BR-PENDING-global-peripheral-exceptions` manifest entry.

**Group A — 6 findings, 6 files** (`AllergyPatientMapperDaoImpl.java`, `AppointmentVitalMapperDaoImpl.java`, `MedicationHistoryDaoImpl.java`, `PatientFamilyHistoryDaoImpl.java`, `PatientMedicalHistoryDaoImpl.java`, `PatientSurgicalHistoryDaoImpl.java`): each catch wraps a secondary, best-effort MyLife-sync push that runs *after* the primary database save has already succeeded. Option B (recommended and approved): response/behavior left exactly as-is (still genuinely `SUCCESS` for the primary save), empty or console-only catch bodies replaced with `logger.error(...)` so the sync gap is now visible centrally. Refactoring (Safe) — no caller-visible behavior changed.

**Group B — 9 findings, across `OrganizationWebRegistrationController.java`, `TwilioController.java`, `whatsAppServiceImpl.java` (6 send methods), and `UserRoleMasterDaoImpl.java`**: each catch is the *entire* operation, and previously returned a fabricated `SUCCESS`/`SUCCESS_CODE` status despite a real caught exception. Option B (recommended and approved): kept the existing `Response`/`ResponseTwilio`-returning contract (no `throw`, no HTTP-status change), but flipped the fabricated `SUCCESS` to an honest `ERROR`/`ERROR_CODE` and added `logger.error(e.getMessage(), e)`. Behavioral Change — a caller that branches on the status field now sees the true outcome. (Note: the decision doc's own prose labels this "3 files" while listing 4 file names; the manifest entry and this doc count the actual 4 files that received code changes — `OrganizationWebRegistrationController.java`, `TwilioController.java`, `whatsAppServiceImpl.java`, `UserRoleMasterDaoImpl.java` — confirmed against `git show --stat 75dab436`.)

Applied in commit `75dab436`. Verified via `mvn -pl Global -am compile -DskipTests -o`: BUILD SUCCESS — expected, since none of these 15 fixes removed a `throw`/`return`, only added logging or changed a status-field value in place, so no reachability analysis was triggered.

## The 14 `ScheduledLogsScheduler.java` findings — interim log-only fix

Full detail in `docs/DECISION_NEEDED_ScheduledLogsScheduler_BatchContinuation.md`. This is the only file in the 8,040-finding peripheral set whose class carries `@Scheduled` methods. Converting any of its 14 catches to the standard `throw`-based fix would risk permanently disabling the entire scheduled sync job: both `syncSchedulingLogs()` and `syncPathalogyReport()` use a static guard flag (`isExecuted` / `isLabReportSync`) that is reset to `'N'` only on normal completion of the `try` block, with no `finally` — a thrown exception would leave the flag stuck at the "running" value forever, silently stopping the job until an application restart, with nothing downstream watching for it. Twelve of the 14 findings are additionally inside a per-record loop, so a `throw` there would also abort every other pending record in that run.

Interim fix applied (no owner sign-off needed, matching the same-shaped precedent already used for HIS-WAR/Procurement/Inventory batch-continuation risks): a class-level `org.apache.log4j.Logger` was added, and all 14 catch bodies now call `logger.error(<context>, e)` — confirmed via `git diff` (14 `logger.error` calls added, 0 new `throw` statements in this file). No `throw` was added and no control flow changed; every sync failure is now visible in the centralized log for the first time (previously 12 silently discarded, 2 `printStackTrace()`-only), while the existing swallow-and-continue behavior — and the existing, separate stuck-flag bug — is preserved exactly as today. Classified Refactoring (Safe): no caller- or scheduler-visible behavior differs.

**Not yet resolved:** the stuck-flag bug itself (wrapping the guard reset in a `finally`) is a pre-existing defect, independent of this exception-handling audit, that must be fixed *before* any future decision to convert these catches to `throw` — otherwise every thrown exception reintroduces the "job dies until restart" risk. That fix, and the subsequent per-catch throw/no-throw decision, remain open and are explicitly out of scope for this branch.
